# 场景 9：相机验证与测试基础设施

**典型题：** 你负责一个 30 人的相机团队，如何建立让这个团队能持续快速交付的验证体系？

**核心考点：** 回放框架、硬件在环、金标语料、故障注入、fleet 遥测、以及"什么该自动化什么不该"。

**为什么这题会出现：** 这是 **E6 及以上专属的题**。E5 被问"怎么设计相机系统"，E6 会被问"怎么让一个团队在这个系统上持续交付"。而且它是**唯一一道你可以主动引出的题**——在任何一道设计题的 §9 里说"我会建立 X"，面试官很可能顺势深挖。

**如果面试官没问，你也应该在别的题里主动提。** 因为绝大多数候选人在这一层是空白的。

---

## 1. 需求与约束

| 维度 | 现实 |
|------|------|
| 团队 | 20–50 人：驱动、ISP、3A/IQ、算法、框架、测试 |
| 变更频率 | 每天几十个 PR；每周 FW/IQ 包更新 |
| 硬件稀缺 | 早期样机只有几十台，且被抢；不同 EVT/DVT/PVT 阶段硬件不同 |
| 反馈延迟 | 真机测试一轮几小时；等硬件排队可能几天 |
| 失败成本 | 一个画质回归上线 → 用户投诉 → 灰度回滚 → 一周 |
| 不可自动化的部分 | "好不好看"、"晕不晕"、"烫不烫" |

**开场金句：** 相机团队最大的效率杀手是**反馈回路太长**——改一行 3A 代码要拿到真机、拍一组照片、人眼看一遍，一轮两小时。所以基础设施的核心目标只有一个：**把尽可能多的验证从"真机 + 人眼"搬到"离线 + 自动"**，同时诚实地承认哪些永远搬不动。我会按**反馈回路的时间尺度**分层设计，从秒级到周级，每一层解决不同的问题。

---

## 2. 分层架构：按反馈时间尺度组织

```
┌─ 秒级 ─────────────────────────────────────────────┐
│ 单元测试 / 算子级测试                                 │
│ 纯软件，无硬件，PR 门禁                               │
└────────────────────────────────────────────────────┘
┌─ 分钟级 ───────────────────────────────────────────┐
│ **离线回放（Replay）**  ← 这一层是整个体系的基石         │
│ 录制的 RAW + metadata + IMU → 灌进真实代码 → 比对输出   │
│ 无硬件，可大规模并行，PR 门禁                          │
└────────────────────────────────────────────────────┘
┌─ 十分钟级 ─────────────────────────────────────────┐
│ **硬件在环（HIL）**                                  │
│ 真硬件 + 自动化夹具（光箱、转台、图卡切换）              │
│ 数量有限，合入主干后跑                                │
└────────────────────────────────────────────────────┘
┌─ 小时–天级 ────────────────────────────────────────┐
│ 长跑 / 压力 / 热 / 功耗 / 稳定性                      │
│ 夜间跑，每日报告                                     │
└────────────────────────────────────────────────────┘
┌─ 周级 ─────────────────────────────────────────────┐
│ **人工评测**：主观画质、舒适度、可用性                  │
│ 不可自动化，但可以流程化和量化                          │
└────────────────────────────────────────────────────┘
┌─ 持续 ─────────────────────────────────────────────┐
│ **Fleet 遥测**：真实用户、真实场景、长尾                │
└────────────────────────────────────────────────────┘
```

**设计原则：每一层只做这一层能做的事，并且尽量把问题往上层（更快的层）推。**

## 3. 核心子系统

### 3.1 回放框架：整个体系的基石

> **如果只能建一样东西，建这个。**

**要求：**

```
录制：RAW 帧 + 完整 metadata（曝光/增益/色温/时间戳/序号）
      + IMU 原始样本 + 所有硬件时间戳 + 传感器型号与标定
回放：脱离硬件，灌进**真实的生产代码**（不是简化的仿真）
输出：bit-exact 可比对
```

**关键设计约束（这些决定了它有没有用）：**

| 约束 | 为什么 |
|------|--------|
| **必须能重现时序** | 丢帧、乱序、时间戳抖动都要能在回放里复现，否则测不到时序相关的 bug |
| **必须是生产代码** | 一个"简化仿真"只能测算法逻辑，测不到集成问题——而集成问题占 bug 的大头 |
| **必须 bit-exact** | 否则无法做"这次改动是否影响输出"的判断，只能靠指标阈值（会漏掉小回归） |
| **必须能故障注入** | 见 §3.4 |
| **必须快** | 目标是一段 10 秒的录制在 1 分钟内跑完，否则进不了 PR 门禁 |

**收益（要能说出量化的收益）：**

- IQ 调参：改一个参数 → 10 分钟跑完全部语料，而不是重新拍摄
- 算法回归：每个 PR 自动跑，回归当场暴露
- 现场问题复现：用户上传的 RAW 能在本地精确重现
- **不需要硬件**：新人第一天就能开始改代码

> **E6 的表述：** "回放框架的投入大约是 2–3 个工程师 × 一个季度。它的回报是**每个工程师每天省下 1–2 小时的真机等待**——30 人的团队就是每天 40 小时，一个月回本。**而且它是唯一能让团队规模线性扩展的基础设施**：没有它，第 31 个工程师只会让抢硬件的队列更长。"

### 3.2 硬件在环（HIL）

回放测不到的：真实传感器行为、驱动/内核、时序、功耗、热。

**典型 HIL 台架：**

```
[被测设备] ── 固定在夹具上
     │
     ├─ 面对：可编程光箱（色温、亮度可扫）+ 电动图卡切换
     ├─ 装在：电动转台（可编程运动，用于 tracking / EIS / RS）
     ├─ 供电：电源分析仪（逐轨功耗）
     ├─ 探针：示波器 / 逻辑分析仪（FSYNC、I2C、MIPI 状态）
     ├─ 环境：温控箱
     └─ 输出：串口日志 + adb + 屏幕采集（HDMI/CSI capture）
```

**关键设计：完全无人值守。** 任何需要人手动摆图卡、手动改光源的台架，都不会被真正用起来。

**HIL 数量的经济学：**

> "HIL 台架每台几万到几十万美元。数量不够就会变成新的瓶颈。我的做法是**分级**：
> - **少量高配台架**（转台 + 温控 + 电源分析）：跑完整的每日验证
> - **多台低配台架**（只有光箱 + 图卡）：跑 IQ 和基本功能，数量足够让每个 PR 都能排上
>
> 把'每个 PR 都要跑'的部分设计成用最便宜的台架就能跑，是让 HIL 真正可扩展的关键。"

### 3.3 金标语料库

| 语料 | 内容 | 用途 |
|------|------|------|
| **IQ 语料** | 几百到几千段 RAW，覆盖光照/场景/传感器 | ISP 和 IQ 回归 |
| **失败案例库** | 历史上出过问题的每一个场景 | **每个 bug 修复后必须往这里加一条** |
| **Tracking 语料** | RAW + IMU + 动捕真值 | VIO 精度回归 |
| **长尾人群语料** | 不同肤色、眼型、佩戴方式（见 [`05-eye-face-tracking.md`](./05-eye-face-tracking.md) §9.2） | 公平性验证 |
| **压力语料** | 极端场景：全黑、强逆光、快速运动、闪烁光源 | 鲁棒性 |

> **"每个 bug 修复后必须往失败案例库加一条"是最重要的流程约定。** 它让语料库随时间单调变好，而且保证同一个 bug 不会回来。**这不是技术，是纪律——但建立这个纪律是 E6 的工作。**

**语料的版本管理：** 语料本身要有版本、要能追溯"这段是为了哪个 bug 加的"、要定期审查（有些语料会过时）。语料库最终会到 TB 级，需要真正的数据管理而不是一个共享文件夹。

### 3.4 故障注入：降级路径不测试就等于不存在

**这是被忽略最多的一层。** 每一道设计题的 §8 都列了降级阶梯，但**如果没有测试，那些代码路径从来没被执行过**——它们在真正需要的时候几乎必然是坏的。

| 注入什么 | 怎么注入 |
|---------|---------|
| 丢帧 / 乱序 | 回放框架里直接构造 |
| 时间戳抖动 / 时钟漂移 | 回放框架里改时间戳 |
| MIPI CRC 错误 | 驱动里的调试钩子，或硬件上人为干扰 |
| Buffer 耗尽 | 限制池大小 |
| 客户端崩溃 | kill 进程 |
| NPU / IPE hang | 调试钩子让它不返回 |
| 热失控 | 伪造温度读数 |
| 标定损坏 | 写入坏数据 |
| 传感器掉线 | 断供电（HIL 上可以做） |

**验收标准不是"不崩溃"，而是"表现符合设计"**：进入了预期的降级档、遥测上报了正确的原因、恢复后回到正常态。

> **一句要说的话：** "我会要求**每一条降级路径都有一个对应的故障注入测试**，并且这个映射关系是可审计的——设计文档里的每一行降级，都能指向一个测试用例。**没有测试的降级路径，我在设计评审时就不接受。**"

### 3.5 不可自动化的部分：诚实地对待它

**永远搬不到自动化的：**

| 项 | 为什么 | 怎么做 |
|----|--------|--------|
| **主观画质** | "好看"没有客观定义 | 盲测 A/B、固定显示设备、足够样本量、统计显著性 |
| **舒适度 / 晕动** | 生理反应 | 标准问卷（SSQ）、A/B 而非绝对评分、敏感人群分组 |
| **热的主观感受** | 与材质、接触面积相关 | 人体试戴 + 与热电偶建立相关性 |
| **可用性** | 用户能不能理解 | UXR 的工作 |

> **E6 的态度：** "我不会假装这些能自动化。但我会做两件事：**① 把它们流程化**——固定的评测流程、固定的被试池、固定的呈现设备，让结果可比较；**② 用它们去校准自动化指标**——如果我能证明客观指标 X 和主观评分的相关性是 0.9，那我就可以用 X 做日常门禁，只在重要节点做主观评测。**这是把周级反馈变成分钟级反馈的唯一正当途径。**"

### 3.6 Fleet 遥测：唯一能看到长尾的地方

实验室永远测不到的：真实光照的组合、用户的奇怪操作、硬件的个体差异、长时间使用的累积效应。

**设计原则：**

| 原则 | 说明 |
|------|------|
| **只上标量，绝不上像素** | 隐私红线 |
| **分层计数器是架构要求** | 每一层（sensor/CSI/IFE/IPE/HAL/App）都要有独立的成功和失败计数——见 [`../additional_questions.md`](../additional_questions.md) §3 |
| **端上过滤** | 不要上传每帧的指标，上传聚合 + 异常样本 |
| **可分组** | 按 SKU、传感器批次、固件版本、地区分组，否则回归会被平均掉 |
| **有 kill switch** | 遥测本身出问题时能远程关掉 |

**最重要的用法是 OTA 灰度守护：**

```
灰度 1% → 对比灰度组与对照组的每一个 SLI
任一显著回归 → 自动 halt rollout
```

> "**没有 fleet SLI 的 OTA 是在赌博。** 相机的很多回归（画质变差、偶发掉帧）不会产生崩溃，只会产生用户投诉——而投诉的延迟是几天到几周。等你从投诉里发现问题，100% 的设备已经更新了。"

## 4. 优化与边界

| 问题 | 策略 |
|------|------|
| **CI 时间过长** | 分层门禁：PR 只跑秒级+分钟级；合入主干跑 HIL；夜间跑长跑 |
| **测试不稳定（flaky）** | 相机测试天生有噪声（光源波动、时序抖动）。**对策不是加重试，是让指标本身鲁棒**（用分位数而非单次值、用统计检验而非阈值比较） |
| **HIL 排队** | 见 §3.2 的分级策略 |
| **语料库膨胀** | 定期审查；用覆盖度分析找冗余；分"必跑"和"完整"两档 |
| **回放与真机不一致** | 定期做一致性检查：同一场景真机跑 + 回放跑，输出必须一致；不一致本身就是 bug |

## 5. 跨团队落地

| 团队 | 契约 |
|------|------|
| 各开发团队 | 新功能必须带回放语料和故障注入测试才能合入 |
| 测试 / QA | 台架的运维、语料的管理、报告的产出 |
| 数据 / 云 | 遥测的采集、存储、看板 |
| 隐私 | 遥测的数据分级审查 |
| 制造 | HIL 台架与产线工装的复用（部分可以共用） |
| 管理层 | **基础设施的投入需要被当成产品功能来排期**，而不是"有空再做" |

## 6. 数字预算：基础设施的 ROI

### 6.1 回放框架的投入产出

**投入：** 2.5 人 × 1 个季度 ≈ 0.6 人年。

**产出（保守估计）：**

| 收益项 | 计算 |
|--------|------|
| 省下的真机等待 | 30 人 × 1.5 h/天 × 200 天 = **9000 小时/年 ≈ 4.5 人年** |
| 避免的回归上线 | 假设每年拦下 3 次画质回归，每次的处理成本（排查+回滚+重发）约 20 人日 = **60 人日** |
| 新人上手加速 | 每个新人省 2 周的环境搭建和硬件等待 |

第一年 ROI：


$$
\mathrm{ROI} \approx \frac{4.5 + 0.3}{0.6} \approx \mathbf{8\times}
$$

> **把基础设施的价值算成人年，是 E6 争取资源的方式。** "我需要两个人做三个月的回放框架"这句话在排期会上会输给任何一个产品功能。"这个投入第一年回报 8 倍，而且它是团队规模能否继续扩张的前提"——这句话不一样。

### 6.2 HIL 台架数量

假设每个 PR 需要 15 分钟 HIL 时间，每天 40 个 PR：

台架小时/天：


$$
H_{\mathrm{demand}} = \frac{40 \times 15}{60} = 10\ \mathrm{h/day}
$$

按每台架每天有效 16 小时（留出维护和排队缓冲，利用率 60%）：

基础功能所需台架数：


$$
N_{\mathrm{rig}} = \frac{10}{16 \times 0.6} \approx \mathbf{1}
$$

**但这只是"每 PR 必跑"的部分。** 加上每日全量、夜间长跑、专项调试，实际需要 **5–10 台**，其中高配（转台+温控+功耗）2–3 台。

> **利用率 60% 这个数字要主动说：** "我不会按 100% 利用率规划。测试台架排到 90% 利用率时，排队时间会指数增长（排队论），反馈回路又变长了——**那就回到了我们要解决的原问题**。留出缓冲不是浪费，是保证反馈速度。"

### 6.3 什么该进 PR 门禁：用时间和拦截率算

| 测试层 | 耗时 | 拦截率（发现的 bug 占比） | 该进 PR 门禁吗 |
|--------|------|------------------------|---------------|
| 单元测试 | 2 min | 20% | ✅ |
| **回放（精简语料 50 段）** | 8 min | **45%** | ✅ |
| 回放（完整语料 2000 段） | 3 h | +10% | ❌ 夜间 |
| HIL 基础功能 | 15 min | 15% | ✅（如果台架够） |
| HIL 全量（含热、功耗） | 2 h | 8% | ❌ 每日 |
| 长跑 | 8 h | 2% | ❌ 夜间 |

> **门禁的设计是一个优化问题：** 最大化拦截率，约束是总耗时 < 30 分钟（超过这个数开发者就会开始想办法绕过）。**"开发者会绕过太慢的门禁"是必须纳入设计的人性事实**，不是纪律问题。

## 7. 关键决策与被否方案

| 决策 | 我选 | 否掉的 | 为什么 | 什么会让我翻盘 |
|------|------|--------|--------|----------------|
| 回放用什么代码 | **生产代码本身** | 简化的算法仿真 | 仿真测不到集成问题，而集成问题是 bug 的大头；而且仿真会和生产代码漂移 | 生产代码与硬件耦合太深无法解耦——**那本身是需要修的架构问题** |
| 比对方式 | **bit-exact 为主 + 指标阈值为辅** | 只比指标 | 指标阈值会漏掉小回归，而小回归会累积 | 算法本身有不确定性（多线程、浮点归约顺序）——此时要先消除不确定性，实在不行才退到指标 |
| 门禁范围 | **< 30 分钟，最大化拦截率** | 跑全量 | 太慢的门禁会被绕过 | — |
| flaky 测试 | **让指标鲁棒（分位数、统计检验）** | 加重试 | 重试掩盖真实的间歇性问题 | — |
| 主观评测 | **流程化 + 用来校准客观指标** | 完全依赖客观指标 / 完全依赖人眼 | 前者会优化出难看的图，后者不可扩展 | — |
| 语料管理 | **每个 bug 加一条，定期审查** | 随手放共享盘 | 无法追溯、无法去重、会腐烂 | — |
| 遥测 | **分层计数器在架构阶段设计进去** | 出问题了再加日志 | 事后加的日志覆盖不全，而且改架构成本高 | — |
| HIL 自动化程度 | **完全无人值守** | 半自动（人摆图卡） | 需要人的台架实际利用率会很低 | 某些测试（例如佩戴）物理上需要人 |

## 8. 这套体系本身的失效模式

**基础设施也会坏，而且它坏了很难被发现（因为它坏了通常表现为"测试都过了"）。**

| 失效 | 检测 | 恢复 |
|------|------|------|
| **回放与真机漂移**（回放通过但真机失败） | 定期一致性检查：同场景真机 vs 回放 | 修回放；这本身是 P0 bug |
| **语料库覆盖不足**（新场景没有语料） | 用 fleet 上的失败场景反查语料库有没有 | 补语料 |
| **门禁被绕过** | 统计 skip / force-merge 的频率 | 如果频率高，说明门禁太慢或太 flaky——**修门禁而不是骂人** |
| **flaky 测试导致信任崩塌** | 测试的失败率统计 | flaky 率超阈值的测试**下线修复**，不要留在门禁里降低信任 |
| **HIL 台架漂移**（光源衰减、图卡脏污） | **金标设备定期跑**（同 [`08-calibration-system.md`](./08-calibration-system.md) §9.2 的思路） | 校准或更换 |
| **指标与用户体验脱钩** | 客观指标全绿但用户投诉上升 | 重新校准指标与主观评分的相关性 |
| **遥测本身有 bug** | 数据的自洽性检查（各层计数器之间的守恒关系） | 修复；期间不能盲信数据 |

**最后一行值得强调：**

> "分层的丢帧计数器之间应该满足守恒关系：sensor 出的帧数 = CSI 收到 + CSI 丢的，以此类推。**如果这个等式不成立，说明遥测本身有 bug**。我会把这类自洽性检查做成遥测系统的自监控——因为**基于错误数据做的决策比没有数据更糟**。"

## 9. 怎么证明这套体系是有效的（元验证）

**这是这道题最"元"也最能体现 E6 的部分：你怎么知道你的测试体系是好的？**

| 指标 | 定义 | 说明 |
|------|------|------|
| **逃逸率（escape rate）** | 到达 fleet 的 bug 中，本应被哪一层拦住却没拦住的比例 | **最核心的指标**。每一个逃逸的 bug 都要做归因："哪一层该拦住它？为什么没拦住？" |
| **拦截层分布** | bug 被哪一层发现 | 健康的分布是金字塔形（越早的层拦得越多）；如果大量 bug 在 HIL 或 fleet 才被发现，说明前面的层不够 |
| **反馈时间 p50/p95** | 从提交到拿到完整结果 | 直接决定开发者的迭代速度 |
| **门禁通过率** | 太高说明门禁没用，太低说明太严或太 flaky | 健康区间大约 80–90% |
| **flaky 率** | 同一提交重跑结果不一致的比例 | < 1%，否则信任崩塌 |
| **语料覆盖度** | fleet 上的失败场景中，语料库已覆盖的比例 | 应该单调上升 |
| **基础设施可用率** | 台架和 CI 的正常运行时间 | < 95% 就会成为瓶颈 |

> **逃逸归因（escape analysis）是最重要的流程：** "每一个到达用户的相机 bug，我都会问一个问题——**'哪一层测试本应该拦住它？'** 答案通常是三种之一：① 那一层没有对应的用例（→ 补用例，通常是补语料）；② 有用例但没覆盖到这个条件（→ 扩展用例）；③ 根本没有合适的层能拦（→ 需要新的验证能力）。
>
> **第三种最有价值**，因为它指出了基础设施的缺口。这个流程跑几个季度，测试体系就会自然收敛到覆盖真实的风险分布，而不是覆盖我们想象中的风险分布。"

## 10. 演进与组织

### 10.1 建设顺序（依赖倒排）

| 阶段 | 建什么 | 为什么这个顺序 |
|------|--------|---------------|
| **第一** | **录制能力 + 基本回放** | 一切的前提；而且录制能力越早有，语料积累的时间越长 |
| 第二 | 分层计数器 + 基本遥测 | 需要在架构阶段设计进去，晚了要改架构 |
| 第三 | PR 门禁（单元 + 精简回放） | 立刻开始拦截回归 |
| 第四 | HIL 基础台架 | 覆盖驱动和时序 |
| 第五 | 故障注入 | 配合降级路径的开发 |
| 第六 | 金标语料 + 主观评测流程 | 需要时间积累 |
| 第七 | Fleet SLI + OTA 灰度守护 | 上线前必须就位 |
| 第八 | 逃逸归因流程 | 有 fleet 数据后才能做 |

**关键判断：录制能力必须最早做，哪怕回放还没做完。** 因为语料的价值来自覆盖面和时间——早期样机上拍到的场景，后面拍不回来了（硬件都变了）。

### 10.2 组织上的三条

**① 基础设施要有明确的 owner，不能是"大家有空就做"**

> "共享的所有权等于没有所有权。我会指定 1–2 个人专职负责验证基础设施，并且**让他们的绩效由团队的交付速度衡量**，而不是由他们写了多少测试衡量。"

**② 把"带测试"做成合入的硬门槛，但要先把写测试变容易**

> "要求'新功能必须带语料和故障注入测试'之前，我必须先保证**添加一条语料是 5 分钟的事而不是半天**。如果基础设施难用，纪律要求只会产生应付了事的测试。**先降低成本，再提高要求**——顺序反了就会失败。"

**③ 逃逸归因要是无责的（blameless）**

> "逃逸归因如果变成追责，人们就会隐瞒和辩解，这个流程立刻失效。它的目的是找基础设施的缺口，不是找人的错误。**这需要我在第一次做归因时就明确树立规范**——第一次做错了，后面就再也做不起来了。"

### 10.3 怎么向上争取资源

这是 E6 的真实工作。三个有效的论证：

| 论证 | 形式 |
|------|------|
| **ROI 算成人年** | §6.1：0.6 人年投入换 4.8 人年产出 |
| **规模化的前提** | "没有回放框架，团队规模超过 20 人后边际产出会下降——第 21 个人只是让抢硬件的队列更长" |
| **风险的量化** | "一次画质回归上线的成本是 X（排查 + 回滚 + 重发 + 用户信任）。回放框架每年拦下 3 次就回本了" |

> **最后一条最有效**，因为它把基础设施从"效率提升"（nice to have）变成了"风险控制"（must have）。

**收口金句：** 相机团队最大的效率杀手是反馈回路太长，所以验证体系要**按反馈时间尺度分层**，把尽可能多的验证从"真机+人眼"搬到"离线+自动"。基石只有一个——**能用生产代码 bit-exact 回放录制数据的框架**，它的 ROI 第一年就是 8 倍，而且它是团队规模能否继续扩张的前提。而衡量这套体系是否有效的元指标是**逃逸归因**：每一个到达用户的 bug 都要回答"哪一层本应拦住它"，这个流程跑几个季度，测试体系就会收敛到真实的风险分布上——**而不是我们想象中的风险分布。**
