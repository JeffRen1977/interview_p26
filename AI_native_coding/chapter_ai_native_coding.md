## 引子：一个被压缩到 60 分钟的行业转折

2025 年 10 月，Meta 开始在 onsite 里试点一轮新的面试。它替换掉了两轮算法题中的一轮，规则很简单：60 分钟，一个 CoderPad 三栏工作区（左边文件树、中间编辑器、右边一个内置的 AI 助手），一个你没见过的小工程，一套预置的单元测试。你可以随便用 AI——事实上，题目的工作量就是按"你会用 AI"来设计的。

这一轮迅速在候选人社区里引起困惑。困惑的原因不是它难，而是它**不像面试**。没有"给定一个数组，返回……"，没有白板。你打开仓库，看到的是四个文件、一个跑不过的测试套件，和一句"先把它修好"。

我认为这一轮值得单独写一章，理由和面试无关。它是我见过的**对"AI 原生编程"这件事定义得最准的一份操作化描述**。它不问"你会不会用 AI"，它问的是：当写代码这个动作的边际成本趋近于零之后，一个工程师身上**剩下的**能力是什么。

这一章讲的就是那个"剩下的东西"。

## 一、稀缺资源的迁移

过去二十年，软件工程的方法论几乎都建立在一个隐含前提上：**写代码是昂贵的**。设计模式、复用、抽象层、代码生成器、DRY 原则——它们要解决的都是同一个问题，即减少人类敲键盘的次数。代码评审之所以是瓶颈，是因为写它的人花了三天；重构之所以谨慎，是因为改错了要再花三天。

这个前提正在失效。不是"部分失效"，是在很多具体场景里**彻底失效**。一个能被清晰描述的函数，从描述到可运行实现，成本已经从"小时"掉到"秒"。

但工程并没有因此变便宜。稀缺资源只是换了个地方：

| | 旧稀缺 | 新稀缺 |
|---|---|---|
| 昂贵的动作 | 把想法变成代码 | 把想法变成**精确的**描述 |
| 昂贵的动作 | 手写实现 | 判断生成的实现**是否真的对** |
| 瓶颈岗位 | 能写的人 | 能**定义**和能**验证**的人 |
| 主要风险 | 写不完 | 写完了，但和你以为的不是一回事 |

这不是修辞。它有一个可观察的后果：**一段语法正确、类型正确、看起来完全合理、并且通过了现有测试的代码，可能是错的**——而且错得比人手写的更隐蔽，因为它没有人类犯错时留下的那些"痕迹"（犹豫的命名、半途而废的注释、不一致的缩进）。AI 生成的错误代码，长得和正确代码一模一样。

于是"定义"和"验证"这两件事的价值被顶上去了。Meta 那一轮的三段式结构，恰好把这两件事拆成了可打分的动作。

## 二、三段式结构里的三个缺口

按面经整理，这一轮的题池不大（一个内部说法是九道左右轮换），但结构高度统一：

- **Phase 1 — 修一个已经埋好的 bug**（通常明确要求或强烈暗示不用 AI）
- **Phase 2 — 实现核心功能**（明确鼓励用 AI，工作量在 120 行以上）
- **Phase 3 / 4 — 面对更大的输入或更强的约束**，原来的解法会失效

这个顺序不是难度递增那么简单。它对应着**大模型在真实工程里的三种失效模式**，而且是按"越来越难被发现"的顺序排列的。

### Phase 1 揭示的是**上下文缺口**

模型看得到代码，看不到代码**应该**满足什么。不变量、领域约束、上游模块的隐含承诺——这些东西要么写在注释里（模型会读但不会当真），要么写在别人脑子里（模型根本读不到）。所以 Phase 1 的 bug 从来不是语法错误或者笔误，而清一色是**契约违反**：代码在自洽地做一件错事。

### Phase 2 揭示的是**边界缺口**

模型没有"这个不归我管"的概念。你让它实现一个函数，它可能顺手改了另一个函数的签名、引入了一个新依赖、把测试注入的时钟换成了 `time.time()`。它不是恶意的，它只是在优化"让这段代码看起来更好"，而"不许动的东西"从来没有被告诉它。

### Phase 3/4 揭示的是**判断缺口**

模型有性能知识，但没有**性能直觉**，更没有"何时不该优化"的判断。它知道倒排索引比全表扫描快，但它不知道这份数据的选择度接近 1，倒排会退化成扫表还多付一份写放大。它知道 2-hop 展开比全图打分快，但它不知道你的社交图里有一个八千好友的名人。

这三个缺口有一个共同点：**它们都不是"模型不够聪明"造成的，而是"模型没有那份信息"造成的**。这就是为什么"换个更强的模型"解决不了它们，而"把信息组织好再交给模型"能解决大半。

## 三、案例解剖

下面七个案例全部来自本章配套的可运行工程。我挑的不是最难的，而是**最能说明某一类缺口**的。

### 3.1 永远为假的那一行：AI 看不见不变量

社交图推荐（People You May Know）那道题，Phase 1 的校验函数要保证五条规则，其中第三条是"已经是该用户好友的人不能被推荐"。开局代码是这样的：

```python
def is_valid_recommendations(graph, user, candidates):
    if not graph.has_user(user):
        return False
    seen = set()
    for candidate in candidates:
        if candidate == user:
            return False
        if candidate in graph.friends(candidate):   # ← 就是这一行
            return False
        if candidate in seen:
            return False
        seen.add(candidate)
    return True
```

这一行有什么问题？它查的是**候选人自己的**好友集，问的是"候选人是不是自己的好友"。而这张图是**非自反**的——没有人是自己的好友，`add_friendship` 甚至会拒绝自环。所以这个分支**永远不会触发**。

规则三看起来实现了，实际上是一行死代码。

现在换位思考：如果你把这个函数丢给任何一个模型，问"有 bug 吗"，它会怎么回答？大概率它会说"看起来正确地实现了自我推荐检查、好友排除、去重"。因为**从代码本身看，这一行是完全合理的**。要发现它错了，你必须知道一个不在这段代码里的事实：**这张图是非自反的**。

这就是上下文缺口的标准形态。这类 bug 的判据不是"哪一行长得不对"，而是"哪一行的语义依赖了一个没有被表达出来的前提"。

> **可迁移的判断法**：当你 review 一段代码（人写的或 AI 写的），对每一个条件分支问一句"这个分支在什么输入下会被触发？"。答不上来、或者答案是"不会"的分支，就是这类 bug 的藏身处。

### 3.2 上游的谎言：错误的基准比没有基准更危险

编译器优化那道题（三地址码的代价分析）把这个道理演到了极致。它的 Phase 1 bug 在用例加载器里：

```cpp
if (section == "costs") {
    const auto pos = line.find('=');
    result.costs[line.substr(0, pos)] = std::stoi(line.substr(pos + 1));
    //          ^^^^^^^^^^^^^^^^^^^^ "+ = 1" 的 key 是 "+ "，带一个尾空格
} else if (section == "expected") {
    expected[trim(line.substr(0, pos))] = std::stoi(line.substr(pos + 1));
    //       ^^^^ 这一支反而 trim 了
}
```

两处细节值得停一下：

第一，`std::stoi` 会跳过前导空白，所以 `std::stoi(" 1")` 正常返回 1。**value 那一侧完全正常，坏的只有 key**。这种"一半对一半错"的 bug，比全错的 bug 危险得多，因为它不会立刻爆炸。

第二，**同一个 `if / else if` 的两个分支，对同样形状的输入做了不同的处理**。这是这类 bug 能活过 code review 的根本原因：单看任何一支都是对的，只有并排看才发现不一致。

但真正的杀伤力在下游。这个 bug 让整个成本表变成 `{"+ ": 1, "* ": 4, ...}`，于是 `costs.at("*")` 抛异常。如果你没先修它，你会在 Phase 2 花十分钟调试自己的分析器——**而分析器是对的**。更糟的情况是 bug 不抛异常而只是给出错误数字：那时你会让 AI 帮你"修" Phase 2，AI 会顺着错误的基准，把一个正确的实现改成错的，并且让测试变绿。

> **原则**：在 AI 协作中，**先验证数据通路，再验证逻辑**。一个错误的基准会让 AI 成为你的共犯——它会非常高效地帮你朝错误的方向收敛。

### 3.3 契约写在注释里，而 AI 只读代码

TTL 内存 KV 那道题的 Phase 1 bug 只有一行：

```python
self._data[key] = Entry(value, ttl, frozenset(tags or []))
#                              ^^^ 应该是 clock.now() + ttl
```

`ttl` 是"从现在起多少秒"，但被直接当成绝对过期时间戳存了进去。测试把时钟钉在 `t = 1000`，所以 `set("a", 1, ttl=10)` 写进去的 `expires_at` 是 `10`，一读就判死。

这个 bug 的关键在于：**"ttl 是时长不是时刻"这件事，只写在 docstring 里**。类型系统里 `float` 就是 `float`，代码里两者完全无法区分。

这引出一个 AI 时代被严重低估的问题：**我们的类型系统对"单位"和"参考系"几乎一无所知**。时长 vs 时刻、相对路径 vs 绝对路径、行索引 vs 列索引、字节 vs 字符、摄氏 vs 开尔文——这些区别在人脑里是常识，在编译器眼里是同一个类型，在模型眼里是一段可能被忽略的自然语言。

同一个工程里的迷宫题埋的是它的孪生兄弟：`grid[coord.col][coord.row]`——行列写反。正方形迷宫会把这个 bug 完美藏起来，只有 3×7 的非正方形迷宫才会让它下标越界。测试里那个非正方形样例是**故意**放的。

> **工程含义**：如果你希望 AI 少犯这类错，最有效的动作不是写更长的 prompt，而是**把契约从注释挪进类型**。`NewType("Seconds", float)`、`struct Duration`、`Row`/`Col` 两个不同的强类型——这些过去被嫌"啰嗦"的做法，在 AI 协作下的收益率翻了几倍。注释是给人看的，类型是给机器看的，而现在你的协作者是机器。

### 3.4 从 BFS 到 Dijkstra：算法选型不可外包

迷宫题有一条完整的阶梯，从 Q1 一路加到 Q5（Q5 是 2026 年 4 月才加的）：

| 阶段 | 新增需求 | 状态 | 算法 |
|---|---|---|---|
| Q2 | 最短路 | `cell` | BFS |
| Q3 | 方向门（踩上去只能朝指定方向走） | `cell` | BFS |
| Q4 | 钥匙与门 | `(cell, keys_mask)` | BFS |
| Q5 | 崎岖地形 + 炸弹预算 | `(cell, keys_mask, bombs_left)` | **Dijkstra** |

前三级都是"状态变大"，第四级是**算法本身换了**。原因只有一句话：Q5 之前每条边的代价都是 1，这是 BFS 最优的唯一理由；Q5 引入了"踩进崎岖地形花 5 点、炸开一堵墙花 4 点"之后，队列不再按代价顺序访问状态。

具体到测试里的这个迷宫：

```
#######      BFS 的答案：5 格直线，能量 16
#S~~~E#      Dijkstra 的答案：7 格绕行，能量 6
#.....#
#######
```

BFS 会自信地返回那条穿过泥地的直线，因为它确实是"最短"的——按格子数。它不是慢，它是**错**。

这里有两件事是模型很难替你做的。

**第一，代价模型是需求，不是代码。** "踩进泥地花几点"这个数字不在任何一个源文件里，它在题面里、在产品经理的脑子里、在那份你还没读的设计文档里。选 BFS 还是 Dijkstra，取决于这个数字，而这个数字只有你有。

**第二，换算法会连带改变两条不起眼的规矩**，而这两条恰恰是最容易被 AI 生成代码搞错的：

```python
while heap:
    cost, state = heapq.heappop(heap)
    if cost > dist.get(state, cost):
        continue                          # 陈旧堆项
    coord, mask, left = state
    if coord == end and mask == goal_mask:
        return cost, rebuild(parent, state)   # ← 终点判定在 pop，不在 push
```

- **终点判定从 push 时挪到 pop 时**。BFS 里"入队看到终点就返回"是对的，靠的是层序遍历的保证；Dijkstra 里这样写会返回次优解。
- **`visited` 变成 `dist`**。不再是"见过就跳过"，而是"这次更便宜才重新展开"。

如果你只对模型说"改成 Dijkstra"，你有相当大的概率拿到一个保留了 push 时判终点的版本——它跑得很快，测试可能还过了几条，但它是错的。

### 3.5 值域先验：领域知识就是降维

卡牌题（从桌面上找出三张点数和为 15 的牌）的朴素解法是 `itertools.combinations(cards, 3)`，`O(n³)`。当桌面有几千张牌时它会死。

正确的观察只有一句：**牌的点数只有 1 到 9**。所以搜索空间不是"牌"，是"点数"。满足 `r1 ≤ r2 ≤ r3` 且和为 15 的点数三元组，一共只有 **13** 组：

```
(1,5,9) (1,6,8) (1,7,7) (2,4,9) (2,5,8) (2,6,7) (3,3,9)
(3,4,8) (3,5,7) (3,6,6) (4,4,7) (4,5,6) (5,5,5)
```

于是算法变成：数一遍点数频次（`O(n)`），然后对这 13 个固定模式用组合数展开。总复杂度 `O(n) + O(13)` —— **和合法组合的数量完全无关**。对抗性用例里那 `C(2000,3) ≈ 1.3×10⁹` 个三元组，一个都不用碰。

顺带一提，"无解"的判定也从"枚举完所有组合才敢返回 None"变成了 13 次查表——这正是对抗性用例攻击的那个点。

我把这个案例放进来，是因为它演示了一件 prompt 工程解决不了的事：**这个优化的全部内容是一个领域观察**（点数值域是 1..9），而这个观察不在代码里，在牌的规则里。你可以让模型帮你写频次表，但你没法让它替你**注意到**这件事——除非你在 prompt 里已经把它说出来了，而那时优化其实已经被你完成了。

> **顺便一个真实的小故事**：本章配套仓库自己的 README 里，这个数字一度写成了 84（那是"1..9 里所有严格递增三元组"的个数 `C(9,3)`，不是"和为 15"的个数）。**代码是对的，注释是错的**（`all_triplet_ranks()` 一直返回 13 组）。写这一章的时候实际跑了一遍才发现，随后连同 `prompts.md`、`question_bank.md` 里的同一处一起改掉了。这恰好是 3.3 节那个论点的活体标本：注释会漂移，而漂移的注释在 AI 时代不再只是误导人类，它会被当成 prompt 的一部分喂给模型。

### 3.6 同一道题换一门语言，坑会换位置

编译器优化那道题我写了 Python 和 C++ 两个版本，契约完全一致、用例文件是同一批。有意思的是，**Phase 4 最大的陷阱在两个版本里完全不同**。

Python 版的坑是**除法方向**：题目要求整数除法向零截断（C 语义），而 Python 的 `//` 是向下取整。`-7 // 2` 是 `-4`，正确答案是 `-3`。正确写法是 `abs(a) // abs(b)` 再补符号——注意也不能写 `int(a / b)`，大整数会先掉进浮点。

C++ 版的这个坑**根本不存在**：C++ 的整数 `/` 从 C++11 起就保证向零截断，直接写 `a / b` 就是对的。取而代之的是两个 Python 里不存在的坑：

```cpp
std::stoi("4000000000")            // 抛 std::out_of_range
int a = 2000000000 + 2000000000;   // 有符号溢出 = 未定义行为
```

必须 `std::stoll` 解析、`long long` 运算。以及一个更隐蔽的：

```cpp
const std::string& name = stack.back();
stack.pop_back();          // ← name 当场悬空
```

这行悬空引用在 AI 生成的 worklist 代码里出现的频率高得惊人。

**为什么这件事重要？** 因为它揭示了模型的一个结构性偏差：**模型的"常见陷阱"意识来自训练分布，而训练分布不等于你的代码库**。Python 的 `//` floor 陷阱在网上被讨论了千百遍，所以模型对它相当警觉；C++ 的 `stoi` 溢出和悬空引用讨论得少，模型就容易滑过去。

结论不是"C++ 更危险"，而是：**你不能把"模型会替我注意常见陷阱"当成一个稳定的假设**。它注意的是**它见过的多的**陷阱。你的责任是把你这门语言、这个代码库、这个领域里真正致命而讨论稀少的那些，显式写进约束。

在 C++ 版里，这条约束长这样（直接写进 prompt）：

```
- Parse literals with std::stoll and compute in long long. std::stoi would
  throw on 4000000000, and int arithmetic would be signed overflow (UB)
- The worklist is a std::vector<std::string>. Take the top BY VALUE before
  pop_back(): a reference into the vector dangles the moment you pop or push
```

以及一个把"审查"也自动化掉的动作：

```bash
make test CXXFLAGS="-std=c++17 -g -O1 -fsanitize=address,undefined"
```

在 AI 协作里，sanitizer、静态分析、property test 这类工具的价值是**上升**的，因为它们检查的恰好是模型最容易滑过去的那一类错误，而且检查成本是零边际的。

### 3.7 知道优化的失效边界，比知道优化本身更值钱

这是全章最想留下的一条。

社交图推荐的 Phase 4：4 万用户、平均 4 个好友、查 2000 次。朴素做法给图里每个人打分，实测 **14.2 秒**；只走 2-hop 邻域，实测 **0.012 秒**。一千倍。

核心恒等式一句话就能说清：

```
f ∈ friends(user) 且 c ∈ friends(f)  ⟺  f ∈ friends(user) ∩ friends(c)
```

也就是说，"有多少个我的好友指向 c"本身就是共同好友数，根本不用做集合求交。

到这里为止，是一个称职的优化。**真正拉开差距的是下一句**：

> 2-hop 展开不是普遍更优的。它的开销是 `Σ deg(f)`——我所有好友的度数之和。所以**一个名人好友就能主宰全部开销**：如果我关注了一个有 8000 好友的账号，我的 2-hop 要走 8000 步，而小图上的全表扫描可能还不到这个数。生产系统会截断——跳过度数超过阈值的邻居，或者改用 **Adamic-Adar** 权重（`1/log(deg(f))`），让共享一个名人的贡献远小于共享一个密友。

配套测试里专门放了一个八千好友的名人星形图，但那条测试**只断言正确性，不断言速度**——因为实测下来，那个形状里 2-hop（0.4 秒）反而比全表扫描（0.2 秒）慢。这不是测试设计失误，这就是要教的东西。

同样的结构在 TTL KV 那道题里重演：倒排索引在稀有 tag 上是两次哈希查找，但**如果每个 tag 的选择度都接近 1（几乎所有 key 都命中），倒排会退化成扫表，还额外付一份写放大**。

这两个例子指向同一件事。**"用什么数据结构"是可以外包给模型的知识；"这个数据结构在什么形状的数据上会失效"是判断，而判断需要你同时握着算法特性和数据分布**。后者才是你在这一轮、以及在真实工作里，唯一无法被替代的部分。

> **一个可以立刻用的习惯**：每次你（或模型）引入一个优化，强制自己回答一句——"什么样的输入会让这个优化变成负优化？"答不上来，说明你还没真正理解它。

## 四、契约优先的六步循环

前面全是诊断，这一节给方法。它是一个循环，每个 checkpoint 都跑一遍，我把它记作 **RNCPRR**。

| 步骤 | 动作 | 为什么这一步必须存在 |
|---|---|---|
| **R**ead | 只读相关的那一两个函数，不通读全仓 | 通读全仓是在替模型做它擅长的事。你要读的是**契约面**：签名、调用者、测试断言 |
| **N**arrate | **先口述根因，再动手** | 这是唯一能证明"是你在主导"的动作。也是自检：说不清根因，说明你还没定位到 |
| **C**ontract | 写下输入/输出/**不许改的东西** | 对应 §二的边界缺口。没有 Do-NOT 清单，模型的默认行为是"顺手改好" |
| **P**rompt | 四段式指令（下一节） | — |
| **R**un | **你**跑测试，不是模型说"应该过了" | 模型对自己输出的正确性没有可靠的自我评估。它说"已修复"的置信度和它对不对无关 |
| **R**eview | 逐行看 diff，删掉多余的东西 | 模型倾向于"添加"：多余的深拷贝、防御性 try、用不上的参数。这些是熵，会在下一个 checkpoint 咬你 |

**Narrate 那一步千万别省。** 它看起来是面试技巧，其实是工程实践：一个说不出根因就直接让 AI 改的人，在真实项目里会持续生产"看起来修好了"的补丁。区分"会用 AI"和"被 AI 牵着走"，就在这一步。

还有一个几乎零成本、收益极高的动作：**每个 checkpoint 结束时 commit 一次**。

```bash
git add -A && git commit -m "phase1 green"
```

模型把文件改乱是常态而不是意外。`git diff` 是你的 review 界面，`git checkout --` 是你 10 秒钟的后悔药。在 AI 协作下，**commit 的频率应该显著高于以前**——因为"回滚的成本"变成了对冲"生成的不确定性"的主要工具。

## 五、Prompt 是一次对搜索空间的约束

好的 prompt 有四段，缺一不可：

```
Task:        要做什么（一句话，动词开头）
Constraints: 必须满足什么（签名、复杂度、语义、错误类型）
Do NOT:      不许碰什么（其它函数、公共接口、依赖、测试）
Output:      要什么形式的输出（只返回函数体 / 只返回改动的方法）
```

为什么"Do NOT"这一段单独存在？因为它和 Constraints 在信息论上做的是不同的事。

把模型的生成看成在一个巨大的程序空间里采样。**Constraints 是在告诉它目标区域在哪**；**Do-NOT 是在把大片高概率但错误的区域直接切掉**。而那些区域之所以高概率，恰恰因为它们在训练数据里很常见——"顺手重构一下"、"加个防御性检查"、"把这个也改得更好些"在开源代码里到处都是。

对比两个真实 prompt。模糊版：

```
帮我实现 Phase 2
```

约束版（社交图推荐的 Phase 2）：

```
Task: implement recommend_baseline(graph, user, k=5) -> List[str].
Constraints:
- Score of candidate c = |friends(user) & friends(c)|
- Only candidates with score >= 1 are eligible
- Exclude the user and everyone already in friends(user)
- Sort by score descending, then user id ascending; return the first k
- Unknown user or k <= 0 -> []
- Scanning graph.users() is fine at this stage
- The output must satisfy is_valid_recommendations for every user
- Do NOT touch evaluate or recommend_fast
Return only the function body.
```

注意几个细节：

1. **`Scanning graph.users() is fine at this stage`** —— 显式**禁止过早优化**。不写这句，模型很可能直接给你一个 2-hop 版本，于是你就没机会在下一阶段展示"识别瓶颈"这个动作了。在真实工程里，同样的句子叫"这一版先不做缓存"。
2. **`The output must satisfy is_valid_recommendations`** —— 把已有的不变量作为约束交叉引用。这是**用代码约束代码**，比任何自然语言描述都可靠。
3. **`Unknown user or k <= 0 -> []`** —— 边界行为写死。模型对边界的默认选择（抛异常？返回 None？返回空？）是不可预测的。

还有一个很多人不会用的模板，我认为是最高杠杆的一个——**让模型只解释，不写码**：

```
Read <files>. Do NOT write implementation code.
List:
1. The public API I must implement (exact signatures and return types)
2. The invariant each test class is asserting
3. Edge cases implied by the tests
4. Anything the tests do NOT require, so we don't build it
```

第四条是精髓：**明确圈出"不要做的事"**。AI 协作里最大的隐性浪费不是写错，是**写多**。

## 六、验证：差分测试

如果这一章只能留下一节，我希望是这一节。

前面五节讲的都是"怎么让模型少犯错"。这一节讲的是另一半，而且是更重要的一半：**假设它还是犯了错，你靠什么发现？**

### 6.1 预言机问题

软件测试里有一个古老的难题叫**预言机问题**（the oracle problem）：要判断一个程序的输出对不对，你得先知道正确答案是什么；可如果你已经知道正确答案，你为什么还要写这个程序？

传统上我们用三种方式绕开它：手写期望值（`assertEqual(f(3), 7)`）、检查不变量（"输出必须是有序的"）、或者干脆靠人眼。这三种方式在过去够用，是因为**代码产出得慢**——一个函数写三天，你有的是时间盯着它看。

AI 协作把这个平衡打破了。当生成一个实现只要三十秒，**判定它对不对就成了整条流水线上唯一的瓶颈**。手写期望值跟不上（你不可能为每个生成的版本手写一遍），人眼更跟不上（生成的错误代码长得和正确代码一模一样）。

差分测试是对预言机问题的一个特别务实的回答：

> **不要试图凭空知道正确答案。保留那个慢的、显然正确的实现，让它当裁判。**

这句话里每个词都有分量。"慢"意味着它可以用最笨最直白的写法，笨到一眼能看懂；"显然正确"意味着它的正确性靠**阅读**就能确信，不需要再套一层验证；"保留"意味着它不是过渡产物，而是长期资产。

### 6.2 三种形态

差分测试不只有"新旧对比"一种。本章的几个工程里同时用了三种，值得分开命名。

**形态一：等价（equivalence）——同一输入，两个实现，逐字节相同。**

这是最标准的一种。快版和慢版必须给出完全一样的结果，包括排序的 tie-break、包括边界情形的返回值。

```python
def test_same_answers_as_the_baseline(self):
    graph = random_graph(seed=1234, n_users=400, edges_per_user=3)
    for user in graph.users()[:120]:
        self.assertEqual(
            recommend_fast(graph, user, k=5),
            recommend_baseline(graph, user, k=5),
            f"fast and baseline disagree for {user}",
        )
```

注意 `assertEqual` 比的是**列表**，不是集合。tie-break 顺序也在契约里 —— 这一点很容易被放过，而它恰恰是"两个实现看起来都对但结果不同"的高发区。

**形态二：退化（degeneracy）——把新实现约束到旧实现的定义域上，两者必须重合。**

当新实现是旧实现的**严格推广**时，这是最强的一条自检。迷宫题里那条测试是这么写的：

```python
def test_degenerates_to_bfs_when_every_step_costs_one(self):
    maze = Maze.from_text(SQUARE)          # 没有崎岖地形
    result = min_energy_path(maze, bombs=0)  # 没有炸弹
    self.assertEqual(result[0], len(shortest_path(maze)) - 1)
```

当所有边权都是 1、炸弹为 0 时，Dijkstra 的能量必须**精确等于** BFS 路径长度减一。

这条测试的价值在于它的**顺序**：写完 Dijkstra 立刻跑它。如果它红了，说明你的新实现在最简单的情形下就已经错了 —— 复杂情形不用再看。它是一条"廉价的早期否证"，成本几乎为零，却能在三十秒内否掉一个错误的实现方向。

**形态三：变形（metamorphic）——不知道输出应该是什么，但知道输出之间该有什么关系。**

这是最被低估的一种，因为它**不需要第二个实现**。你只需要知道"如果输入这样变，输出应该那样变"。

编译器优化那道题里有一组这样的关系，全部实测成立：

| 关系 | 断言 | 为什么成立 |
|---|---|---|
| 单调性 | `optimize` 后的 time / memory 都不大于优化前 | 优化不许让程序变差，这是"优化"的定义 |
| 幂等性 | `fold_constants(fold_constants(p)) == fold_constants(p)` | 单赋值 + 无分支，一轮即到不动点 |
| 幂等性 | `optimize(optimize(p)) == optimize(p)` | 同上 |

社交图推荐里还有一条：

| 关系 | 断言 |
|---|---|
| 前缀性 | `recommend_fast(g, u, 3) == recommend_fast(g, u, 5)[:3]` |

`k` 只是截断长度，所以小 `k` 的结果必须是大 `k` 结果的前缀。这条在 300 个节点的随机图上逐一验证过，全部成立。

变形关系的好处是**它们几乎都能从契约里直接读出来**。"优化不让程序变差"、"折叠到不动点"、"top-k 是 top-(k+1) 的前缀"——这些句子你在设计阶段就说过，只是从来没把它们写成断言。

> **实践建议**：写完一个函数的 docstring 之后，把里面每个形容词（"最短的"、"最优的"、"排序后的"、"去重的"）都试着翻译成一条变形关系。翻译得出来的，就该有一条测试。

### 6.3 慢实现是资产，不是技术债

工程师的本能是：快版跑通了就删掉慢版，不然是重复代码。

在 AI 协作下这个本能是错的。慢版给你三样东西，每一样都在持续产生价值：

1. **正确性的证据来源**。它是裁判，而且是可以任意扩大样本量的裁判 —— 想更有信心，把随机输入从 400 个加到 40000 个就行，成本是几秒钟。
2. **一份活的性能对照**。社交图那道题里，慢版 14.2 秒、快版 0.012 秒，这个"一千倍"不是估算，是每次跑测试都在重新测量的事实。哪天有人改动了快版让它悄悄退化，这个数字会立刻说话。
3. **一块安全的重构地基**。快版可以被反复重写 —— 换数据结构、换语言、让模型整个重生成一遍 —— 因为有一个不动的裁判在那里。**没有裁判的重构是赌博；有裁判的重构是工程。**

第三点在 AI 时代的权重被显著放大了。既然重新生成一个实现只要三十秒，那么"敢不敢扔掉重写"就完全取决于"重写完敢不敢信"。慢版就是那个"敢信"的来源。

那什么时候可以删掉慢版？我的标准是：**当它不再显然正确的时候**。如果为了让慢版也能跑完大输入，你开始给它加优化，它就失去了当裁判的资格 —— 那时候你有的是两个都需要被验证的实现，而不是一个实现加一个裁判。

### 6.4 输入生成器决定了这条测试的上限

这是差分测试最容易被高估的地方，也是我想重点讲的一节。

**一条差分测试的强度，不取决于比较得多严格，而取决于输入生成器能到达哪里。**

看一个来自本章工程的真实数据。社交图推荐的差分测试用的是这个生成器：

```python
graph = random_graph(seed=1234, n_users=400, edges_per_user=3)
```

我实际量了一下它产生的度数分布：

```
最大度数: 13    前五: [13, 12, 12, 11, 11]    平均: 5.94
```

均匀随机图，度数集中在均值附近。而 §3.7 里那个会让 2-hop 展开退化的形状是什么？**一个有 8000 个好友的名人**。

这个生成器**永远不可能生成那个形状**。哪怕你把随机输入从 400 个加到 4000 万个，最大度数也只会在十几附近晃。所以那条差分测试，无论跑多少次，都无法覆盖 §3.7 讲的那个失效边界 —— 那个用例是**手写**的：

```python
def test_high_degree_hub_is_handled(self):
    graph = SocialGraph()
    for i in range(8_000):
        graph.add_friendship("celebrity", f"fan{i:05d}")
    ...
```

这引出两条实践结论。

**第一，随机生成负责"广度"，手写用例负责"形状"。** 两者不能互相替代。随机输入擅长找那种"我压根没想到的组合"，但它只在生成器的分布里找。真实世界的病态形状 —— 幂律分布的社交图、全是同一个值的数组、深度一万的退化树、恰好等于阈值的边界 —— 几乎都要手写。

**第二，写生成器时要显式回答"我这个分布覆盖了什么、漏掉了什么"。** 这句话应该写成注释放在生成器旁边。本章工程里那个生成器就应该注明：均匀随机、度数集中在均值附近、**不覆盖高度数节点，hub 场景见手写用例**。

还有一条纪律层面的要求：**随机必须可复现**。注意上面那行代码里的 `seed=1234`。一条会随机飘红的差分测试，比没有这条测试更糟 —— 它会训练团队养成"重跑一次就绿了"的习惯，而那正是把真 bug 埋掉的最快方式。种子写死，失败时把种子打进错误信息，需要更多覆盖就加种子，不要靠时间戳。

（如果用 Hypothesis / QuickCheck 这类框架，还能白拿一个**收缩**（shrinking）能力：失败后自动把反例缩到最小。手写生成器时这一步要自己做 —— 值得做，因为一个 400 节点的反例几乎没法调试，一个 5 节点的反例一眼就看明白了。）

### 6.5 相关性失效：它证明的是"一致"，不是"正确"

这是差分测试的根本局限，必须说清楚，否则它会变成一种虚假的安全感。

**差分测试验证的是两个实现彼此一致，而不是它们符合契约。** 如果两个实现共享了同一个错误的前提，它们会完美地一致，然后一起错。

本章工程里就有一个现成的例子。社交图推荐的契约规定：**只有共同好友数 ≥ 1 的人才有资格被推荐**。假设你把这条读漏了，写成"给所有人打分，排序取前 k"。那么：

- `recommend_baseline` 会把毫无关系的陌生人也推上来；
- 你照着同一个理解写的 `recommend_fast` 也会；
- **差分测试全绿**。

抓住这个的不是差分测试，而是另一条**非差分**的、直接对着契约写的测试：

```python
def test_no_mutual_friends_returns_empty(self):
    self.graph.add_user("loner")
    self.assertEqual(recommend_baseline(self.graph, "loner", k=5), [])
```

所以差分测试永远只是测试策略的**一层**，不是全部。一套完整的验证至少要有三层：

| 层 | 回答的问题 | 本章例子 |
|---|---|---|
| 契约测试（手写期望） | 我理解的规格对不对？ | `test_no_mutual_friends_returns_empty` |
| 不变量 / 变形测试 | 输出本身合不合法、关系对不对？ | `assert_valid_walk`、`optimize` 单调性 |
| 差分测试 | 优化后的实现和优化前一致吗？ | `test_same_answers_as_the_baseline` |

顺序也有讲究：**第一层必须由人写**，因为它是你对规格的理解的唯一载体，没有任何自动化手段能替你产生它。第二、三层可以大量借助 AI 生成 —— 而且效果很好，因为它们的正确性有客观标准。

> **一个务实的分工**：把"读懂规格、写第一层测试"留给自己；把"照着不变量批量生成用例、写生成器、写差分脚手架"交给模型。这大概是我目前见过投入产出比最高的一种人机分工。

### 6.6 没有裁判的时候：不变量校验

Phase 2 的处境是最尴尬的：你在写**第一个**实现，没有慢版可以对比。

这时候的替代品是**不变量校验** —— 不检查"输出等于什么"，而检查"输出必须满足什么"。迷宫题里的路径校验器是个好模板：

```python
def assert_valid_walk(self, maze, path, require_all_keys=False):
    self.assertEqual(path[0], maze.start)          # 起点对
    self.assertEqual(path[-1], maze.end)           # 终点对
    mask = 0
    for i, cell in enumerate(path):
        self.assertFalse(maze.is_wall(cell))       # 不穿墙
        char = maze.at(cell)
        if char in GATES:                          # 过门时必须已持钥匙
            self.assertTrue(mask & (1 << key_bit(char)))
        if char in KEYS:
            mask |= 1 << key_bit(char)
        if i:                                      # 每一步必须相邻
            prev = path[i - 1]
            self.assertEqual(abs(prev.row - cell.row) + abs(prev.col - cell.col), 1)
    if require_all_keys:
        self.assertEqual(mask, maze.all_keys_mask)
```

它有一个硬编码期望值永远比不上的优点：**换算法之后它一行都不用改**。

这不是小事。迷宫题从 Q2 走到 Q5，算法换了三次（BFS → bitmask BFS → Dijkstra），路径的具体走法每次都变。如果测试里硬写着"正确路径应该是 `[(1,1), (2,1), (3,1), ...]`"，那么每换一次算法就要重写一遍测试 —— 而**重写测试来迁就新实现，正是最危险的动作**：你已经没有独立的判据了，你只是在把新实现的行为誊写成期望值。

Q5 加进能量之后，校验器扩了一个版本 `assert_valid_blast_walk`，多校验三件事：炸的必须是可炸的内部墙（不能炸外框）、用掉的炸弹数不超预算、**报告的能量必须等于沿路重新累加出来的能量**。最后这条是自洽性检查 —— 它不需要知道最优解是多少，只需要确认"你报的数和你走的路对得上"。

> **一个通用配方**：任何"返回一条路径 / 一个方案 / 一份计划"的函数，都应该配一个校验器，检查这条路径**本身**合法。最优性可以另外验（差分或变形），但合法性必须无条件成立。这两件事分开验，测试就不会在换算法时全线报废。

### 6.7 从单元测试走到生产

差分测试在生产环境里有个更响亮的名字：**影子流量**（shadow traffic）。新老实现并行跑同一份真实请求，只对比结果，不对外输出新实现的响应。

结构完全一样，只是三件事变了：

| | 单元测试版 | 生产版（影子流量） |
|---|---|---|
| 输入从哪来 | 生成器 + 手写用例 | **真实流量**（自动解决 §6.4 的分布问题） |
| 不一致怎么办 | 测试红，阻断合并 | 记录采样、告警，**不阻断请求** |
| 主要成本 | 几乎没有 | 双倍计算 + 采样存储 |

影子流量最大的价值恰恰是补上 §6.4 那个洞：**真实流量天然带着你生成器造不出来的形状**。那个八千好友的名人，你在测试里得手写；在生产里他自己就来了。

中间还有一档常被忽略的形态 —— **录制回放**：把线上一段真实输入录下来，作为固定的测试数据集反复用。它的成本远低于影子流量，却能拿到真实分布的大部分好处，特别适合数据密集、请求可序列化的系统。

顺带一提，在编译器 / 图像处理 / 信号处理这类**输入可枚举、输出可逐位比较**的领域，差分测试的威力是最大的：整个 pass pipeline 可以对着一个未优化的解释器逐条对拍，覆盖率能做到很高。本章那道编译器优化题之所以适合当例子，就是因为它天然属于这一类。

### 6.8 一张可执行的清单

当你（或模型）要写一个新实现，按顺序过一遍：

1. **有没有一个慢而显然正确的版本？** 有就留着；没有就先写一个 —— 写它的时间会在后面全部赚回来。
2. **新实现是旧实现的严格推广吗？** 是的话，第一条测试写退化自检（§6.2 形态二），它最便宜也最早否证。
3. **契约里的形容词能翻成关系吗？**（最短的、排序的、去重的、幂等的、单调的）能翻的都写成变形测试。
4. **随机生成器覆盖了什么形状，漏了什么？** 把答案写成注释放在生成器旁边，漏掉的部分手写用例补上。
5. **种子写死了吗？失败信息里带种子了吗？**
6. **有没有至少一条非差分的、直接对着契约写的测试？** 没有的话，你只验证了一致性，没验证正确性（§6.5）。
7. **返回"方案 / 路径 / 计划"的函数，有没有配一个合法性校验器？** 有的话，换算法时测试不会全线报废。
8. **这套东西能不能升级成影子流量或录制回放？** 数据密集型系统通常值得。

## 七、失效模式目录

把前面的诊断压缩成一张可以贴在显示器上的表。

| 失效模式 | 表现 | 为什么会发生 | 对策 |
|---|---|---|---|
| **上下文缺口** | 生成的代码自洽但违反不变量（如 §3.1 永远为假的分支） | 不变量不在代码里 | 把契约写进类型；对每个分支问"什么输入会触发它" |
| **上游污染** | 你在调试一个正确的模块（§3.2） | 错误的基准让 AI 帮你朝错误方向收敛 | 先验证数据通路，再验证逻辑 |
| **单位错配** | 时长当时刻、行当列（§3.3） | 类型系统对单位无知 | `NewType` / 强类型包装；非对称样例（3×7 而不是 5×5） |
| **越界修改** | 公共接口被顺手改了 | 模型没有"不归我管"的概念 | Prompt 里的 Do-NOT 清单；每阶段 commit |
| **算法误选** | 结果不是"慢"而是"错"（§3.4 BFS vs Dijkstra） | 代价模型是需求，不在代码里 | 换算法前先口述"为什么旧的不再正确" |
| **训练分布偏差** | 冷门语言/领域的致命陷阱被滑过（§3.6） | 模型警觉的是"讨论得多的坑" | 把你领域的坑写进约束；上 sanitizer / 静态分析 |
| **过度优化** | 引入了在你的数据上更慢的结构（§3.7） | 模型有知识没数据分布 | 强制回答"什么输入让它变成负优化" |
| **过早优化** | Phase 2 就写了 Phase 4 的解法 | 模型默认给"最好的"实现 | Prompt 显式写 "scanning is fine at this stage" |
| **熵增** | 多余的深拷贝、防御性 try、用不上的参数 | 模型倾向于添加 | 逐行 review diff，主动删 |
| **虚假绿灯** | "已修复"但你没跑测试 | 模型对自身正确性没有可靠自评 | 永远自己跑；差分测试（§6.2） |
| **相关性失效** | 快版和慢版完美一致，但一起错 | 两个实现共享了同一个错误前提 | 至少留一条非差分的契约测试（§6.5） |
| **生成器盲区** | 差分测试全绿，线上照样炸 | 随机生成器到不了病态形状（实测最大度数 13 vs 真实 8000） | 随机管广度、手写管形状；升级到影子流量（§6.4、§6.7） |

## 八、从面试回到工程

这一章借了一个面试格式当解剖台，但真正的结论跟面试没关系。把上面的东西平移到日常工作，我认为有四条最直接：

**1. 你的代码库需要为"机器读者"重写一部分文档。**
过去写注释是为了帮后来的人理解意图；现在注释和 docstring 会被当作 prompt 的一部分。这带来两个变化：漂移的注释危害翻倍（它现在会主动误导你的生成器），而**能被机器验证的契约**（类型、断言、property test）的价值远高于自然语言描述。§3.3 和 §3.5 那个"注释写 84、代码是 13"的例子就是这个变化的缩影。

**2. 测试从"防止回归"升级成"定义系统"。**
在 Meta 那一轮里，测试文件**就是**题面——没有别的规格说明。这个设计不是偷懒，它准确反映了 AI 协作下的真实状态：你能可靠地传达给模型的东西，只有可执行的东西。团队里那份"大家都知道但没人写下来"的约定，在 AI 时代是纯粹的负债。

**3. 评审的重心从"这样写好不好"移到"这样写对不对，以及它在什么输入下会崩"。**
风格问题正在被工具吃掉（formatter、linter、模型本身）。评审者剩下的高价值动作是 §3.7 那一类：这个优化的失效边界在哪、这个分支什么时候会触发、这个数据结构在我们真实的数据分布上表现如何。

**4. 回滚成本决定了你敢用多大的生成粒度。**
频繁 commit、小步提交、feature flag、影子流量——这些老实践在 AI 时代的收益率大幅上升。因为生成的边际成本趋近于零之后，**限制你迭代速度的不再是"生成多快"，而是"错了能多快退回去"**。

## 结语

Meta 那一轮面试真正在问的问题，不是"你会不会用 AI"。它在问：

> 当"把想法变成代码"这一步几乎免费之后，你还剩下什么？

这一章给出的答案是三样东西：**你知道契约在哪里**（因为你读得懂不变量，而不只是读得懂语法）；**你知道边界在哪里**（因为你能说清什么不该动、什么不该做）；**你知道判断在哪里**（因为你握着数据分布和代价模型，那是任何模型都没有的信息）。

这三样都不是"用 AI 的技巧"。它们是工程能力本身——只是过去被"写代码"这个昂贵的动作遮住了，现在那层遮蔽物被拿掉了而已。

好消息是：它们都可以练。本章配套的七个工程，每一个都是一次带计时器的练习。
