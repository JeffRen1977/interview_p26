# 场景 4：AI + 传统 ISP 混合 — RAW 域深度学习进 Pipeline

**典型题：** 如何把 Raw-domain 深度学习去噪 / 夜景超分集成进现有 Camera Pipeline？

**核心考点：** 前/后处理分流、实时预览 HW 快路径 vs 抓拍 NPU 慢路径并发、内存与算力 QoS 隔离。

传统 ISP 级序见 [`02-e2e-isp-pipeline.md`](./02-e2e-isp-pipeline.md) 与 [`camera/3A.md`](../../camera/3A.md)。

---

## 1. 需求与约束

| 维度 | 假设 |
|------|------|
| 预览 | 必须 **HW ISP 实时**，<30ms，不能等 NPU 夜景模型 |
| 抓拍 | 夜景 / 超分可 **100–800 ms** 甚至数秒（多帧），要有 UI 进度 |
| 模型 | RAW denoise 吃 **线性 Bayer**（BLC/LSC 后）；超分常在 RGB/YUV |
| 算力 | NPU 与 IFE/IPE/Encoder **抢 DDR 和电源轨** |
| 兼容 | 关掉 NPU 或模型加载失败时，HW ISP 仍能出 JPEG |

**开场金句：** AI 不是替换 ISP，是 **插在线性 RAW 上的可选 Node**。预览永远不走这条 Node；抓拍才分流。用 QoS 保证 tracking/预览不被夜景模型打死。

---

## 2. 高层架构

```
Sensor Bayer
    ▼
IFE：BLC → LSC → BPC → Stats（3A 仍在这里，实时）
    │
    ├──────────────────────────────┐
    ▼                              ▼
HW 快路径（每帧）              抓拍慢路径（用户快门）
IFE/IPE：demosaic 轻 NR        把「线性 RAW 环」里 N 帧
tone + scale → Preview         dma-buf 交给 NPU RAW denoise
Encoder ← 录像走快路径          → 融合 / 超分（GPU/NPU）
                               → CCM/Gamma 可用 HW IPE 收尾
                               → JPEG
```

关键：**3A 不依赖 NPU 输出。** 否则预览 AE 会等夜景网络，系统锁死。

---

## 3. 核心子系统

### 3.1 前处理 / 后处理分流

模型训练域必须和运行域一致。推荐切分：

| 阶段 | 放 HW ISP | 放 NPU | 原因 |
|------|-----------|--------|------|
| BLC / LSC / BPC | ✓ | | 标定表、线性、便宜 |
| Stats / 3A | ✓ | | 实时闭环 |
| RAW denoise / 拆马赛克联合网络 | | ✓ | 非线性、内容自适应 |
| Demosaic | 快路径 HW；慢路径可融合进网络 | 二选一，**不要 HW demosaic 完再喂 RAW 网络** |
| CCM / Gamma / Sharpen | 快路径 HW；慢路径可 HW 收尾 | 保持品牌色 |

错误切分：

- 先 tonemap 成 8-bit 再“AI 去噪”→ 高光信息没了。  
- 预览也进 NPU RAW 网 → 延迟和功耗双死。  
- 超分放在 Bayer 上但训练用 sRGB → 色偏。

夜景超分更常见：**N 帧 RAW align（gyro + 光流）→ 融合网络 → 一次 demosaic/tonemap**。对齐在 DSP/GPU，卷积在 NPU。

### 3.2 双路径并发调度

HAL3 上这是两条 **stream / usecase**，不是 if 像素：

```
Session 配置：
  Stream A: 1080p YUV preview     → IPE 快路径
  Stream B: 1080p NV12 video      → IPE + VPU
  Stream C: FULL RAW private      → 环形 ZSL（仅 metadata + RAW fd）
快门：
  从 RAW 环取 M 帧 → 提交 CaptureRequest(still)
  快路径继续跑，预览不准停
  AI Node 异步；完成后再 processCaptureResult(JPEG)
```

调度器规则：

1. **预览 Request 优先级 > 抓拍 AI。** IFE 写 RAW 环用独立 DMA 客户端，不被 NPU 堵住 QBUF。  
2. AI 任务队列深度 1：连按快门则合并或丢旧的（产品定）。  
3. 录像中夜景抓拍：限 NPU 带宽，或只做单帧 HW snapshot。  
4. 模型未加载（冷启动）：still 回退纯 HW BPS，Result 带 vendor tag `ai_bypass=1`。

时间线：

```
t=0     快门
t=0–30ms  预览照常；UI 快门动画
t=0–50ms  选帧、对齐
t=50–400ms NPU infer
t=400ms+  IPE 收尾 + JPEG
预览全程 30fps 不中断
```

### 3.3 内存与算力隔离（QoS）

NPU 跑 12MP RAW 卷积会打满 DDR。不隔离就会：预览掉帧、tracking 丢、encoder 花屏。

| 机制 | 用法 |
|------|------|
| **独立 analysis/RAW 缓冲池** | 与 preview YUV 池分开，避免 HAL buffer 饿死 |
| **缩小网络输入** | 12MP → 在 Bayer 上 2×2 bin 再进网络，输出再引导融合 |
| **NPU DVFS cap** | 预览掉帧时压 NPU 频率，而不是压 IFE |
| **带宽 QoS / 业务优先级** | SoC 若有 camera traffic class：IFE/VPU > GPU > NPU still |
| **DDR 忙则延期 AI** | 热路径只设 flag，下一帧再跑 |

Zero-copy：NPU 直接 import IFE 的 RAW dma-buf（需 **cache/SMMU 属性** 与 ISP 写出一致）。若网络要 planar 16-bit，在 **IFE 或小 DSP 做 unpack**，仍避免 CPU。

功耗：夜景是 burst，允许短时超 2W，但必须能被眼镜热状态机 **T2 直接取消 NPU**（见 [`03-smart-glasses-power-thermal.md`](./03-smart-glasses-power-thermal.md)）。

## 4. 性能优化与边界

| 问题 | 处理 |
|------|------|
| 鬼影 | 对齐失败则少融合帧或回退单帧 HW |
| 闪烁 | 多帧 AE 变化 → 只融曝光相近帧；或先对齐曝光 |
| 掉帧恢复 | NPU hang watchdog 100ms → kill infer、HW JPEG、上报 |
| Tiling | 超分按 tile，重叠 halo，降低 peak 内存 |
| 版本 | 模型文件与 ISP IQ 绑定；OTA 同包，避免“新模型 + 旧 BLC” |

调试：预览正常、JPEG 差 → 查训练域 vs BLC；JPEG 好、预览差 → 别怪 NPU，查快路径 IQ。

## 5. 跨团队落地

| 团队 | 契约 |
|------|------|
| 算法 | 输入张量 layout（packed RAW10 vs 16-bit）、黑电平是否已减、Bayer pattern、色温作为 side feature |
| IQ | 快路径与 AI 收尾 CCM 必须同一套，否则预览/成片色不一致 |
| 驱动 | RAW 环深度、fd 生命周期、NPU 与 IFE 并发的 SMMU 上下文 |
| 系统 | QoS 表、热取消 AI 的 API |
| 产品 | 夜景等待文案；失败回退是否对用户可见 |
| 评测 | 预览 FPS、抓拍 PSNR/SSIM、DDR 占用、皮肤温；**不能只报网络 PSNR** |

标定：LSC/BLC 仍归 ISP；网络不要学镜头阴影，否则换模组必坏。产线只出传统 OTP + 通用模型；SKU 特化用微调包。

**收口金句：** 混合架构的成功标准是 **预览帧率在 AI 抓拍时不掉、3A 不依赖 NPU、NPU 挂了还能出片**。画质增益是附加条件，不是系统正确性本身。

## 6. 数字预算：为什么"12MP 上跑网络"是不可能的

### 6.1 激活值内存——这是第一堵墙，而且大多数人算不出来

一个在**全分辨率**上跑的 U-Net，第一层 32 通道，输入 12MP：


$$
12\times10^6 \times 32 \times 1\ \mathrm{byte\ (INT8)} = 384\ \mathrm{MB}
$$

**一层的激活值就是 384 MB。** NPU 的片上 SRAM 通常是 **2–8 MB**。这意味着每一层的中间结果都要完整写回 DDR 再读出来。

DDR 流量估算（假设网络 20 层，平均通道数 32，每层写一次读一次）：


$$
20 \times 384\ \mathrm{MB} \times 2 = 15.4\ \mathrm{GB}
$$

这是**单张照片**的 DDR 流量。

按 1 GB/s 的可用带宽算就是 **15 秒**。**这个方案在物理上不成立**，不需要任何 benchmark 就能否定它。

> **说出这个数字，比说"要注意内存"强十倍。** E6 的标志是：用一次心算就把一个看似合理的方案证伪。

### 6.2 三条可行的路，以及它们各自的代价

| 方案 | 内存 | 代价 | 什么时候选 |
|------|------|------|-----------|
| **① 降分辨率跑网络 + 引导上采样** | 1/4 分辨率 → 96 MB/层 | 高频细节靠传统 ISP 或引导滤波恢复，网络只出"低频修正"（例如去噪的残差、局部曝光图） | **默认选择**。大部分 RAW denoise / 夜景增强都这么做 |
| **② Tiling + halo** | tile 512×512×32 = 8 MB/层，能进 SRAM | 边界要 halo 重叠（感受野半径），重叠区重复计算；tile 之间要保证无接缝（BN 统计量、padding 要一致） | 需要全分辨率输出的任务（超分） |
| **③ 先 2×2 binning 到 3MP** | 96 MB/层 | 直接丢分辨率，但对**去噪**任务其实是合理的（噪声本来就是高频） | 输出本身不需要全分辨率时 |

**Tiling 的隐藏成本要说出来：** 感受野半径 $R$ 的网络，tile 边长 $S$，重叠开销 $\approx (1 + 2R/S)^2 - 1$。$R=32$、$S=256$ 时是 **56% 的额外计算**。所以 tile 不能太小，而 tile 大小又受 SRAM 限制——**这是一个可以在白板上写出来的优化问题**。

### 6.3 算力与延迟


$$
t_{\mathrm{ideal}} = \frac{\mathrm{FLOPs}}{\mathrm{TOPS}},\qquad
t_{\mathrm{real}} = \frac{t_{\mathrm{ideal}}}{\eta}
$$

其中 $\eta$ 是 NPU 利用率。

一个 3MP 输入、20 层、平均 32 通道、3×3 卷积的网络：


$$
\text{FLOPs} \approx 3\times10^6 \times 20 \times 32 \times 32 \times 9 \times 2 \approx 1.1\ \mathrm{TFLOP}
$$

10 TOPS 的 NPU，**理论 110 ms**。但实际利用率在这类 memory-bound 的图像网络上通常只有 **20–40%**（因为激活值进出 DDR，算力吃不满），所以：


$$
t_{\mathrm{real}} \approx 110 / 0.3 \approx \mathbf{370\ ms}
$$

**这落在"抓拍慢路径 100–800 ms"的预算内，但没有余量。** 结论：
- 连按快门必须合并或丢弃（队列深度 1）
- 录像中不能跑这个网络
- 要给 UI 一个明确的进度反馈

> **E6 的补充判断：** "这类网络是 **memory-bound 而非 compute-bound**。所以换一颗 TOPS 翻倍的 NPU **不会让它快一倍**——真正的杠杆是减少激活值的 DDR 往返（融合算子、降通道数、量化到 INT8 甚至 INT4）。**如果有人拿'我们升级到 20 TOPS'来解决这个问题，我会要求先看 roofline 分析。**"

### 6.4 功耗与热的耦合

NPU burst 在 0.5–2 W。眼镜上（见 [`03-smart-glasses-power-thermal.md`](./03-smart-glasses-power-thermal.md)）稳态上限只有 0.4–0.9 W。

370 ms 的 burst，能量 $= 1.5 \times 0.37 = 0.55$ J。热时间常数是分钟级，所以**单次夜景抓拍完全不影响温度**。但：

- **连拍 10 张夜景** = 5.5 J + 3.7 秒的 1.5W → 开始有影响
- **录像中抓拍** = NPU 叠加在已经接近热墙的录像负载上 → **必须禁止或降级为纯 HW 单帧**

> 所以热状态机要有一个 **`ai_allowed` 标志**，T2 以上直接置否。这不是 AI 模块自己决定的，是热 governor 的下游执行（呼应 03 篇的中心化 governor 设计）。

### 6.5 量化：RAW 域为什么比 RGB 域难量化

RAW 是**线性的、高动态范围的**（10–14 bit，动态范围 60–84 dB）。直接 INT8 量化会把暗部全部压成 0——而**暗部恰恰是去噪最需要工作的地方**。

三个可行做法：

| 做法 | 说明 |
|------|------|
| **对数 / PWL 域量化** | 先做非线性压缩（类似 companding）再量化，暗部得到更多量化级 |
| **Per-tile 动态缩放** | 每个 tile 按自己的亮度范围缩放，scale 作为 side info 传递 |
| **混合精度** | 首尾层用 FP16 保精度，中间层 INT8 |

**量化必须在训练时就模拟（QAT）**，不能训练完再 PTQ——PTQ 在这种高动态范围输入上通常掉点严重。

> 这一段能说出来，就说明你真的做过端侧模型部署，而不是只读过架构图。

## 7. 关键决策与被否方案

| 决策 | 我选 | 否掉的 | 为什么 | 什么会让我翻盘 |
|------|------|--------|--------|----------------|
| 网络插入点 | **BLC/LSC/BPC 之后的线性 Bayer** | demosaic 之后的 RGB | 噪声在 RAW 域是（近似）独立的；demosaic 会把噪声空间相关化，去噪难度大增。且 CFA 的相位信息在 RGB 域丢失了 | 网络任务本身是 RGB 域的（例如风格化、局部色彩调整） |
| 是否让网络接管 demosaic | **慢路径可以联合做（joint demosaic+denoise）；快路径绝不** | 全部走网络 | 联合网络在慢路径上质量更好；但预览必须有确定性延迟 | 无。预览走网络是架构性错误 |
| 3A 的输入 | **永远来自 IFE 硬件 stats** | 从网络输出算 | 3A 依赖 NPU = 预览 AE 要等网络 = 系统死锁 | 无。这是硬约束 |
| 分辨率策略 | **1/4 分辨率跑网络 + 引导上采样** | 全分辨率 tiling | §6.1 的内存墙；且引导上采样在去噪任务上质量损失很小 | 任务是超分（必须出全分辨率细节），此时上 tiling |
| 失败回退 | **模型缺失/超时 → 纯 HW BPS 出片，result 带 `ai_bypass=1`** | 报错给用户 | 用户按了快门就必须拿到照片；画质差好过没有 | 无 |
| 多帧对齐放哪 | **DSP / GPU（光流 + gyro 先验）**，不放 NPU | 端到端网络做对齐 | 对齐是几何问题，传统方法更可控、更省算力，且失败可检测（残差） | 有专门的对齐加速器，或端到端方案在评测上明确胜出 |
| 模型与 IQ 的绑定 | **模型文件 + IQ 包 + ISP FW 三者同包 OTA** | 模型独立更新 | 模型学的是"BLC/LSC 之后的特定数据分布"，换了标定或 FW 分布就变了 | 模型对输入分布做了显式归一化且验证过鲁棒性 |

**关于"网络会不会学到镜头阴影"，这是一个值得主动提的陷阱：**

> "如果训练数据没有做 LSC，网络会把暗角当成场景的一部分学进去。换一个模组（LSC 不同）就会失效。所以 **LSC/BLC 必须在网络之前由 ISP 做完，且训练数据必须用同样的流程生成**。产线只出传统 OTP 标定，模型是通用的——这个分工要写死在契约里。"

## 8. 失效模式与降级

| 失效 | 检测 | 恢复 | 用户可见 |
|------|------|------|----------|
| **NPU hang** | watchdog（例如 2× 预期延迟） | kill inference、走 HW BPS 出片、上报 | 照片正常，画质是 HW 水平 |
| **模型加载失败**（文件损坏 / 版本不匹配） | 启动时校验 hash + 版本戳 | 拒绝加载，`ai_bypass=1` | 无（画质差异，不报错） |
| **多帧对齐失败**（大运动、场景变化） | 对齐残差超阈值 | 减少融合帧数；极端情况退化为单帧 | 噪点略多 |
| **鬼影**（运动物体） | 对齐后的帧间差异图 | 运动区域只用参考帧（局部融合掩码） | 无 |
| **多帧曝光不一致导致闪烁** | 帧间 AE 参数差异 | 只融合曝光相近的帧；或先做光度对齐 | 无 |
| **NPU 抢带宽导致预览掉帧** | 预览帧率监控 | **压 NPU 的 DVFS，而不是压 IFE**；或延后 AI 到下一帧 | 无（这是设计目标） |
| **热限制** | thermal governor 的 `ai_allowed` | 直接跳过 AI 路径 | 夜景效果降级 |
| **生成式伪影**（超分"编造"出不存在的细节，例如把模糊文字补成错误的字） | 需要专门的语料审计，运行时难检测 | **产品层面限制超分倍率**；对文字/人脸区域降低网络强度 | 潜在的信任问题 |

**最后一行值得单独展开，这是 E6 应该主动提出的风险：**

> "超分和生成式增强有一个**非画质的风险**：网络可能产生看起来合理但实际错误的内容——把模糊的车牌补成一个不同的号码，把远处的人脸补成不同的人。这在消费产品上是**信任问题**，在某些场景下甚至是法律问题。
>
> 我的处理是三层：① 限制放大倍率（2× 而不是 4×）；② 对文字和人脸区域用更保守的处理强度；③ 在 metadata 里标注这张图经过了生成式增强。**第三条尤其重要——它让下游（包括用户和平台）知道这不是纯光学记录。**"

## 9. 怎么证明它是对的

### 9.1 为什么 PSNR 不够（E6 必须说的话）

> "**我不会用 PSNR 作为发布门槛。** PSNR 奖励平滑，所以一个把细节全磨掉的网络能拿到很高的 PSNR，但看起来像塑料。而且 PSNR 完全看不到伪影——一个在 99% 的图上很好、在 1% 的图上产生诡异纹理的模型，平均 PSNR 依然漂亮。"

替代方案是一个**分层的评测体系**：

| 层 | 指标 | 作用 |
|----|------|------|
| **像素级** | PSNR / SSIM | 只用来防止**大幅退步**，不作为提升的证据 |
| **感知级** | LPIPS、DISTS | 与人眼相关性更好 |
| **纹理保留** | Dead Leaves 卡的 MTF | 专门抓"细节被磨掉" |
| **伪影审计** | **失败案例语料库** + 人工过一遍 | 抓 PSNR 看不到的东西 |
| **主观** | 盲测 A/B，固定显示设备，N ≥ 20 人 | 最终仲裁 |
| **系统级** | 预览 FPS、抓拍端到端延迟、DDR 峰值、皮肤温 | **画质增益不能以系统退化为代价** |

**最后一行是这道题的收口标准**：一个把画质提升 2 dB 但让预览掉到 25fps 的方案，是**不合格**的，不是"需要权衡"的。

### 9.2 失败案例语料库（必须专门建）

这类网络的失败是**长尾且内容相关**的，随机采样测不出来。必须主动收集：

- **文字**：路牌、书页、屏幕（超分最容易编造的地方）
- **人脸 / 皮肤**：肤色保真、毛孔纹理（磨皮 vs 保留）
- **规则纹理**：格子衬衫、砖墙、栅栏（容易产生摩尔纹和错误纹理）
- **点光源**：夜景霓虹、星点（容易被当噪声抹掉）
- **极端噪声**：高 ISO 全黑场景（模型可能产生色块）
- **运动**：多帧融合的鬼影重灾区
- **非自然内容**：屏幕拍摄、印刷品、艺术画作

**每次模型更新都要人工过一遍这个语料库。** 这是不能自动化的部分，也正因如此，它的价值最高。

### 9.3 A/B 与灰度

- **端上 A/B**：同一张 RAW 同时用新旧模型出两张图，本地对比（不上传图像，只上传标量指标）
- **灰度发布**：按 SKU + 用户群分批；监控**照片保存率**（用户拍完删掉的比例是最诚实的画质指标）和投诉关键词
- **kill switch**：模型可以被远程关闭并立刻回退到纯 HW，不需要等 OTA

### 9.4 Fleet SLI

| SLI | 阈值 |
|-----|------|
| AI 路径成功率（未 bypass 的比例） | > 95% |
| NPU 推理延迟 p95 | < 600 ms |
| AI 抓拍期间的预览掉帧数 | ≈ 0（这是硬指标） |
| `ai_bypass` 原因分布（超时/热/模型缺失/内存） | 监控趋势 |
| 照片保存率（vs 拍完即删） | 回归即告警 |
| 抓拍到出图的端到端延迟 p95 | < 1 s |

**"AI 抓拍期间的预览掉帧数 ≈ 0" 是这个系统的核心 SLI。** 它直接检验了 QoS 隔离是否真的生效。

## 10. 演进与组织

### 10.1 契约（这一篇的契约特别容易出事）

| 契约物 | Owner | 消费者 | 出事的方式 |
|--------|-------|--------|-----------|
| **输入张量规格**：layout（packed RAW10 vs u16 planar）、Bayer pattern、**黑电平是否已减**、是否已过 LSC、数值范围 | 你 | 算法 | "算法以为黑电平已减，实际没减"——模型在暗部完全失效，但亮部正常，很难被发现 |
| 色温 / gain / 曝光作为 side feature | 你 | 算法 | 训练时用了，推理时没传 → 分布偏移 |
| 模型文件格式 + 版本戳 + 兼容的 FW/IQ 版本 | 算法 | 你 | 三者版本错配 |
| NPU / SMMU 上下文与 dma-buf 的 cache 属性 | 驱动 | 你 | ISP 写出的 buffer NPU 读到脏数据 → 花屏或诡异输出 |
| Thermal governor 的 `ai_allowed` 接口 | 系统 | 你 | AI 无视热限制 |
| 评测语料库与指标定义 | 你 + IQ | 算法 | 算法优化 PSNR，产品要的是观感 |

**第一行是最经典的坑。** 我会把它做成**运行时可校验**：输入张量带一个描述头（pattern、black level、range、是否 LSC 后），推理前校验，不匹配就拒绝并上报——而不是靠文档和口头约定。

### 10.2 分阶段

| 阶段 | 出口标准 |
|------|----------|
| P0 | 离线跑通：PC 上用真实 RAW 跑通网络，确认训练域 = 部署域 |
| P1 | 端上跑通：NPU 上跑出正确结果（先不管速度），dma-buf 零拷贝打通 |
| P2 | 性能达标：延迟进预算；**QoS 隔离验证——AI 跑起来预览不掉帧** |
| P3 | 画质：评测体系建立、失败语料库建立、主观 A/B 通过 |
| P4 | 上线：bypass 路径全部验证、kill switch、版本绑定、fleet SLI |

**P2 的 QoS 验证要在 P3 之前。** 因为如果隔离做不到，画质再好也不能上——先证明它不会破坏系统，再证明它有用。这个顺序本身就是 E6 的判断。

### 10.3 一个组织层面的建议

> "AI-ISP 最大的组织风险是**算法团队和相机团队的评价标准不一致**：算法团队的 KPI 是 PSNR/数据集指标，相机团队的 KPI 是端到端体验。这会导致算法交付一个在 GPU 上很棒、在端侧不可用的模型。
>
> 我的做法是：**在项目一开始就让算法团队的评测跑在真实的端侧约束下**——给他们一个包含延迟、内存、DDR 流量预算的评测框架，模型在框架里不达标就不算完成。**把系统约束前移到算法的迭代循环里**，比事后拒收有效得多。"

**收口金句（E6 版）：** 混合架构的成功标准是**预览帧率在 AI 抓拍时不掉、3A 不依赖 NPU、NPU 挂了还能出片**——画质增益是附加条件，不是系统正确性。而真正决定这个项目成败的是两个更早的判断：**用一次心算否掉全分辨率方案**（激活值 384 MB/层），以及**把端侧约束前移进算法的迭代循环**（否则你会在集成期收到一个不可用的模型）。
