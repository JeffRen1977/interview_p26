# 场景 7：多客户端相机仲裁与隐私

**典型题：** 眼镜/头显上同时有系统 tracking、AI 助手、用户拍照、第三方 app，设计相机资源的仲裁与隐私保护。

**核心考点：** 资源仲裁策略、硬件强制的隐私指示、数据分级与最小化、崩溃后的资源回收、可审计性。

**为什么这题会出现：** 这是 Ray-Ban Meta 这类产品**最真实的系统难题**，也是唯一一道**技术答案不足以通过**的题——它需要你同时给出工程方案和信任模型。很多候选人会把它答成一道纯资源调度题，那就丢掉了一半分数。

---

## 1. 需求与约束

| 维度 | 默认假设 |
|------|----------|
| 客户端 | 系统 tracking（常驻）、系统 AI 助手、用户主动拍照/录像、第三方 app、远程协助/直播 |
| Sensor | 眼镜：1 主摄（可能 + ULP）；头显：4–8 tracking + 2 passthrough + 彩色 |
| 冲突 | 同一 sensor 不能同时配置互斥的 mode（分辨率/帧率/曝光策略） |
| 延迟 | 用户主动拍照的抢占必须 < 200 ms 生效 |
| 隐私 | **相机开启必须有用户和旁人都能察觉的物理指示** |
| 可靠性 | 任一客户端崩溃不得导致相机资源永久泄漏 |
| 合规 | 录制指示、数据出境、生物识别数据、未成年人保护 |

**开场金句：** 这道题有两个正交的轴，必须分开答。**轴一是资源仲裁**——谁能用相机、冲突怎么解，这是工程问题。**轴二是信任**——用户和旁人怎么知道相机开着、数据去了哪，这不是工程问题，是产品和法律问题，工程的角色是**让承诺在硬件上成立**而不是靠软件自觉。我会先把轴一讲完，然后重点讲轴二，因为轴二是这类产品真正的风险。

---

## 2. 高层架构

```
        ┌─────────────────────────────────────────────┐
        │   Camera Policy Service（单一权威）            │
        │   ├─ 客户端注册与权限校验                       │
        │   ├─ 仲裁策略（优先级 + 兼容性矩阵）             │
        │   ├─ 与热 governor / 电源策略联动                │
        │   └─ 审计日志（不含像素）                        │
        └───────────────┬─────────────────────────────┘
                        │ 授权 / 撤销
        ┌───────────────┴─────────────────────────────┐
        ▼                                             ▼
  [系统客户端]                                  [应用客户端]
  tracking（常驻，最高优先级）                    第三方 app（沙箱）
  AI 助手（后台，可被抢占）                       用户拍照（前台，可抢占后台）
        │                                             │
        └──────────────┬──────────────────────────────┘
                       ▼
              Camera Service / HAL
                       │  配置合法性检查（stream 组合矩阵）
                       ▼
              Sensor + ISP（物理资源）
                       │
                       ▼
        ┌──────────────┴──────────────┐
        │  **隐私指示灯（硬件强制）**    │
        │  与相机电源域绑定，软件不可关   │
        └─────────────────────────────┘
```

**关键设计：** 仲裁不在 Camera Service 里做（它太底层，不懂产品语义），而在一个**独立的 Policy Service** 里做。Camera Service 只负责执行和物理合法性检查。

> 这个分层的价值：**策略是会变的**（新产品需求、新法规、新客户端类型），而 HAL 和驱动是不该跟着变的。把策略隔离出来，它可以独立迭代、独立测试、独立审计。

## 3. 核心子系统

### 3.1 仲裁策略：优先级 + 兼容性，两者都要

**只有优先级是不够的。** 两个客户端可能优先级不同但**可以共存**（共享一条流），也可能优先级接近但**物理互斥**。

**兼容性矩阵（要在白板上画）：**

| 组合 | 可否共存 | 怎么做 |
|------|---------|--------|
| tracking + 用户拍照 | **可以**（不同 sensor） | 各自独立，无冲突 |
| AI 助手（低分辨率分析流）+ 用户录像 | **可以**（同 sensor 不同 stream） | 一条 sensor 流，ISP 分出两路：录像 1080p + 分析 320×240 |
| AI 助手（需要 30fps）+ 用户拍照（需要全分辨率） | **部分**（需要 mode 切换） | 拍照瞬间抢占，AI 暂停 < 1 s |
| 第三方 app 预览 + 系统 AI 后台分析 | **策略决定** | 通常禁止：第三方 app 前台时系统不做后台分析（隐私 + 功耗） |
| 两个第三方 app 同时用相机 | **禁止** | 只有前台 app 能拿到相机 |
| 用户录像 + 远程直播 | **可以**（同一条编码流分发） | 一次编码多路分发，不要编两次 |

**判定顺序（这是算法）：**

```
1. 权限检查    → 没权限直接拒绝
2. 兼容性检查  → 能共存？直接授权
3. 优先级仲裁  → 不能共存时，高优先级抢占
4. 抢占执行    → 通知被抢占方（给它机会保存状态），超时则强制回收
5. 恢复        → 抢占者释放后，按等待队列恢复
```

**优先级不是一个静态数字，而是上下文相关的：**

| 客户端 | 基础优先级 | 上下文提升 |
|--------|-----------|-----------|
| 系统 tracking | 最高（不可抢占） | — |
| 用户主动操作（按快门） | 高 | 用户显式意图永远高于后台 |
| 前台 app | 中 | 切到后台立即降级 |
| 系统 AI 后台 | 低 | 用户主动唤醒时提升 |
| 后台上传/分析 | 最低 | 充电+入盒时提升 |

> **要说出的原则：** "**用户的显式意图（按了快门）永远压过任何后台任务。** 这不是性能优化，是产品契约——用户按下快门却因为后台 AI 占着相机而拍不到，是不可接受的失败。所以抢占路径必须有 < 200 ms 的硬指标，而且要有测试专门守它。"

### 3.2 崩溃与资源泄漏：相机"卡住"是最常见的用户投诉

**问题：** 客户端进程崩溃、被 OOM kill、或者忘记 `close()`，相机资源不释放 → 后续任何人都打不开相机 → 用户只能重启设备。

**分层防御：**

| 层 | 机制 |
|----|------|
| **进程生命周期绑定** | Policy Service 监听客户端进程的死亡通知（binder death recipient / cgroup 事件），进程死 → 立即回收授权 |
| **租约（lease）机制** | 授权带 TTL，客户端必须周期性续租；不续租则自动回收。**这是防"进程活着但卡死"的关键**——死亡通知抓不到这种情况 |
| **Buffer 引用计数** | 见 [`../code/frame_pool.md`](../code/frame_pool.md)：buffer 归还靠引用计数，客户端死亡时其引用被强制释放 |
| **HAL 层看门狗** | HAL 内部的操作超时（configureStreams、processCaptureRequest）都有超时，超时则 abort 而非无限等待 |
| **最后手段：服务重启** | Camera Service 自身可重启并重新初始化硬件，代价是所有客户端断开（但比重启设备好） |

> **租约机制值得强调：** "进程死亡通知只能抓到进程**没了**的情况。更常见的故障是**进程还在但卡死了**（死锁、无限等待）——这时候死亡通知不会来，相机会被永久占用。租约是唯一能覆盖这种情况的机制。我会把租约做成默认机制，而不是可选的健壮性增强。"

### 3.3 隐私指示：为什么必须是硬件

**威胁模型（要明确说出来）：**

| 威胁 | 软件 LED 能防吗 | 硬件绑定能防吗 |
|------|----------------|---------------|
| 应用忘记点灯（bug） | ❌ | ✅ |
| 恶意应用故意不点灯 | ❌（如果它有权限） | ✅ |
| 系统被攻破（root / 供应链） | ❌ | ✅ |
| 用户物理遮挡 LED（贴胶带） | — | 需要额外的遮挡检测 |

**设计：**

```
相机电源域 / MIPI streamon 信号 ──┬──► Sensor 上电
                                  └──► LED 驱动（硬件与门，不经过 SoC 软件）
```

**关键性质：** LED 的点亮不是"软件决定的一个动作"，而是"相机通电的物理副作用"。软件**无法**在相机工作时关掉它。

**要主动讨论的几个细节：**

1. **遮挡检测**：用户贴胶带遮住 LED 怎么办？可以做光反馈检测（光电二极管测 LED 实际亮度），检测到遮挡则**拒绝开启相机**。这是产品决策：要不要把"能被遮挡"当成攻击面。
2. **ULP always-on 传感器要不要点灯？** 这是一个真实的困难问题。如果 ULP sensor 只做"有没有运动"的判断、不输出图像、不存储、不上传——它算不算"相机在录制"？**我的立场：只要有光进入感光元件就应该有指示**，因为向旁人解释"这个传感器不算相机"是行不通的。但这需要产品和法务定，工程要做的是**把两种方案的成本都算清楚**。
3. **指示的可见性**：LED 要让**旁人**看见，不只是用户。位置、亮度、颜色都要经过实测（不同环境光下的可见距离）。
4. **音频提示**：某些法域要求录制有声音提示（例如日韩的拍照快门音强制）。

### 3.4 数据分级与最小化

**核心原则：每一条数据流都要能回答"谁能看到、存多久、去哪里"。**

| 数据 | 谁能访问 | 存储 | 出设备 |
|------|---------|------|--------|
| **Tracking 相机像素** | 只有系统 tracking 进程 | 不落盘 | **绝不** |
| Tracking 输出（pose、特征点） | 系统 + 授权 app | 内存 | 匿名化后可选 |
| **眼动图像** | 只有眼动进程 | 不落盘 | **绝不**（见 [`05-eye-face-tracking.md`](./05-eye-face-tracking.md)） |
| 眼动输出（注视向量） | 系统渲染 + 显式授权的 app | 不持久化 | 需明确同意（可推断注意力/认知状态） |
| AI 助手的分析流 | AI 进程 | 不落盘 | 看具体功能：本地推理不出；云端推理需明确同意 + 脱敏 |
| 用户主动拍摄的照片/视频 | 用户 + 授权 app | 落盘 | 用户主动分享 |
| 相机遥测 | 系统 | 聚合 | 只有标量，**绝不含像素** |

**分级的工程落实：**

- **不同数据流用不同的 buffer 池和不同的进程**，靠进程隔离而不是代码约定
- Tracking 和眼动的像素 buffer **不通过通用的 Gralloc 路径**，避免被其他进程 import
- **调试通道是最大的泄漏风险**：量产固件必须编译掉图像 dump 路径，或者要求硬件级的解锁（fastboot unlock 会擦除用户数据）

> **要说的一句：** "隐私最常见的泄漏不是被攻破，是**调试功能忘了关**。所以我不依赖'记得在发布前关掉'——我要求敏感路径的 dump 能力在量产构建里**编译不进去**，并且有自动化检查在 CI 里守着。"

### 3.5 可审计性

**要求：** 相机什么时候被谁开启过，要有不可否认的记录；**但日志本身不能泄露隐私**。

```
审计日志条目 = {时间戳, 客户端标识, 授权时长, 分辨率/帧率, 目的分类, 是否有网络出口}
不含：像素、缩略图、位置（除非用户开启）、场景内容
```

**用户可见的呈现：** 一个"最近相机使用记录"界面，让用户能看到哪个 app 什么时候用了相机多久。这是 iOS/Android 已经在做的，眼镜上更重要（因为相机是常驻的）。

## 4. 性能优化与边界

| 问题 | 策略 |
|------|------|
| **抢占延迟** | 抢占路径要避免完整的 `configureStreams` 重配。做法：预先配置好一个"抢占用"的 stream 组合，抢占时切换而不是重建 |
| **共享流的分发** | 一条 sensor 流 → ISP 输出多个分辨率（主流 + 分析流），各消费者 import 各自的 dma-buf，不做 CPU 拷贝 |
| **优先级反转** | 低优先级客户端持有 buffer 不还，阻塞高优先级 → buffer 有超时强制回收；池按客户端配额隔离 |
| **通知与优雅退出** | 被抢占方收到通知后有 100 ms 保存状态，超时强制回收。**不要无限等待"礼貌"** |
| **热与电源联动** | 热 governor 可以否决新的相机授权（见 [`03-smart-glasses-power-thermal.md`](./03-smart-glasses-power-thermal.md)）；Policy Service 要把热状态纳入决策 |

## 6. 数字预算

### 6.1 抢占延迟的分解

用户按快门到第一帧可用，在"AI 后台正在占用相机"的情况下：

```
① 按键事件 → Policy Service                    5 ms
② 权限与仲裁决策                                1 ms
③ 通知 AI 客户端释放                            1 ms
④ AI 客户端优雅退出（保存状态）                  0–100 ms（有超时）
⑤ 停流 + 重配 stream 组合                       30–150 ms  ← 支配项
⑥ Sensor mode 切换（如果分辨率变了）             50–100 ms  ← 第二大项
⑦ 3A 重新收敛                                   100–300 ms ← 最大项！
────────────────────────────────────────────
合计                                            190–650 ms
```

**超标（目标 < 200 ms）。** 三个杠杆：

| 杠杆 | 省多少 | 做法 |
|------|--------|------|
| **① 预配置抢占 stream** | ⑤ 的 30–150 ms → ~10 ms | 常驻一套"拍照用"的 stream 配置，抢占时切换而不重建 |
| **② 避免 sensor mode 切换** | ⑥ 全省 | 让 AI 分析流跑在**与拍照同一个 sensor mode** 上（AI 用裁剪/缩放的子流），而不是自己配一个低分辨率 mode |
| **③ 3A 状态继承** | ⑦ 的大部分 | 抢占时**把 AI 流的 3A 收敛结果直接交给拍照流**——同一个 sensor、同一个场景，AE/AWB 是通用的 |

> **③ 是这道题最有价值的洞察：** "3A 收敛是抢占延迟里最大的一项，而它**完全不必要**——AI 流已经在看同一个场景了，它的 AE/AWB 是收敛的。我要做的不是加速 3A，是**让 3A 状态跨客户端继承**。这需要把 3A 的状态从'某个 session 的私有状态'提升为'sensor 级别的共享状态'，是一个架构决策而不是优化。"
>
> 优化后：$5 + 1 + 1 + 30 + 10 + 0 + 20 = \mathbf{67\ ms}$ ✓

**②的隐含设计：** 这条推论说明 **AI 分析流不应该自己选 sensor mode**，而应该复用主 mode 的裁剪流。代价是 AI 流的功耗略高（sensor 跑在高分辨率），收益是抢占几乎无延迟。**这个权衡要在架构阶段定，事后改不了。**

### 6.2 共享流的带宽收益

假设 AI 分析要 320×240@10fps，用户录像要 1080p@30fps。

| 方案 | Sensor | ISP 输出 | DDR |
|------|--------|---------|-----|
| **两个独立 session（不可行）** | 需要两个 mode，物理互斥 | — | — |
| **两条 ISP 流，各自 buffer** | 1 个 mode | 1080p + 320×240 | 93 + 2.3 = 95 MB/s |
| **一条 1080p 流，AI 自己降采样** | 1 个 mode | 1080p | 93 MB/s + AI 读 93 MB/s = 186 MB/s |

> **共享流（第二行）比"AI 自己降采样"（第三行）省 90 MB/s ≈ 9 mW。** 更重要的是省掉了 AI 侧的降采样算力。**让 ISP 硬件出多个分辨率是免费的，让软件降采样是要付钱的**——这是一个应该在架构里默认采用的模式。

### 6.3 隐私 LED 的功耗

一个可见的指示灯需要 1–5 mA @ 2V ≈ **2–10 mW**。

> 在眼镜 1.5 W 的预算里这是 0.5%，**完全不是砍它的理由**。主动说出这个数字，是因为总会有人在功耗评审上提出"LED 能不能只闪一下"——用数字直接否掉，比争论快。

## 7. 关键决策与被否方案

| 决策 | 我选 | 否掉的 | 为什么 | 什么会让我翻盘 |
|------|------|--------|--------|----------------|
| 仲裁位置 | **独立的 Policy Service** | 在 Camera Service / HAL 里做 | 策略会随产品和法规变，HAL 不该变；策略需要独立审计 | 系统实在轻量（RTOS 单进程），此时分层的开销大于收益 |
| 授权模型 | **租约（TTL + 续租）** | 只靠进程死亡通知 | 死亡通知抓不到"进程活着但卡死" | 无 |
| AI 流的 mode | **复用主 mode 的裁剪流** | AI 自己配低分辨率 mode | §6.1：避免抢占时的 mode 切换 | AI 需要长时间常驻且功耗压力极大，此时接受抢占慢一点 |
| 3A 状态 | **提升为 sensor 级共享状态** | 每个 session 私有 | §6.1：3A 收敛是抢占延迟的最大项 | 不同客户端需要完全不同的 3A 策略（例如 tracking 的固定曝光 vs 拍照的自动曝光）——此时要分别维护但仍可交叉初始化 |
| 隐私指示 | **硬件与电源域绑定** | 软件控制 | 威胁模型里软件不可信 | 无。产品红线 |
| ULP sensor 是否点灯 | **点**（建议） | 不点 | 无法向旁人解释"这个不算相机" | 产品与法务判断不同——但工程要把两案成本都给出来 |
| 遮挡检测 | **做**（光反馈） | 不做 | 否则 LED 保证形同虚设 | 成本/体积不允许，此时要在威胁模型文档里显式记录这个已知缺口 |
| 第三方 app 并发 | **只有前台一个** | 允许多个 | 隐私 + 功耗 + 用户无法理解谁在用 | 有明确的多 app 场景需求（例如直播 + 录制） |
| 调试 dump | **量产构建编译掉** | 运行时开关 | 运行时开关会被忘记关 / 被绕过 | 无 |

## 8. 失效模式与降级

| 失效 | 检测 | 恢复 | 用户可见 |
|------|------|------|----------|
| **客户端崩溃** | 进程死亡通知 | 立即回收授权和 buffer | 无 |
| **客户端卡死（进程活着）** | **租约超时** | 回收授权；下次它再请求时按新客户端处理 | 该 app 相机功能中断 |
| **Camera Service 崩溃** | 服务监控 | 重启服务 + 重新初始化硬件；所有客户端收到断开通知并可重连 | 短暂中断（比重启设备好） |
| **Buffer 泄漏（被客户端长期持有）** | 池的 in-use 高水位 + 每 buffer 的持有时长 | 超时强制回收；累犯客户端降级配额 | 该 app 掉帧 |
| **抢占超时（被抢占方不释放）** | 100 ms 超时 | 强制回收，不等待 | 被抢占方看到 error 而非优雅退出 |
| **隐私 LED 被遮挡** | 光反馈检测 | **拒绝开启相机** + 提示用户 | "指示灯被遮挡，无法使用相机" |
| **LED 驱动故障（不亮）** | 光反馈检测 | **拒绝开启相机**（fail-closed） | "相机不可用，请联系支持" |
| **热限制拒绝授权** | 热 governor | 拒绝低优先级请求；用户主动操作仍允许（短时 burst） | "设备过热，部分功能受限" |
| **权限被撤销（用户在设置里关闭）** | 权限变更事件 | 立即停流并回收 | app 收到通知 |
| **审计日志写入失败** | 写入错误 | **这是一个需要决策的场景**：是拒绝开相机（fail-closed，可审计性优先）还是允许（可用性优先）？ | 取决于决策 |

**fail-closed 原则（要说出来）：**

> "隐私相关的失效必须 **fail-closed**——LED 坏了就不让开相机，遮挡了就不让开相机。这和性能相关的失效（fail-open，降级但继续）方向相反。**把这两类失效混在一起处理是设计错误。** 我会在代码里把它们分成两个不同的错误类型，让处理路径不可能写错。"

最后一行的审计日志问题是一个好的开放讨论点——**E6 应该识别出这是一个需要和法务/产品共同决策的问题，而不是自己拍板。**

## 9. 怎么证明它是对的

### 9.1 仲裁的正确性验证

**状态爆炸问题：** N 个客户端 × M 种请求类型 × 各种时序 = 组合爆炸，人工测试覆盖不了。

**做法：**

| 方法 | 说明 |
|------|------|
| **形式化状态机 + 模型检查** | 把仲裁策略写成显式状态机，用模型检查工具验证不变式（例如"tracking 永不被抢占"、"任何时刻最多一个前台 app 持有相机"、"授权总量不超过物理资源"） |
| **属性测试 / fuzzing** | 随机生成客户端请求序列（含崩溃、超时、并发），验证不变式始终成立 |
| **崩溃注入** | 在任意时刻 kill 任意客户端，验证资源 100% 回收 |
| **压力测试** | 高频 open/close/抢占循环跑几小时，检查泄漏 |

> **不变式驱动的验证是这道题的关键。** "我不会试图枚举所有场景，而是定义一组必须始终成立的不变式，然后用随机测试去攻击它们。**不变式清单本身就是设计文档的核心部分**——如果我说不清系统的不变式，说明我还没设计清楚。"

**核心不变式清单：**

1. 任意时刻，被授权的资源集合 ⊆ 物理资源集合
2. 系统 tracking 的授权永不被撤销（除非设备关机）
3. 任一客户端进程终止后 1 秒内，其所有授权和 buffer 被回收
4. 相机通电 ⟺ 隐私指示灯亮（**这条要在硬件上验证，不是软件**）
5. 用户显式操作的抢占在 200 ms 内生效
6. 审计日志的条目数 = 授权次数（无遗漏）

### 9.2 抢占延迟测量

- **端到端计时**：从按键中断到第一帧 buffer 可用，打硬件时间戳
- **分解计时**：§6.1 每一项单独埋点，找出实际的支配项（可能和估算不同）
- **回归守护**：这个指标要进 CI，任何 PR 让它超过 200 ms 就阻断

### 9.3 隐私保证的验证

**这一节是这道题的重点，因为它验证的是"承诺"而不是"功能"。**

| 保证 | 怎么验证 |
|------|---------|
| **相机通电必亮灯** | **硬件测试**：示波器同时测相机电源域和 LED 驱动信号，验证时序关系；**故障注入**：让软件尝试关灯（模拟被攻破），验证灯仍亮 |
| **遮挡检测有效** | 物理遮挡测试（胶带、手指、不同材质），验证拒绝开启 |
| **像素不出设备** | **网络流量审计**：抓包分析设备所有出站流量，验证没有图像数据；静态分析：检查代码里所有网络出口的数据来源 |
| **量产构建无 dump 路径** | **CI 检查**：对量产二进制做符号/字符串扫描，发现 dump 相关符号即失败 |
| **审计日志完整** | 注入随机的相机使用序列，验证日志条数与实际一致 |
| **数据分级隔离** | 尝试从低权限进程 import 高敏感 buffer（tracking/眼动），必须失败 |

> **最后一行是主动的红队测试。** "我会让安全团队真的去尝试从一个第三方 app 拿到 tracking 相机的 buffer。**如果没人试过，'进程隔离'就只是一句话。**"

### 9.4 用户理解度验证（容易被忽略）

隐私保护如果用户看不懂就没有价值：

| 测试 | 方法 |
|------|------|
| **指示灯可见性** | 不同环境光（室内、户外、夜间）下，旁人在 1–3 m 距离的识别率 |
| **用户心智模型** | 访谈：用户认为什么时候相机开着？和实际是否一致？ |
| **旁人感知** | 让不知情的第三方判断"这个人在录像吗" |
| **审计界面可理解性** | 用户能否正确回答"昨天哪个 app 用了相机" |

**这些是 UXR 的工作，但要在工程设计阶段就介入**——因为指示灯的位置、亮度、颜色是硬件设计，改不了。

### 9.5 Fleet SLI

| SLI | 阈值 |
|-----|------|
| 抢占延迟 p95 | < 200 ms |
| 相机资源泄漏事件（需要服务重启） | < 1 次/1000 设备日 |
| 客户端异常终止后的回收成功率 | 100% |
| 隐私 LED 自检失败率 | ~0（任何非零都要调查） |
| 遮挡检测触发率 | 监控（异常高可能是硬件问题或用户行为信号） |
| 授权被拒绝的原因分布 | 监控（权限/冲突/热/LED） |
| 审计日志写入失败率 | ~0 |

## 10. 演进与组织

| 契约物 | Owner | 消费者 | 出事的方式 |
|--------|-------|--------|-----------|
| **隐私 LED 的硬件绑定电路** | HW | 你 + 安全 | 设计成"软件控制 + 软件保证"，评审时才发现不满足威胁模型——**而硬件已经流片** |
| 威胁模型文档 | 安全 | 所有人 | 没写下来 → 每个人有不同的假设 |
| 数据分级表 | 隐私/法务 | 你 | 定得晚 → 架构已经按"所有数据都一样"做了 |
| 仲裁策略与优先级 | 产品 | 你 | 产品不给明确答案 → 工程自己定 → 上线后被推翻 |
| 客户端 API 与租约语义 | 你 | 所有客户端团队 | 客户端不实现续租 → 频繁被回收 |
| 不变式清单 | 你 | QA / 安全 | 没有清单 → 无法系统性验证 |
| 各法域的合规要求 | 法务 | 你 + 产品 | 发现太晚 → 某个市场不能发 |

**最容易出事的是第一行，而且它是不可逆的：**

> "隐私 LED 的硬件绑定必须在**硬件设计评审阶段**就定下来。如果等到软件集成期才发现'我们需要硬件强制'，板子已经流片了，唯一的选择是软件方案 + 在威胁模型文档里记录这个缺口——然后这个缺口会跟着产品的整个生命周期。
>
> **所以这是一个 E6 必须在项目最早期就推动的事项**，即使那时候还没人在讨论隐私。识别出'哪些决策是不可逆的、必须最早做'，是这个级别的核心能力。"

**分阶段：**

| 阶段 | 出口标准 |
|------|----------|
| P0（**硬件设计期**） | 隐私 LED 电路方案 + 威胁模型评审签字；数据分级表初版 |
| P1 | Policy Service 骨架 + 租约机制；不变式清单定稿 |
| P2 | 仲裁策略实现 + 属性测试/崩溃注入跑通 |
| P3 | 抢占延迟达标（3A 状态共享 + 预配置 stream） |
| P4 | 隐私保证验证（硬件测试 + 红队 + 网络审计 + CI 检查） |
| P5 | 用户理解度验证；审计界面；fleet SLI |

**收口金句：** 这道题有两个正交的轴——**仲裁是工程问题**（优先级 + 兼容性矩阵 + 租约回收，抢占延迟的最大项是 3A 收敛，靠状态共享而不是加速来解决）；**信任不是工程问题**，工程的角色是**让产品承诺在硬件上成立**：隐私指示灯必须与电源域绑定而非软件控制，敏感路径的 dump 能力必须在量产构建里编译不进去，隐私相关的失效必须 fail-closed。而这两条硬件级的约束**必须在硬件设计评审期就推动**，因为它们是整个项目里最不可逆的决策。
