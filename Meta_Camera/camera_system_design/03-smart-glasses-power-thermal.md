# 场景 3：智能眼镜 — 低功耗、热约束、AI 唤醒与连续录像

**典型题：** 为 Ray-Ban 类智能眼镜设计 AI 视觉唤醒 + 连续录像系统。

**核心考点：** 异构功耗分层、Zero-Copy DMA-BUF / ION、热节流时降帧 / 降分辨率且要平滑。

功耗数字与级联唤醒叙事对齐 [`company/openai/smart-glasses-ai-runtime.md`](../../company/openai/smart-glasses-ai-runtime.md)。

---

## 1. 需求与约束

贴脸设备 **热是产品约束，不是优化项**。

| 维度 | 默认假设 |
|------|----------|
| 整机功率 | **1.5–2.5 W** 峰值；待机 / AON ≪ 100 mW |
| 电池 | 400–600 mAh → 连续录像以小时计要靠降档 |
| 内存 | 2–4GB 共享；CPU/GPU/NPU/ISP 抢同一套 LPDDR |
| 延迟 | 视觉唤醒 **< 100–200 ms** 到主摄出第一帧；预览 <30ms |
| 体验 | 长按录像不烫耳；误唤醒率低；隐私（指示灯 / LED） |
| 传感器 | ULP 视觉或 IMU+麦克风 做 AON；主摄 1080p 级 RS |

**开场金句：** 主 SoC + 全 ISP + 编码器不能 Always-on。架构中心是 **级联唤醒状态机 + 热状态机**，像素全程 dma-buf，CPU 不拷 1080p。

## 2. 高层架构

```
[IMU / 触摸 / 语音 DSP]          [ULP 视觉 Sensor 或主摄 subsample]
         │                              │ 极低 MIPI 或 SPI
         ▼                              ▼
    Always-on MCU/DSP              运动 / 简易人物检测（mW 级）
         │                              │
         └──────── 唤醒条件满足 ────────┘
                         ▼
              打开主 MIPI + IFE + 有限 IPE
                         │
                         ▼ dma-buf
              ┌──────────┼──────────┐
              ▼          ▼          ▼
           预览/取景   录像 Encoder  NPU（手势/场景，短 burst）
```

状态（只允许这些跳转，带滞回）：

```
S0 Sleep        AON IMU/语音     ~1–10 mW
S1 ULP vision   低分辨率检测     数十 mW
S2 Peek         主摄短预览/抓拍  数百 mW–1W 数百 ms
S3 Record       1080p30 + encode 接近热墙
S4 Throttle     720p15 / 关 NPU  守皮肤温
```

S3 不能直接回 S0（用户在录）；只在 S4 与 S3 之间按温度滞回。

## 3. 核心子系统

### 3.1 异构计算与功耗分层

| 层 | 硬件 | 干什么 | 不干什么 |
|----|------|--------|----------|
| AON | 独立 DSP/MCU | VAD、敲击、IMU wake | 跑 ISP、跑大模型 |
| ULP CV | 小阵列或主摄 binning + 微型 CV | 运动、或许 HOG/tiny CNN | 4K、3A 猎焦 |
| 主 ISP | IFE + 轻 IPE | 录像 / 预览 | 夜景 10 帧融合（改抓拍态） |
| NPU | Burst | 唤醒确认、场景、语音视觉 | 持续 30fps 大模型 |

唤醒策略（降低误触）：

1. IMU 或语音过门槛 → S1  
2. ULP 确认“像使用意图”（举镜、有人脸/手）→ S2 开主摄  
3. NPU 二次确认才进 S3 长录  

主摄启动成本：PLL lock、MIPI settle、第一帧 3A。为压到 200ms：**预保持 Sensor 在 standby 而不是 power-off**（漏电 vs 延迟的权衡，产品定）。

### 3.2 内存与带宽削峰（Zero-Copy）

录像时三条消费者：encoder、（可选）预览、（可选）NPU。错误做法：IFE → CPU memcpy 三份。

正确：

```
Gralloc / dma-buf 分配 NV12（或 UBWC）
IFE/IPE 写 fd
        ├─ Encoder import fd   （HW）
        ├─ GPU/Display import  （预览，可降分辨率另一条 stream）
        └─ NPU import fd       （若要 AI，用缩小的 analysis stream）
sync fence：生产者 signal，消费者 wait
```

ION 是高通历史上的连续内存堆；新平台是 **dma-buf heap**。面试说：“用户态只传 fd 与 fence，SMMU 映射给各 IP。”

削峰：

- Analysis 流 320×240 给 NPU，不要喂 1080p。
- Encoder 与 ISP 协商 UBWC，少 30–50% DDR。
- 禁止预览 RGB 888。
- 环形缓冲深度 3；App 持 buffer 过久 → 掉帧，用超时回收（HAL3 buffer 管理）。

Cache：DMA 写后 CPU 若要读（调试 dump），必须 invalidate；热路径 CPU 不读像素。

### 3.3 热节流平滑策略

皮肤温 / 结温 / 电池温 三个传感器。策略要 **单调、有滞回、用户可感知但不闪烁**。

建议阶梯（示例，数字面试时声明是假设）：

| 档 | 触发（示意） | 动作 |
|----|--------------|------|
| T0 | 正常 | 1080p30 + 轻量 NPU 1Hz |
| T1 | 皮肤温升 | 关 NPU 连续推理；ISP NR 降档 |
| T2 | 再升 | **30 → 24 或 15 fps**（先降帧，分辨率暂时不变） |
| T3 | 接近限 | **1080p → 720p**，encoder GOP 简化 |
| T4 | 硬限 | 停录、提示过热；Sensor 回 S1 |

为什么先降帧再降分辨率：分辨率切换要 **重 configureStreams**（闪一下、要重新 3A）；降 fps 可在 sensor VTS 上改，体验更连续。

防抖振：升档阈值 < 降档阈值（例如 41°C 降、37°C 才升），最短停留 15–30s。

录像文件：fps 变化要写进容器时间戳，播放器按 PTS，不要假装一直 30fps。

## 4. 性能优化与边界

- **Always-on 误唤醒：** 用双因子（运动+视觉）；记录隐私灯与本地日志（无图）。
- **第一帧发黑：** Sensor 从 standby 起来 AE 未收敛 → 用 ULP 估的 lux 做 **warm start exposure**。
- **边录边传：** Wi-Fi 上传不得阻塞 ISP 线程；独立低优先级进程，热档 T2 以上禁止后台编码第二路。
- **掉帧：** 见 [`camera/掉帧.md`](../../camera/掉帧.md)。眼镜上优先假设 **热和 DDR**，再查 MIPI。
- **隐私：** 物理指示灯与 ISP streamon 绑定，软件关不掉（HW 或安全元件）。

| 团队 | 契约 |
|------|------|
| 工业设计 / 热 | 皮肤温测点位置、限值、风扇（通常没有）→ 软件阶梯必须匹配实测 |

## 6. 数字预算：热是这题唯一真正的约束

### 6.1 先把热墙算出来，其余全部从它推导

一阶集总 RC 模型：


$$
\Delta T = P \times R_{th}, \qquad \tau = R_{th} \times C_{th}
$$

眼镜镜腿的量级（要声明是假设，让面试官修正）：

- $R_{th}$（芯片结 → 皮肤接触面 → 环境）≈ **15–25 °C/W**
- 皮肤长时接触限值 ≈ **43 °C**（塑料外壳可略高，金属更低；参考 IEC 62368 的接触温度限）
- 环境温度按 25 °C 设计，**但要按 35 °C 校验**（夏天户外）


$$
P_{\max}(25^{\circ}\mathrm{C}) = \frac{43 - 25}{20} = \mathbf{0.9\ W},\qquad
P_{\max}(35^{\circ}\mathrm{C}) = \frac{43 - 35}{20} = \mathbf{0.4\ W}
$$

> **这个 0.4 W 是整道题最重要的数字。** 它说明：**在 35 °C 环境下，眼镜的稳态可用功率不到半瓦。** 连续录像在物理上就是做不到的——不是软件优化不够，是热力学不允许。所以产品定义必须是"限时录像"，软件的任务是**把这个限制变成优雅的体验**而不是消灭它。

### 6.2 时间常数决定了 burst 策略


$$
\tau = R_{th} \times C_{th} \approx \mathbf{3\text{--}10}\ \mathrm{min}
$$

物体升温到稳态值的 63% 需要一个 $\tau$。这意味着：

- **短于 $\tau/3$（约 1–3 分钟）的 burst 可以显著超过稳态功率上限**，温度还来不及升上去
- 这直接支撑："拍照（几百毫秒 2W）随便拍；录像（持续 1.5W）限时 3–5 分钟"
- 也直接给出滞回的时间参数：**最短停留时间应该是几十秒量级**（远小于 $\tau$，但足够让阈值穿越不抖动），而不是几秒


$$
T(t) = T_\infty + (T_0 - T_\infty) e^{-t/\tau}
$$

用这个式子可以**预测**多久会撞墙，从而做**前瞻性降级**（在温度到达阈值前就开始平滑降档），而不是等撞到再急刹车。这是 E6 会提的做法：

> "我不想用纯阈值触发的反应式节流，因为那会产生可见的画质台阶。我用温度的**一阶导数**做预测：如果按当前升温斜率外推 60 秒会越限，现在就开始降一档。用户看到的是缓慢变化而不是突变。"

### 6.3 能量预算（决定"一天"能不能撑住）


$$
500\ \mathrm{mAh} \times 3.7\ \mathrm{V} = 1.85\ \mathrm{Wh} = 6660\ \mathrm{J}
$$

**单场景续航（无意义但要先算）：**

| 场景 | 功率 | 续航 |
|------|------|------|
| 待机（AON only） | 20 mW | 92 小时 |
| S1 ULP 视觉 | 60 mW | 31 小时 |
| S3 录像 1080p30 | 1.5 W | 74 分钟 |
| 拍照单张（含唤醒） | 2 W × 1.5 s = 3 J | — |

**混合使用模型（这才是产品的真实问题）：**

| 活动 | 次数/时长 | 能量 |
|------|-----------|------|
| 全天待机 16 小时 @ 20 mW | — | 1152 J |
| S1 ULP 视觉抽样 2 小时 @ 60 mW | — | 432 J |
| 拍照 30 张 @ 3 J | — | 90 J |
| 录像 10 分钟 @ 1.5 W | — | 900 J |
| Wi-Fi 上传 500 MB | — | ~600 J |
| **合计** | | **3174 J** |

$3174 / 6660 = \mathbf{48\%}$ ——留了一倍余量，**这个用例模型下能撑一天**。

> **E6 的关键动作：把待机功率单独拎出来做敏感度分析。** 待机占了 1152 J（36%），而它是 16 小时 × 20 mW。**如果 AON 从 20 mW 涨到 50 mW，就多消耗 1728 J，直接击穿预算。** 所以"AON 功耗每一毫瓦都要抠"不是洁癖，是算出来的：**待机功率的边际成本是录像功率的 800 倍**（16 小时 vs 10 分钟）。
>
> 这条推论比任何定性描述都有说服力，而且它直接决定了架构：**唤醒判断必须在最低功耗的那一层做到足够准，因为把主 SoC 唤醒起来"看一眼"的代价是几百倍。**

### 6.4 误唤醒的功耗代价（把误报率变成毫瓦）

假设一次误唤醒（S1→S2→发现没事→回 S1）耗时 300 ms，平均功率 800 mW：


$$
E_{\mathrm{FA}} = 0.8 \times 0.3 = 0.24\ \mathrm{J}
$$

每小时误唤醒 $N$ 次，等效常态功率增加：


$$
P_{\text{eq}} = \frac{0.24 N}{3600}\ \mathrm{W} = 0.067 N\ \mathrm{mW}
$$

- $N = 10$/小时 → 0.67 mW（可忽略）
- $N = 100$/小时 → 6.7 mW（占 AON 预算 1/3，开始疼）
- $N = 600$/小时（每 6 秒一次）→ 40 mW（**待机续航直接砍半**）

> **这个计算给出了唤醒分类器的设计指标：误唤醒率必须压到 < 50 次/小时。** 而这个数字反过来决定了 ULP CV 需要多复杂的模型。**把体验指标翻译成可验证的工程指标，是 E6 的核心动作。**

### 6.5 带宽也要换算成功耗

按 **~100 mW/(GB/s)**：

- 1080p30 NV12 录像：ISP 写 93 + encoder 读 93 = 186 MB/s ≈ **19 mW**
- 如果 CPU 多拷一份（错误做法）：+186 MB/s ≈ **+19 mW**，还要加 CPU 本身的几十 mW

> 一次多余的 `memcpy` 大约值 **40–60 mW**，占整机预算的 3%。零拷贝在眼镜上不是优雅，是**算得出来的续航**。

## 7. 关键决策与被否方案

| 决策 | 我选 | 否掉的 | 为什么 | 什么会让我翻盘 |
|------|------|--------|--------|----------------|
| AON 视觉来源 | **独立 ULP 图像传感器** | 主摄跑 binning 低功耗模式 | 主摄即使 binning 也要 CSIPHY + IFE 上电，量级在 100 mW+；ULP sensor 可以做到个位数 mW（片上简单检测，甚至不出图） | SoC 有超低功耗的 CSI 通路（部分 SoC 有专用 AON camera path），或 BOM/体积不允许多一颗传感器 |
| 主摄空闲态 | **standby（保持寄存器 + PLL 关，几 mW 漏电）** | 完全断电 | 冷启动要 PLL lock + MIPI settle + 3A 收敛，200 ms+；standby 能压到 50–80 ms | 待机时长要求极端（多天），此时接受慢启动 |
| 降级顺序 | **先降 fps，后降分辨率** | 先降分辨率 | 改分辨率要 `configureStreams` 重配，画面会闪一下并重新 3A；改 fps 只改 sensor VTS，连续无感 | 编码器在低 fps 下效率反而差（某些 encoder 有最低码率约束），此时先降分辨率 |
| 节流触发 | **预测式（温度一阶导外推）+ 阈值兜底** | 纯阈值反应式 | 纯阈值会产生可见的画质台阶和抖振 | 温度传感器噪声大导致导数不可用，退回阈值 + 更大滞回 |
| 唤醒确认 | **三级级联（IMU/语音 → ULP CV → NPU）** | 单级 ULP 判断 | 单级要么误唤醒率高（吃电，见 §6.4）要么漏检率高（体验差） | 用例简单到只有明确手势触发（例如必须按按钮），那就不需要级联 |
| 上传时机 | **仅在充电 / 入盒 / 接 Wi-Fi 且温度低于 T1 时** | 随时机会式上传 | 上传本身发热且耗电，与录像叠加会直接撞热墙 | 产品要求"实时分享"，此时必须给上传单独的热预算并允许它抢占录像 |
| 隐私指示灯 | **硬件与相机电源域绑定** | 软件控制 GPIO | 软件 bug 或被攻破时 LED 必须仍然亮；这是**设计上的可信**而非实现上的正确 | 无。这条是产品红线 |

## 8. 失效模式与降级

| 失效 | 检测 | 恢复 | 用户可见 |
|------|------|------|----------|
| **温度失控**（散热路径异常，例如设备被放进包里） | 升温斜率异常高 | 跳过中间档直接进 T4 停录 | "设备过热，已停止录制" |
| **温度传感器失效** | 读数卡死 / 超出物理范围 | **fail-safe 到最保守档位**，不是忽略 | 功能受限 |
| **电池低温**（户外冬天） | 电池温度 < 0 °C | 限制放电电流 → 禁止高功耗模式；不是软件 bug 是电化学限制 | "温度过低，部分功能不可用" |
| **误唤醒率飙升**（衣服遮挡 ULP sensor） | 误唤醒计数器 | 自适应提高阈值；持续则暂时禁用视觉唤醒只留按钮 | 唤醒变迟钝 |
| **主摄冷启动超时** | 首帧 watchdog | 重试一次；仍失败则报错并回 S1，**不要卡在 S2 耗电** | 拍摄失败提示 |
| **首帧过曝/过暗** | 首帧统计偏离目标 | 用 ULP 估计的 lux 做 warm start；必要时丢弃首 1–2 帧 | 无 |
| **存储写入抖动 / 满** | 写延迟 p99；剩余空间 | 提前预分配文件；空间不足提前停录并保证文件可播 | "存储空间不足" |
| **录像中降档** | 热状态机 | fps/分辨率变化**必须写进容器时间戳** | 流畅度变化；播放不能错乱 |
| **上传与录像争抢** | 温度 + 带宽 | T2 以上禁止后台上传 | 上传变慢 |
| **电池老化后功率不足** | 电池内阻上升导致高负载掉压 | 按电池健康度调整最高档位 | 老设备录像时长变短 |

**一条设计原则：** 热状态机是**全局单一权威**。ISP、NPU、编码器、Wi-Fi 都是它的下游执行器，不允许任何模块自行决定"我再多跑一会儿"。实现上是一个中心化的 thermal governor，各模块注册自己的降级能力和收益（省多少 mW），governor 按性价比排序执行。

> **这个设计的价值在组织层面：** 没有中心 governor 时，每个团队都在自己的模块里加节流逻辑，互相踩踏，最后没人知道为什么设备在某个场景下降到 15fps。**中心化是为了可解释性，不只是为了效率。**

## 9. 怎么证明它是对的

### 9.1 热验证台架

| 测试 | 方法 | 出口标准 |
|------|------|----------|
| **稳态热** | 恒温箱 25 °C / 35 °C，跑最大负载至热平衡 | 皮肤接触点热电偶 < 43 °C |
| **热成像** | 红外相机拍全机，找热点 | 无局部热点超限（热点常在 PMIC 和 SoC 正上方，不一定是软件能解的） |
| **热电偶布点** | **贴在真实皮肤接触位置**（镜腿内侧、鼻托），不是贴在 PCB 上 | 与人体测试相关性验证过 |
| **人体试戴** | 真人佩戴 + 主观不适评分 | 这是最终仲裁；热电偶只是代理指标 |
| **降级阶梯验证** | 强制升温，记录每一档的触发时刻和动作 | 阶梯单调、无抖振、动作与设计一致 |
| **低温** | -10 °C，验证电池限流路径 | 不崩溃，提示正确 |

**E6 的关键点：** 热电偶读数和用户感受不是一回事。**同样 42 °C，金属件比塑料件"更烫"**（导热率不同），**接触面积也影响主观感受**。所以必须有人体试戴环节，并把它和台架指标建立相关性——之后才能用台架代替人测。

### 9.2 功耗验证

- **逐 block 功耗拆解**：用带电流探头的电源分析仪 + 各电源轨分别测（不能只测总电流）。这是 §6.2 那张表的数据来源，**没有实测的功耗表是编的**。
- **场景化续航**：按 §6.3 的混合模型做自动化脚本跑 24 小时，测真实电量曲线。
- **待机漏电**：最难测也最重要——设备静置 8 小时的电量下降。**AON 功耗的回归必须自动化**，因为它涨了 20 mW 没人会立刻发现，但续航会掉 30%。

### 9.3 唤醒质量

| 指标 | 测法 | 目标 |
|------|------|------|
| 误唤醒率 | 佩戴设备日常活动 8 小时，统计唤醒事件 | < 50 次/小时（由 §6.4 推出） |
| 漏检率 | 脚本化手势/场景重复 N 次 | < 5% |
| 唤醒延迟 p95 | 从触发动作到首帧可用 | < 200 ms |
| 首帧可用性 | 首帧 AE 偏差 | 在目标 ±1 EV 内 |

**误唤醒测试必须在真实佩戴场景做**（走路、坐车、吃饭、和人说话），实验室静置数据毫无意义。

### 9.4 Fleet SLI

| SLI | 阈值 |
|-----|------|
| 日均待机功耗（从电量曲线反推） | 回归即告警 |
| 每小时唤醒次数分布 | p95 < 50 |
| 热降级发生率 / 各档停留时长分布 | T3+ 占比 < 5% |
| 录像被热中断的比例 | < 10% |
| 唤醒到首帧 p95 | < 200 ms |
| 电池健康度分布（按设备年龄） | 趋势监控 |

**热降级的档位分布是最有信息量的一条**：如果 fleet 上 30% 的录像都进了 T3，说明产品定义（"能录多久"）和物理现实脱节，这是要反馈给产品而不是继续优化软件的信号。

## 10. 演进与组织

### 10.1 契约

| 契约物 | Owner | 消费者 | 备注 |
|--------|-------|--------|------|
| **热限值与测点定义** | 工业设计 / 热团队 | 你 | 必须是**实测标定过**的测点，不能是仿真值 |
| Thermal governor API（注册降级能力、上报收益） | 你 | ISP / NPU / 编码器 / Wi-Fi | 中心化权威，所有模块必须走它 |
| DVFS 表 / 电源轨分配 | 系统 PM | 你 | T2 时砍哪些频点、留给谁 |
| Sensor standby 电流 vs 出图时间 | Sensor 厂 | 你 | 这是 §7 那个决策的输入数据 |
| ULP CV 模型的功耗-准确率曲线 | 算法 | 你 | 你按 §6.4 的公式给出功耗预算，他们在预算内选点 |
| 隐私指示灯的硬件绑定方案 | HW | 你 + 法务 | 产品红线，需要 HW 设计评审签字 |
| 降档时的 IQ 预设（15fps / 720p 各一套） | IQ | 你 | 避免降档后突然"更糊或更噪"，用户会以为坏了 |

**最容易被忽略的是最后一行。** 降到 720p15 时如果沿用 1080p30 的 NR 参数，画质会断崖式下跌，用户的投诉是"录一会儿就变糊了"——而团队会以为是热降级本身的问题。**每一个降级档位都是一个需要单独调优的产品状态**，不是一个应急旁路。

### 10.2 分阶段

| 阶段 | 出口标准 |
|------|----------|
| P0 | 逐 block 功耗实测表建立（不是估算） |
| P1 | AON 通路打通，待机功耗达标且有自动化回归 |
| P2 | 级联唤醒打通，误唤醒率进指标 |
| P3 | 录像通路 + 零拷贝验证（用带宽计数器证明没有多余拷贝） |
| P4 | 热状态机 + 各档 IQ 预设；热箱与人体试戴通过 |
| P5 | 量产：fleet SLI 上线，续航模型与实测校准 |

**P0 的功耗实测表必须最先做。** 没有它，后面所有的架构决策都是猜的——而这道题的每一个决策都是从功耗数字推出来的。

**收口金句（E6 版）：** 眼镜相机系统是一台**热管理状态机**，ISP 只是它的执行器。但真正把这句话变成可交付系统的是三个数字：**35 °C 环境下 0.4 W 的稳态上限**（决定了产品必须是限时录像）、**待机功率的边际成本是录像的 800 倍**（决定了唤醒判断必须在最低功耗层做准）、以及**误唤醒率 50 次/小时**（把体验指标翻译成了分类器的设计约束）。
