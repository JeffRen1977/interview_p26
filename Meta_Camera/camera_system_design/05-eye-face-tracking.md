# 场景 5：眼动 / 面部追踪与 Foveated Rendering

**典型题：** 为头显设计眼动追踪子系统，支撑 foveated rendering 和 avatar 表情驱动。

**核心考点：** 近眼 IR 成像、主动照明与眼安全、PCCR 几何模型、注视延迟与扫视预测、生物识别数据的隐私边界。

**为什么这题会出现：** foveated rendering 直接决定 GPU 预算，是 Meta 头显路线的核心技术。而且它是一道**"子系统必须自己证明 ROI"** 的题——眼动本身耗电，它必须省下比自己更多的电。

---

## 1. 需求与约束

| 维度 | 默认假设 | 为什么 |
|------|----------|--------|
| 相机 | 每眼 1–2 颗**近眼 IR 单色**相机，**GS**，400×400 级，90–120 fps | 单色够用（IR 主动照明）；GS 因为眼球扫视极快 |
| 照明 | 每眼 6–12 颗 **IR LED**（850 或 940 nm），产生角膜反光（glint / 普尔钦斑 I） | 940 nm 对用户不可见；850 nm 效率高但会看到微弱红光 |
| 精度 | **准确度 < 1°，精度（重复性）< 0.5°** | 中央凹约 ±2.5°，误差吃掉 foveation 余量 |
| 延迟 | 注视更新 → 渲染指令 **< 10 ms** | 否则 foveation 边界在扫视后被看见 |
| 功耗 | 全程常开，**目标 < 250 mW（双眼）** | 必须小于它省下的 GPU 功耗 |
| 覆盖 | 眼球转动范围 ±30° 内保持精度 | 超出范围人会转头而不是转眼 |
| 隐私 | 眼部图像是**生物识别数据**，不出芯片 | 法规 + 信任；只输出注视向量 |
| 面部 | 另有嘴/脸颊相机（RS 可接受），驱动 avatar blendshape | 表情不需要亚度精度 |

**开场金句：** 这不是一条成像管线，是一条**几何测量管线**。相机只是传感器，输出不是图像而是**角膜球心 + 瞳孔中心两个 3D 点**。所以 ISP 全砍——不 demosaic、不 3A 美化、不 tonemap，只要线性、低噪、时间戳准。而这个子系统必须自证 ROI：**它耗的 250 mW 要换回 GPU 上省下的瓦级功耗。**

## 2. 高层架构

```
       ┌─────── FSYNC（与主 tracking 同一时钟域）───────┐
       ▼                                               ▼
  [IR LED 环 L]                                  [IR LED 环 R]
       │ 频闪：只在曝光窗口点亮（duty ~10%）              │
       ▼                                               ▼
  [Eye Cam L ×1–2]                              [Eye Cam R ×1–2]
       │ MIPI CSI-2（低速）                              │
       ▼                                               ▼
   CSIPHY/CSID → IFE **FE-only**：BLC + 硬件时间戳（不 demosaic）
       │
       ▼ dma-buf（小帧，160 KB 级）
   DSP / NPU：
       ├─ 瞳孔分割（CNN 或阈值+椭圆拟合）→ 瞳孔中心（亚像素）
       └─ Glint 检测（连通域 + 亚像素质心）→ glint 星座
       │
       ▼
   3D 眼球模型：角膜球心（由 glint 星座 + LED 已知位置解算）
                 + 瞳孔中心 → **光轴**
                 + 用户标定的 kappa 角 → **视轴（真实注视方向）**
       │
       ▼
   注视滤波 + **扫视预测**（补偿渲染延迟）
       │
       ├──► Foveated Rendering（GPU 的注视点）
       ├──► 交互（注视选择、动态景深）
       └──► Avatar（配合面部相机）
```

**Glint 检测就是 [`../code/blob_centroid.md`](../code/blob_centroid.md)。** 亚像素质心的 0.05 px 精度直接换算成角度精度——这是那道 coding 题和这道设计题的接口。

## 3. 核心子系统

### 3.1 为什么必须有 glint（PCCR 的本质）

只用瞳孔中心是不够的：**头显在脸上滑动（slippage）时，瞳孔在图像里的位置会变，但用户根本没有改变注视方向。**

Glint 解决这个问题：

```
角膜近似为一个球（半径 ~7.8 mm）
LED 位置已知 → glint 是 LED 在角膜球面上的镜面反射
≥ 2 个 glint + 已知 LED 几何 → 解出角膜球心的 3D 位置

注视方向 = 归一化(瞳孔中心 - 角膜球心)
```

**关键性质：角膜球心和瞳孔中心是同一个刚体上的两个点。** 相机相对眼睛整体平移时，两者一起动，**差向量不变**。这就是 PCCR（Pupil Center Corneal Reflection）对滑动鲁棒的几何原因。

> 面试时把这句话说出来："glint 不是用来提高精度的，是用来**消除相机-眼睛相对位移的自由度**的。没有它，头戴设备每滑动 1 mm 注视就错几度。"

### 3.2 kappa 角：为什么必须做每用户标定

**光轴 ≠ 视轴。** 中央凹不在眼球光轴上，偏离约 **水平 4–6°、垂直 1–3°**，因人而异（kappa / angle alpha）。

所以：

$$
\text{视轴} = \text{光轴} \oplus \kappa_{\text{user}}
$$

$\kappa$ 只能标定，不能推算。标定流程：

| 方式 | 点数 | 时长 | 精度 |
|------|------|------|------|
| 显式标定 | 5–9 点 | 15–30 s | 最好 |
| 快速标定 | 1–3 点 | < 10 s | 够用（配合眼球模型先验） |
| **隐式标定** | 0 点 | 持续 | 利用 UI 元素的注视统计做在线精化 |

**产品判断：** 显式标定是体验摩擦点（每次戴上都要做用户会烦）。所以架构上必须支持 **per-user 的标定持久化 + 戴上时的快速识别/验证**，而不是每次重来。

> **E6 会主动提的问题：** "标定和用户身份绑定意味着我在存**生物识别衍生数据**。这需要和隐私/法务对齐存储位置、加密、以及用户删除路径。**这不是我能单方面决定的架构，是需要跨职能签字的。**"

### 3.3 LED 频闪：功耗和眼安全的同一个杠杆

LED **只在曝光窗口点亮**，与 FSYNC 同步：

```
帧周期 8.3 ms @120fps
曝光窗口 0.5–1 ms
duty cycle ≈ 6–12%
```

**收益是双份的：**

1. **功耗**：LED 平均功率降到常亮的 1/8–1/16。这是这个子系统能进 250 mW 预算的关键。
2. **眼安全**：IEC 62471 的光生物安全限值是按**时间平均辐照度**算的，频闪直接把平均值压下来，让峰值可以更高（信噪比更好）。

> **必须主动说的一句：** "LED 常亮是错误设计，不只是浪费电——它同时浪费了眼安全预算。频闪让我在同样的安全限值下拿到 8 倍的瞬时照度，也就是更短的曝光和更少的运动模糊。"

**眼安全必须有硬件失效保护：**

| 风险 | 保护 |
|------|------|
| 驱动故障导致 LED 常亮 | **硬件限流** + 独立的看门狗定时器：帧循环停止则强制关断 LED |
| 软件挂死时 LED 停在开状态 | 看门狗不依赖主 SoC 的软件 |
| 单颗 LED 过驱 | 每路电流监测 |

**这条不能只靠软件。** 和 03 篇的隐私指示灯是同一个设计哲学：**安全相关的行为必须在硬件上成立。**

### 3.4 扫视预测：延迟不是靠优化砍掉的

扫视（saccade）角速度可达 **300–900 °/s**。10 ms 的端到端延迟意味着注视点已经移动了 **3–9°**——而中央凹只有 ±2.5°。**光靠降延迟解决不了。**

三个可用的机制：

**① 扫视抑制（saccadic suppression）**
人在扫视期间视觉是被抑制的（约 50–100 ms）。所以：

> **扫视进行中可以大胆降质渲染**，用户看不见。真正要保证的是**扫视落点（landing point）在扫视结束前就渲染好**。

**② 扫视落点预测**
扫视的速度曲线是高度刻板的（主序列关系：幅度与峰值速度强相关）。检测到扫视开始后的前 20–30%，就能预测落点：

$$
V_{\text{peak}} \approx f(A) \quad\Rightarrow\quad \text{由早期速度反推幅度 } A \text{ 与落点}
$$

**③ 分档 foveation 半径**
不确定度高时（扫视中、置信度低、刚丢失）**扩大高清区半径**而不是猜错位置。这是最重要的工程原则：

> **foveation 的失败模式必须是"多渲染一点"，而不是"渲染错地方"。** 前者只是浪费 GPU，后者用户直接看到糊。

### 3.5 面部追踪是另一个问题

嘴/脸颊相机和眼动共用架构但**不共用要求**：

| | 眼动 | 面部 |
|---|------|------|
| 快门 | GS 必须 | RS 可接受（表情慢） |
| 帧率 | 90–120 | 30–60 够 |
| 输出 | 几何量（3D 点） | **blendshape 系数**（ML 回归） |
| 精度要求 | 亚度 | 感知一致即可 |
| 主动照明 | 必须 | 可选 |
| 延迟 | < 10 ms | < 50 ms（社交场景可容忍） |

**所以不要把它们做成同一条管线。** 眼动是几何测量，面部是 ML 推理，它们的失效模式、验证方法、迭代节奏都不一样。共享的只有相机基础设施和时间戳。

## 4. 性能优化与边界

| 问题 | 策略 |
|------|------|
| **ROI 追踪** | 眼球位置帧间变化小 → 只读出眼睛所在的 ROI（sensor 支持 windowing），带宽和曝光时间都省。丢失时才全帧搜索 |
| **算力** | 瞳孔分割用小 CNN（几百 KFLOP 级），glint 用传统连通域。**不要用一个大网络端到端回归注视**——不可解释、不可标定、失败时无法降级 |
| **戴眼镜** | 镜片表面产生**额外的假 glint**。用 LED 时序调制（每颗 LED 按不同 pattern 闪）区分真假 |
| **眨眼** | 检测到眼睑遮挡 → **保持上一注视值**，不要输出跳变。眨眼 100–400 ms，保持即可 |
| **瞳孔大小变化** | 亮度变化时瞳孔缩放，瞳孔中心会有轻微偏移（pupil size artifact）→ 建模或用 glint 主导 |
| **暗瞳 vs 亮瞳** | 照明轴与相机轴同轴 → 亮瞳（视网膜反射，对比度高但受虹膜颜色影响）；离轴 → 暗瞳（更通用）。**默认选暗瞳** |

## 6. 数字预算

### 6.1 带宽和算力：这题不缺资源

双眼各 1 颗 400×400 单色 @120fps：

$$
400 \times 400 \times 1 \times 120 = 19.2\ \mathrm{MB/s}\ \text{（每眼）}\quad\Rightarrow\quad \mathbf{38\ MB/s}
$$

**可以忽略不计。** 用 ROI 读出后更小。所以：

> "带宽和 MIPI 都不是约束。这题的约束是 **功耗**（always-on）、**延迟**（扫视）、和**精度的长尾**（不同人眼差异极大）。我会把时间花在后两个上。"

### 6.2 功耗与 ROI —— 这个子系统必须自证价值

| Block | 功耗 |
|-------|------|
| 2 × 眼动 sensor @120fps | 60 mW |
| IR LED（频闪 10% duty，峰值 500 mW × 2 眼） | 100 mW |
| CSIPHY/CSID + IFE FE-only | 40 mW |
| DSP 检测 + 模型解算 | 60 mW |
| **合计** | **≈ 260 mW** |

**对面的收益：**

Foveated rendering 在 4K/眼 的头显上典型省 **2–3× 的 GPU 像素填充**。GPU 在满负载下 2–4 W：

$$
\text{节省} \approx 2\text{–}4\ \mathrm{W} \times \left(1 - \tfrac{1}{2.5}\right) \approx \mathbf{1.2\text{–}2.4\ W}
$$

$$
\text{ROI} = \frac{1200\ \mathrm{mW}}{260\ \mathrm{mW}} \approx \mathbf{5\text{–}9\times}
$$

> **这个计算是这道题的战略答案。** 它说明：
> - 眼动的功耗预算是**被收益反推出来的**，不是拍脑袋的。如果眼动涨到 800 mW，ROI 掉到 1.5×，这个特性就不值得做。
> - 它给出了一条**明确的红线**：眼动子系统的功耗上限 ≈ GPU 节省的 1/4。任何要求增加眼动功耗的提案（更多相机、更高帧率、更大模型）都要在这个天平上称。
> - **而且它给了一个可以拒绝的理由：** 有人提"我们把眼动帧率提到 240 fps 提高精度"，我可以直接算——功耗翻倍，ROI 减半，而精度收益在扫视预测面前是边际的。

### 6.3 延迟账本与扫视的对撞

```
曝光                        0.5 ms
readout（400×400 小帧）      1.5 ms
DMA + fence                 0.2 ms
瞳孔 + glint 检测            2.0 ms
眼球模型 + kappa             0.5 ms
滤波 + 预测                  0.5 ms
────────────────────────────────
注视可用                     ≈ 5.2 ms
+ 渲染管线（GPU 提交到扫描出） 10–20 ms
────────────────────────────────
注视 → 光子                  ≈ 15–25 ms
```

**扫视 500 °/s × 20 ms = 10° 的位移。** 中央凹 ±2.5°，高清区通常设 ±10–15°。

$$
\text{所需高清区半径} \geq \text{中央凹} + \text{注视误差} + v_{\text{saccade}} \times t_{\text{latency}}
$$

代入：$2.5° + 1° + 10° = 13.5°$。

> **这个公式是这道题的核心结论**，它把三个子系统连起来了：
> - **降延迟 1 ms** ≈ 高清区半径少 0.5° ≈ GPU 省几个百分点
> - **提精度 0.5°** ≈ 同样的效果，但可能比降延迟便宜得多
> - **做扫视预测**能把 $v \times t$ 这一项大幅压掉，这是**最大的一刀**
>
> 所以优化优先级是：**扫视预测 > 精度 > 延迟**。很多团队会本能地先去优化延迟，那是投入产出比最低的一项。

### 6.4 精度如何从像素换算到角度

$$
\theta_{\text{err}} \approx \frac{\Delta_{\text{px}} \times \text{px pitch}}{f_{\text{effective}}}
$$

粗略地说，一个眼动相机的角分辨率约 **0.05–0.15 °/px**（取决于视场和分辨率）。所以：

- **1 px 的质心误差 ≈ 0.1°**
- 目标 < 1° 准确度 → 质心误差预算约 **几个像素**，但要扣掉标定误差、模型误差、滑动残差
- **亚像素质心（0.05–0.1 px）不是过度设计**，它是在给上面几项留预算

> 这就是为什么 [`../code/blob_centroid.md`](../code/blob_centroid.md) 里"用强度加权而不是二值质心"这个细节值钱：**它是 0.5 px 和 0.05 px 的差别，也就是 0.05° 和 0.005° 的差别。**

## 7. 关键决策与被否方案

| 决策 | 我选 | 否掉的 | 为什么 | 什么会让我翻盘 |
|------|------|--------|--------|----------------|
| 注视解算 | **PCCR 几何模型 + CNN 只做瞳孔/glint 分割** | 端到端 CNN 直接回归注视角 | 几何模型可解释、可标定、失败可检测（残差）、跨用户泛化靠物理而非数据；端到端模型的失败是静默的且无法降级 | 有极大规模的跨人群标注数据，且端到端在长尾人群上明确胜出——但即便如此我也会保留几何路径做交叉验证 |
| 照明方案 | **离轴暗瞳** | 同轴亮瞳 | 亮瞳依赖视网膜反射，受虹膜颜色和瞳孔大小影响大，在深色虹膜人群上退化 | 目标人群窄且亮瞳信噪比优势明确 |
| 相机数/眼 | **先做 1 颗，架构预留 2 颗** | 直接上 2 颗 | 2 颗能覆盖更大转动范围和抗遮挡，但功耗和成本翻倍；先用 1 颗验证精度是否已达标 | 极端角度或戴眼镜人群的失败率不可接受 |
| LED 驱动 | **频闪，与 FSYNC 硬件同步** | 常亮 | §3.3：功耗和眼安全预算的双重杠杆 | 无 |
| 眼安全保护 | **硬件限流 + 独立看门狗** | 软件监控 | 软件挂死时保护必须仍然有效 | 无。合规红线 |
| 标定 | **持久化 per-user + 戴上时快速验证** | 每次戴上重新标定 | 体验摩擦 | 无法可靠识别用户身份（多人共用设备） |
| 追踪丢失时 | **回退到固定 foveation（中心高清）** | 关闭 foveation 全分辨率渲染 | 全分辨率会瞬间拉高 GPU 功耗和发热，可能触发热降级——**失败不该引发另一个失败** | GPU 有充足余量 |
| 面部追踪 | **独立管线** | 与眼动合并 | 需求、失效模式、迭代节奏完全不同 | 无 |

## 8. 失效模式与降级

| 失效 | 检测 | 恢复 | 用户可见 |
|------|------|------|----------|
| **眨眼** | 眼睑遮挡 / 瞳孔面积骤降 | 保持上一注视值 100–400 ms | 无 |
| **glint 被遮挡**（睫毛、下垂眼睑） | glint 数 < 2 | 退化为瞳孔中心 + 上一次的角膜位置（精度下降但可用），**并提高置信度不确定性 → GPU 扩大高清区** | 高清区变大（GPU 多花一点） |
| **眼镜镜片假 glint** | glint 数异常多 / 星座匹配失败 | LED 时序调制区分；无法区分则丢弃该帧 | 偶发抖动 |
| **头显滑动（slippage）** | glint 星座整体平移，但瞳孔-角膜差向量不变 | PCCR 天然免疫；若滑动过大超出视场则触发隐式重标定 | 无 |
| **标定失效 / 换用户** | 注视残差系统性偏置 | 提示快速重标定 | "请重新标定" |
| **LED 失效** | 该 LED 对应的 glint 恒定缺失 | 用剩余 LED 解算（≥2 个即可）；全失效则关闭眼动 | 降级到固定 foveation |
| **LED 驱动异常（过流/常亮）** | 硬件电流监测 + 看门狗 | **硬件强制关断**，不经过软件 | 眼动不可用 |
| **扫视预测错误** | 落点预测与实际偏差 | 预测置信度低时**扩大半径而不是赌位置** | GPU 多花一点 |
| **深色虹膜 / 特殊眼型上精度退化** | 分人群的精度统计 | 见 §9.2——这是**验证问题不是运行时问题** | 部分用户体验差（**最严重的失败**） |

**降级的统一原则（要说出来）：**

> "眼动的所有降级路径最终都收敛到一个动作——**提高不确定度，让渲染扩大高清区**。这比任何'尽力猜一个注视点'都好，因为**多渲染的代价是电，猜错的代价是用户看到糊**。我会把置信度做成注视 API 的一等公民，而不是一个可选字段。"

## 9. 怎么证明它是对的

### 9.1 精度台架

```
被试戴设备，注视屏幕上已知角度的靶点网格（例如 5×5 覆盖 ±25°）
测量：报告的注视角 vs 真实靶点角
```

| 指标 | 定义 | 目标 |
|------|------|------|
| **准确度（accuracy）** | 平均角误差 | < 1° |
| **精度（precision）** | 同一靶点的重复标准差 / RMS | < 0.5° |
| **有效追踪率** | 输出有效注视的帧占比 | > 98% |
| **重标定后漂移** | 30 分钟佩戴后的误差增长 | < 0.5° |
| **滑动鲁棒性** | 人为平移设备 ±3 mm 后的误差变化 | < 0.5° |

### 9.2 人群覆盖 —— 这一节是这道题最强的 E6 信号

> **眼动追踪有众所周知的人群偏差问题。** 一个在实验室（通常是年轻、浅色虹膜、不戴眼镜的工程师）上做到 0.8° 的系统，在真实人群上可能有 10–20% 的用户完全用不了。**如果我不主动设计人群覆盖的验证，我就是在设计一个会在发布后暴雷的系统。**

必须分层统计的维度：

| 维度 | 为什么影响 |
|------|-----------|
| **虹膜颜色 / 深浅** | 暗瞳对比度依赖虹膜与瞳孔的反差 |
| **眼型 / 内眦赘皮 / 单双眼皮** | 眼睑遮挡 glint 的概率差异极大 |
| **睫毛长度、是否化妆（睫毛膏）** | 遮挡和假反射 |
| **戴眼镜 / 隐形眼镜 / 角膜塑形** | 假 glint、角膜曲率被改变 |
| **年龄**（瞳孔大小范围、晶状体混浊） | 老年人瞳孔小且反应慢 |
| **斜视 / 弱视 / 义眼** | 双眼一致性假设不成立 |
| **瞳距（IPD）范围** | 极端 IPD 时眼睛可能不在相机最佳视场 |

**验收标准要写成分组的，而不是总体平均：**

> "不是'平均精度 < 1°'，而是**'每一个人群分组的 p90 精度 < 1.5°，且有效追踪率 > 95%'**。总体平均会把少数人群的失败藏起来。这个标准我会在项目开始就定下来，因为它决定了要招募什么样的被试池——**而招募被试池的周期是几个月，不能等到集成期才发现。**"

### 9.3 眼安全验证

| 项 | 方法 |
|----|------|
| 辐照度实测 | 光谱辐射计在眼盒位置测，覆盖所有 LED 全开的最坏情况 |
| IEC 62471 分类 | 目标 Exempt Group（豁免组） |
| **故障注入** | 人为让驱动短路 / 软件挂死 / 帧循环停止，**验证硬件保护真的关断了 LED** |
| 老化 | LED 长期驱动后的输出漂移（会影响 glint 强度和检测阈值） |

**故障注入这一项不能跳过。** "设计上有硬件保护"和"验证过硬件保护会动作"是两回事，合规评审会问后者。

### 9.4 延迟与扫视验证

- **端到端延迟测量**：光电二极管 + 高速相机，测"眼球开始动"到"屏幕上高清区移动"的物理时间。**不要用软件打点自测**，软件测不到显示链路。
- **扫视预测准确率**：用高速眼动仪（商用 500–1000 Hz 设备）作真值，统计预测落点误差分布。
- **回放框架**：录制眼部原始图像序列（**仅实验室，带被试知情同意**）+ 真值，离线回归算法改动。

> **注意这里的隐私边界：** 眼部图像语料库是敏感数据。实验室采集必须有知情同意、访问控制、保留期限；**绝不能有任何机制让量产设备上传眼部图像**——哪怕是"调试用"。我会把这一点写进架构约束，而不是靠流程约束。

### 9.5 Fleet SLI（只能是标量）

| SLI | 阈值 |
|-----|------|
| 有效追踪率（按会话） | p10 > 95% |
| 追踪丢失事件频率 | < 1 次/分钟 |
| 平均高清区半径（反映置信度） | 回归即告警（说明精度在退化） |
| 标定失败率 | < 2% |
| 标定后的自检残差分布 | 趋势监控 |
| **分 SKU / 分地区的上述指标** | 任一组显著偏离即调查（可能是人群覆盖问题的信号） |

**"平均高清区半径"是一个很聪明的代理指标**：它不需要知道真值，但它单调反映系统的置信度。如果某次 OTA 后这个数字涨了，说明追踪质量下降了，即使追踪率看起来没变。

## 10. 演进与组织

| 契约物 | Owner | 消费者 | 出事的方式 |
|--------|-------|--------|-----------|
| **LED 的 3D 位置与朝向**（CAD 名义值 + 产线实测偏差） | 光学 / 结构 | 你 | 用名义值而非实测值 → 每台设备有固定角度偏置，被误当成算法精度问题 |
| 相机内参 + 相机-LED 外参 | 标定（见 [`08-calibration-system.md`](./08-calibration-system.md)） | 你 | 与 tracking 的标定包版本不同步 |
| 注视 API：向量 + **置信度** + 时间戳 + 坐标系 | 你 | 渲染、交互、Avatar | 消费者忽略置信度字段 → §8 的降级原则失效 |
| 眼安全的硬件保护设计 | HW | 你 + 合规 | 需要设计评审签字，不能事后补 |
| 人群覆盖的验收标准与被试池 | 你 + UXR | 算法 | **定得晚 = 招募来不及 = 发布后暴雷** |
| 眼部图像的数据治理策略 | 隐私 / 法务 | 所有人 | 调试通道成为泄露路径 |

**分阶段：**

| 阶段 | 出口标准 |
|------|----------|
| P0 | 出图 + LED 频闪与 FSYNC 同步验证（示波器）+ 眼安全初测 |
| P1 | glint 检测与瞳孔分割跑通；单人精度 < 1° |
| P2 | 标定流程 + 滑动鲁棒性；回放框架建立 |
| P3 | **人群覆盖验证**（被试池必须在 P1 就开始招募） |
| P4 | 扫视预测 + 与渲染集成，端到端延迟实测 |
| P5 | 眼安全合规签字 + 故障注入 + fleet SLI |

**关键的组织判断：** 被试池招募的周期是几个月，而它的产出（人群覆盖数据）决定了算法要不要重做。**所以它必须在 P1 就启动，和算法开发并行，而不是等算法"做好了再验证"。** 这是 E6 会在项目计划上守住的一条依赖线——它不是技术难点，但它是最容易导致项目晚一个季度的那一条。

**收口金句：** 眼动追踪是一条**几何测量管线**，不是成像管线：glint 消除相机-眼睛的相对位移自由度，kappa 角把光轴变成视轴，扫视预测把延迟从高清区半径里买回来。而这个子系统的立项理由是一个可以算出来的比值——**260 mW 换回 1.2 W 的 GPU 节省，ROI 5×**；它的最大风险不是精度不够，而是**在实验室人群上达标、在真实人群上有 15% 的人用不了**。
