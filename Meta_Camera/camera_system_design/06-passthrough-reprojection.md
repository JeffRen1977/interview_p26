# 场景 6：Passthrough 重投影与 EIS

**典型题：** 设计头显的彩色 passthrough 系统，做到低延迟、几何正确、不晕。

**核心考点：** 相机光心 ≠ 眼睛光心的视差问题、深度感知重投影、late latching / timewarp、光子到光子延迟预算、EIS 与前庭一致性的冲突。

**为什么这题会出现：** passthrough 是 Quest 最公开的相机特性，而且它是**唯一一个"延迟就是画质"** 的相机场景——所有传统 ISP 的优化在这里都要重新权衡。

---

## 1. 需求与约束

| 维度 | 默认假设 | 为什么 |
|------|----------|--------|
| 相机 | 2 颗彩色 passthrough（RS 或 GS）+ 复用 tracking 相机做深度 | 彩色需要 Bayer；tracking 相机单色但基线好 |
| 分辨率 / 帧率 | 每眼 1080p 级 @ **60–90 fps**（与显示刷新对齐） | 帧率既是延迟也是流畅度 |
| **光子到光子** | **< 20 ms**（理想 < 15） | 超过就晕，且手眼协调失效 |
| 几何 | 近距离（< 1 m）物体的视差误差 **< 几个角分** | 否则看自己的手会觉得畸变 |
| 亮度适应 | 从暗室到户外阳光，动态范围要跟得上 | 摘头显重新适应是体验灾难 |
| 功耗 | passthrough 常开时接近热墙 | 与 03 篇的热预算直接冲突 |
| 失败 | 不允许黑屏、不允许卡住不动 | 用户看不见现实世界 = 安全问题 |

**开场金句：** passthrough 的核心矛盾是 **相机不在眼睛的位置**。这不是"延迟低就行"的问题——就算延迟为零，直接把相机画面贴到眼前，用户的手看起来也是歪的、距离是错的。所以架构中心是**深度感知的重投影**，延迟只是第二个约束。而且这条路径的失败是**安全问题**（用户看不见现实），所以它的降级策略必须比拍照路径保守得多。

## 2. 高层架构

```
[Passthrough Cam L/R]  ── 与显示刷新锁相（genlock）
        │ MIPI CSI-2
        ▼
   IFE：BLC → LSC → BPC → demosaic → 轻量 CCM/Gamma
        │  **绕过 TNR / MFNR / 重锐化**（延迟换质量）
        ▼ dma-buf + fence
   ┌────┴─────────────────────────┐
   ▼                              ▼
[深度估计]                    [彩色图像]
 立体匹配（tracking 相机       ▲
 或 passthrough 对）           │
 → 稀疏/半稠密深度图           │
   │                           │
   └────────────┬──────────────┘
                ▼
        **重投影（reprojection）**
        用深度把相机视角 warp 到眼睛视角
                │
                ▼
        与虚拟内容合成（MR）
                │
                ▼
        **Late latching + Timewarp**
        合成前一刻取最新 pose 再 warp 一次
                │
                ▼
            Display 扫描出
```

**两次 warp 是关键，要分清：**

| Warp | 解决什么 | 输入 |
|------|----------|------|
| **重投影（reprojection）** | **空间**问题：相机位置 ≠ 眼睛位置 | 深度图 + 相机/眼睛外参 |
| **Timewarp / late latching** | **时间**问题：从渲染到扫描出之间头又动了 | 最新 pose（IMU 传播，见 [`01-multi-camera-slam-sync.md`](./01-multi-camera-slam-sync.md) §6.3） |

混为一谈是常见错误。**重投影需要深度，timewarp 通常只用旋转（不需要深度，但也因此对平移无能为力）。**

## 3. 核心子系统

### 3.1 视差问题：为什么不能直接把相机画面贴上去

相机装在头显外壳前方，眼睛在后方，两者相距 **3–8 cm**。对距离 $d$ 的物体，视角差：

$$
\theta \approx \arctan\frac{b}{d}
$$

| 物体距离 | 相机-眼睛偏移 5 cm 的视角差 |
|----------|---------------------------|
| 5 m | 0.6° |
| 1 m | 2.9° |
| 0.5 m | 5.7° |
| **0.3 m（自己的手）** | **9.5°** |

> **9.5° 是巨大的。** 用户伸手抓一个杯子会抓偏。所以**近距离物体必须做深度校正**，远距离可以近似（$\theta$ 小于视觉分辨率就无所谓了）。
>
> 这个表直接给出了工程结论：**深度精度的要求是距离相关的——近处必须准，远处可以糊。** 所以深度估计的算力应该向近场倾斜（这也和人手交互的场景吻合）。

### 3.2 深度从哪来

| 来源 | 优点 | 缺点 |
|------|------|------|
| **Passthrough 双目立体匹配** | 与彩色图同源，颜色一致 | 基线短（两眼距离），远处精度差；无纹理区域失败 |
| **复用 tracking 相机立体** | 基线长、GS、已经在跑 | 单色、视场不同、需要跨相机标定 |
| **ToF / 结构光深度传感器** | 主动、不依赖纹理 | 功耗、成本、户外阳光下失效 |
| **单目深度网络** | 无需第二个视角 | 尺度不确定、时序不稳定（帧间抖动很致命） |

**实践选择：** 立体匹配为主 + 时序滤波，无纹理区域用平面/深度先验填充。**关键不是深度多准，而是深度要"时序稳定"**——抖动的深度会让画面"呼吸"，比恒定的偏差难受得多。

> **要说出的洞察：** "重投影对深度**误差**的容忍度比对深度**抖动**的容忍度高得多。恒定 10% 的深度偏差用户几乎察觉不到（大脑会适应），但 5% 的帧间抖动会让整个画面像在水下。所以我的深度模块的首要指标是**时序一致性**，不是单帧精度。这会改变算法选型——我会接受一个更平滑但略保守的方法。"

### 3.3 延迟：为什么 late latching 是必需的

朴素管线的延迟（见 §6.1 的完整账本）会到 40–60 ms，**远超 20 ms 目标**。

**Late latching 的原理：** 不要在渲染开始时取 pose，而是在**扫描出前的最后一刻**再取一次最新 pose，对已经渲染好的图做一次廉价的 warp。

```
t=0     取 pose_0，开始渲染 / 重投影
t=15ms  渲染完成
t=16ms  **重新取 pose_1（此时 IMU 已经更新了 16 ms）**
        用 (pose_1 - pose_0) 做一次旋转 warp
t=17ms  开始扫描出
```

**效果：** 用户感知的延迟从"整条管线"缩短到"最后一次 warp 到光子"，通常能砍掉 **10–20 ms**。

**代价与边界（必须说）：**

- Timewarp 通常只补偿**旋转**。平移补偿需要深度，成本高且会在遮挡边缘露馅（disocclusion——转头后露出原本被遮挡的区域，那里没有像素数据）
- 遮挡区域的填充：用上一帧、用背景外推、或者干脆模糊化。**没有完美方案，只有哪种更不明显**
- **Rolling display**：如果显示是逐行扫描的，不同行的光子发出时间不同，严格做法是**逐行（或逐条带）warp**，用该行实际的扫描时刻对应的 pose

### 3.4 曝光与显示锁相

Passthrough 相机必须与显示刷新**锁相（genlock）**，否则：

- 相机 60fps、显示 90Hz → 帧率不整除，会出现重复帧和抖动
- 曝光时刻相对显示扫描的相位漂移 → 延迟在几毫秒内周期性波动，用户感知为"忽快忽慢"

**做法：** 显示的 VSYNC 作为主时钟，相机 FSYNC 由它分频/锁相产生，相位可调（把曝光中点放在最有利的位置）。

> 这里和 [`01-multi-camera-slam-sync.md`](./01-multi-camera-slam-sync.md) §3.1 的区别要说清：**tracking 相机之间的同步是为了三角化；passthrough 相机与显示的同步是为了延迟稳定性。** 两者是不同的同步域，可能有不同的频率（tracking 90fps、passthrough 60fps、显示 90Hz），需要一个统一的时序规划。

### 3.5 EIS 在 VR 里的特殊性

手机 EIS 的目标是"画面稳定"。**VR 里这是错的。**

> **在头显里，画面必须跟着头动。** 如果做了强稳像，用户转头时画面不动，视觉信号和前庭系统的信号矛盾——**这正是晕动症的成因**。
>
> 所以 passthrough 的"EIS"只应该做**极高频的抖动抑制**（例如设备在头上的微小振动、走路时的高频颠簸），而绝不能抑制真实的头部转动。截止频率的选择是一个**需要和人因团队一起做的实验**，不是工程师能拍板的参数。

**RS 相机的额外问题：** 逐行曝光 + 头动 = 逐行的几何畸变。补偿需要：
1. 精确的行时间戳（`readout_ns / (H-1)` 的模型，见 [`../code/timestamp_sync.md`](../code/timestamp_sync.md)）
2. 该行曝光时刻的 pose（IMU 高频插值）
3. 逐行 warp

**这就是为什么 passthrough 用 GS 相机是值得的钱**——它把一个每帧都要做的算法问题变成了零。

## 4. 性能优化与边界

| 问题 | 策略 |
|------|------|
| **ISP 要砍什么** | TNR（引入至少 1 帧延迟）、MFNR、重锐化、复杂 tonemap 全部砍掉。保留 BLC/LSC/BPC/demosaic/CCM/gamma |
| **低光噪声** | 砍了 TNR 之后低光会很噪。折中：用**单帧空域 NR**（无延迟）+ 提高模拟增益；或用一个极轻量的 TNR（只用 1 帧参考，且接受 1 帧延迟） |
| **户外强光** | 曝光时间会很短，噪声不是问题，但**动态范围**是（看向窗外时室内全黑）。需要 HDR 或局部 tonemap，但这些都增加延迟 → 用 HW 的低延迟局部 tonemap，不用多帧 HDR |
| **色彩一致性** | 双眼的白平衡和曝光**必须一致**，否则双眼竞争（binocular rivalry）极其难受。AE/AWB 要跑成一个联合环，不是两个独立环 |
| **遮挡填充（disocclusion）** | 优先用上一帧的对应区域；再不行用邻域外推 + 轻微模糊（模糊比错误的锐利内容好） |
| **虚拟内容合成** | MR 场景要做深度遮挡（虚拟物体被真实桌子挡住），需要深度图与虚拟场景的深度缓冲比较 |

## 6. 数字预算

### 6.1 光子到光子的完整账本（这道题的核心）

每眼 1080p @ 90fps，GS 相机：

```
① 曝光                              4 ms（室内；中点作为参考）
② readout SOF→EOF                   8 ms      ← 由帧率决定
③ DMA 写完 + fence                  0.3 ms
④ IFE 处理（行级流水，不等整帧）      1 ms
⑤ 深度估计                          3 ms
⑥ 重投影 warp                       2 ms
⑦ 与虚拟内容合成                    2 ms
⑧ 等显示 VSYNC（最坏一个周期）       11.1 ms   ← 第二大项
⑨ Late latching warp                1 ms
⑩ 显示扫描出（到该像素）             0–11 ms（取决于行位置）
──────────────────────────────────────────
朴素总计（不含 late latching 收益）  ≈ 32–43 ms
```

**超标。** 三个能动的杠杆，按收益排序：

| 杠杆 | 省多少 | 代价 |
|------|--------|------|
| **① Late latching** | 把用户感知的延迟从 ⑤⑥⑦⑧ 之前的所有项，压缩到 ⑨→⑩ | 只补旋转；disocclusion 露馅 |
| **② 提帧率到 90/120** | ② 和 ⑧ 同时缩短，**这两项占了一半以上** | 功耗、带宽 |
| **③ 相机与显示锁相 + 相位对齐** | 把 ⑧ 从"最坏一个周期"变成"确定的小值" | 需要硬件支持 |

> **要说出的判断：** "②和⑧加起来 19 ms，占了一半，而它们都由**帧率**决定。所以 passthrough 的延迟优化 90% 是**时序设计**（帧率、锁相、相位），只有 10% 是软件优化。有人提议'优化重投影的 shader 省 0.5 ms'时，我会说这不是杠杆所在。"

**Late latching 之后的有效延迟：**

```
最后一次 pose 采样 → warp（1 ms）→ 扫描出（0–11 ms）
有效运动到光子 ≈ 2–12 ms  ✓ 达标
```

**但注意：** 这个"达标"只对**旋转**成立。平移和**画面内容本身的年龄**（内容还是 30 ms 前拍的）没有改变。所以：

> "我要区分两个指标：**运动到光子（motion-to-photon）** 通过 late latching 做到 < 12 ms；**画面内容年龄（content age）** 仍然是 30 ms 左右。前者决定晕不晕，后者决定'看自己的手动起来跟不跟得上'。**只报第一个数字是不诚实的**，而且会让人因团队测出与工程数字不符的结果。"

**这个区分本身就是很强的 E6 信号。**

### 6.2 带宽

每眼 1080p NV12 @ 90fps 单次通过：$1920 \times 1080 \times 1.5 \times 90 = 280$ MB/s。

| 通路 | 双眼 |
|------|------|
| ISP 写 | 560 MB/s |
| 深度模块读 | 560 MB/s |
| 重投影读 + 写 | 1120 MB/s |
| 合成器读 | 560 MB/s |
| **合计** | **≈ 2.8 GB/s** |

**加上 tracking 的 220 MB/s、虚拟内容渲染的 GPU 流量、显示读取——头显 SoC 的 DDR 会很紧张。**

削减手段：
- **重投影和合成融合成一个 GPU pass**（省掉一次读写，约 560 MB/s）
- **AFBC 压缩**（省 30–40%）
- **深度图降分辨率**（1/4 分辨率的深度对重投影通常够用，省大量带宽）

> 按 100 mW/(GB/s)，2.8 GB/s ≈ **280 mW 只是内存**。融合 pass + 压缩能省下 100 mW 以上——在一个热受限的头显上这是实打实的。

### 6.3 深度精度需要多少

立体匹配的深度误差：

$$
\Delta Z = \frac{Z^2}{f \cdot b} \Delta d
$$

其中 $b$ 是基线，$f$ 是焦距（像素），$\Delta d$ 是视差误差（像素）。

取 $f = 800$ px，$b = 6.5$ cm（瞳距），$\Delta d = 0.5$ px：

| 距离 $Z$ | 深度误差 $\Delta Z$ | 重投影角误差（5 cm 偏移） |
|---------|-------------------|------------------------|
| 0.3 m | 1.7 mm | 0.05° ✓ |
| 1 m | 1.9 cm | 0.11° ✓ |
| 3 m | 17 cm | 0.09° ✓ |
| 10 m | 1.9 m | 0.03° ✓ |

> **有意思的结论：深度误差随距离平方增长，但重投影的角误差需求随距离下降——两者恰好抵消。** 所以**均匀的视差精度（0.5 px）在所有距离上都够用**。这是一个能在白板上算出来、并且反直觉的结论：不需要为远处物体做特殊处理。
>
> 真正的问题不在精度而在**覆盖率**：无纹理区域（白墙）根本匹配不出视差。所以工程重点是**填充策略**而不是精度提升。

### 6.4 功耗

| Block | 功耗 |
|-------|------|
| 2 × 1080p 彩色 sensor @90fps | 300 mW |
| CSI + IFE + 轻 IPE | 250 mW |
| 深度估计（DSP/GPU） | 300 mW |
| 重投影 + 合成（GPU） | 400 mW |
| DDR 2.8 GB/s | 280 mW |
| **合计** | **≈ 1.5 W** |

**这是一个大数字。** 叠加 tracking 的 800 mW、显示、以及虚拟内容渲染——头显的整机功耗会到 6–10 W，需要主动散热（风扇）。

> **对比结论：眼镜上做全彩 passthrough 在功耗上是不可能的**（03 篇算出稳态上限 0.4–0.9 W）。这解释了为什么 Ray-Ban 类眼镜没有 passthrough，而这个结论应该在设计一开始就说出来，而不是画完架构才发现。

## 7. 关键决策与被否方案

| 决策 | 我选 | 否掉的 | 为什么 | 什么会让我翻盘 |
|------|------|--------|--------|----------------|
| ISP 深度 | **砍掉 TNR/MFNR/重锐化** | 复用媒体路径的完整 ISP | TNR 至少引入 1 帧（11 ms）延迟，直接吃掉一半预算 | 低光噪声成为首要投诉，此时上"1 帧参考的轻量 TNR"并接受 11 ms |
| 深度来源 | **立体匹配 + 时序滤波** | ToF 深度传感器 | ToF 户外失效、功耗成本高；立体与彩色同源 | 目标场景大量是无纹理室内（白墙办公室），立体覆盖率不可接受 |
| 深度指标 | **时序一致性优先于单帧精度** | 单帧精度优先 | §3.2：抖动比偏差难受得多 | 无 |
| Warp 策略 | **重投影（含深度）+ late latching（仅旋转）两段** | 一次性做完 | 分开做让 late latching 可以极晚、极廉价 | 无 |
| Timewarp 粒度 | **逐条带（strip）warp 匹配 rolling display** | 整帧一次 warp | 逐行光子时刻不同，整帧 warp 会在快速转头时产生画面内的几何不一致 | 显示是全局刷新（global illumination），此时整帧即可 |
| 双眼 3A | **联合环，双眼强制一致** | 各自独立 AE/AWB | 双眼亮度/色彩不一致会引发双眼竞争，极度不适 | 无 |
| EIS | **只抑制高频抖动，截止频率由人因实验定** | 按手机 EIS 强度稳像 | 抑制真实头动 = 晕动症 | 无 |
| 快门 | **GS**（如果预算允许） | RS + 逐行补偿 | 逐行补偿要精确行时间戳 + 逐行 pose，且遮挡边缘会有残差 | 成本约束，此时必须把逐行补偿做扎实并接受残差 |
| 失败时 | **冻结最后一帧 + 明显的视觉提示** | 黑屏 | **用户看不见现实世界是安全问题**；冻结画面虽然不对，但比黑屏安全，且提示让用户知道要摘头显 | 无 |

**最后一行值得展开：**

> "passthrough 的失效不是画质问题，是**安全问题**。用户可能正在走动、正在拿东西。所以我的降级原则和拍照路径完全相反：**拍照失败可以静默重试，passthrough 失败必须立刻、明确地告诉用户**。冻结帧 + 明显的边框提示 + 触觉反馈，让用户知道"现在看到的不是实时的"。这是一个需要和人因、法务一起定的策略。"

## 8. 失效模式与降级

| 失效 | 检测 | 恢复 | 用户可见 |
|------|------|------|----------|
| **深度估计失败**（无纹理区域） | 匹配置信度图 | 用邻域深度/平面先验填充；极端情况退化为**固定深度重投影**（假设所有东西在 2 m） | 近处物体略有几何误差 |
| **深度时序抖动** | 帧间深度差的统计 | 加强时序滤波（代价是响应变慢） | 画面"呼吸" |
| **Disocclusion 空洞** | warp 后的空洞掩码 | 上一帧填充 → 邻域外推 → 模糊 | 转头时边缘轻微拖影 |
| **pose 丢失 / tracking 降级** | tracking 置信度 | late latching 退化为纯旋转外推；持续丢失则冻结 + 提示 | 提示"追踪丢失" |
| **相机与显示失锁** | 帧时序抖动统计 | 重新锁相；期间接受延迟波动 | 轻微不流畅 |
| **双眼曝光不一致** | 双眼 AE 参数差 | 强制同步到较保守的一侧 | 无 |
| **单眼相机故障** | SOF 超时 | **不能只显示一只眼**（极度不适）→ 双眼都显示同一路 + 提示，或直接冻结提示 | 明确提示 |
| **低光噪声过大** | 增益超阈值 | 允许开启轻量 TNR（接受 +11 ms 延迟）并告知用户"低光模式" | 略有拖影 |
| **热降级** | thermal governor | 降 passthrough 帧率（90→60）；**不要降分辨率**（会闪） | 略不流畅 |
| **管线 hang** | watchdog（例如 3 帧周期） | **冻结最后一帧 + 强提示 + 触觉**，重启管线 | 明确的"passthrough 不可用"状态 |

**统一原则：** passthrough 的降级阶梯是 **"降流畅度 → 降几何精度 → 冻结并提示"**，**永远不允许黑屏，永远不允许静默失败**。

## 9. 怎么证明它是对的

### 9.1 延迟测量（必须是物理测量）

> **软件打点测不出 passthrough 延迟**，因为它测不到显示链路，而显示链路占了近一半。

**标准方法：**

```
高速相机（1000 fps）同时拍摄：
  ① 真实世界的一个运动物体（例如摆锤 / LED 阵列）
  ② 头显显示屏上该物体的成像（透过目镜或拆机直拍）
测量：两者在时间轴上的位移差
```

或者更精巧的：**旋转编码器 + 头显固定在转台上**，测量转台的物理角度与画面内容对应角度的时间差。这个方法能分离出**运动到光子**和**内容年龄**两个指标（§6.1 的关键区分）。

补充：**逐行延迟**——如果显示是 rolling 的，画面顶部和底部的延迟不同，要分别测。

### 9.2 几何正确性

| 测试 | 方法 | 指标 |
|------|------|------|
| **视差校正精度** | 已知距离的标定靶点，测量重投影后的角度误差 | 近场（0.3 m）< 0.5° |
| **手眼协调** | 被试伸手触碰真实目标，测量偏差 | 与裸眼对比的偏差增量 |
| **双眼一致性** | 同一物体在左右眼图像中的垂直视差（vertical disparity） | < 几个角分（垂直视差会引起眼疲劳） |
| **深度时序稳定性** | 静止场景下深度图的帧间标准差 | 这是 §3.2 的首要指标 |
| **Disocclusion 可见性** | 标准转头动作序列，人工评分 | 主观评分 |

### 9.3 舒适度验证（这一节是这道题的重点）

> **passthrough 的最终指标是"用户能不能长时间用而不难受"，这只能靠人测。** 客观指标（延迟、几何误差）是必要不充分条件。

| 测试 | 方法 |
|------|------|
| **晕动症问卷** | SSQ（Simulator Sickness Questionnaire）或 MSSQ，在标准任务后填写 |
| **长时佩戴** | 30–60 分钟连续使用，记录不适的发生时刻和强度 |
| **敏感人群** | 前庭敏感者、易晕车人群单独分组（**和 05 篇的人群覆盖是同一个道理**） |
| **任务表现** | 在 passthrough 下完成精细操作（穿针、打字、倒水）的成功率与耗时 |
| **EIS 截止频率** | A/B 不同截止频率，找到"抑制抖动"和"引发不适"之间的窗口 |

**关键的验证设计：** 舒适度实验必须做 **A/B 而不是绝对评分**——人对"有多难受"的绝对判断极不可靠，但对"A 和 B 哪个更难受"的判断相当可靠。

### 9.4 回放与故障注入

- **录制**：相机原始帧 + IMU + pose + 显示时序，全部带时间戳
- **回放**：能在 PC 上 bit-exact 重现整条管线（除了显示）
- **故障注入**：人为丢帧、注入 pose 抖动、模拟深度失败、模拟单眼故障——**验证 §8 的每一条降级路径真的会触发，且表现符合设计**

### 9.5 Fleet SLI

| SLI | 阈值 |
|-----|------|
| 运动到光子 p95（用软件可测的代理量） | < 15 ms |
| passthrough 帧率的稳定性（帧间隔的 p99/p50 比值） | < 1.3 |
| 深度覆盖率（有效深度像素占比） | p10 > 80% |
| Disocclusion 空洞面积占比 | p95 < 2% |
| 冻结/失败事件频率 | < 1 次/小时 |
| 双眼 AE 参数差异分布 | 趋势监控 |
| **热降级导致的 passthrough 降帧率占比** | 与 03 篇的热 SLI 联动 |

## 10. 演进与组织

| 契约物 | Owner | 消费者 | 出事的方式 |
|--------|-------|--------|-----------|
| **相机-眼盒外参**（相机光心相对眼睛的精确位置） | 光学/结构 + 标定 | 你 | 用 CAD 名义值而非实测 → 每台设备固定的视差偏差，被误当成算法问题 |
| 显示时序契约（VSYNC、最晚提交时刻、rolling 参数） | 显示 / 合成器 | 你 | late latching 的时间窗算错 → 掉帧或撕裂 |
| pose API（时间戳语义 + 置信度 + 外推能力） | Tracking | 你 | 与 01 篇同一份时间戳语义文档 |
| **EIS 截止频率与舒适度参数** | 人因 | 你 | 工程师自己调 → 晕 |
| passthrough 的 IQ 目标（与媒体路径不同） | IQ | 你 | IQ 团队用拍照标准调 passthrough → 延迟爆炸 |
| 降级状态的 UX 呈现 | 产品 / UX + 法务 | 你 | 静默失败 → 安全问题 |

**最容易出事的是倒数第二行。**

> "IQ 团队的默认目标是'好看'。但 passthrough 的 IQ 目标是**'低延迟 + 双眼一致 + 时序稳定'**，好看排第四。如果不在项目开始就把这个目标写清楚并让 IQ 团队接受，他们会很自然地加上 TNR 和锐化——然后延迟超标，而且没人觉得自己做错了。**这类冲突不是技术问题，是目标函数没对齐，而对齐目标函数是我的工作。**"

**分阶段：**

| 阶段 | 出口标准 |
|------|----------|
| P0 | 相机出图 + 与显示锁相验证（示波器 / 时序分析） |
| P1 | 直通显示（无重投影），**物理测量延迟**，建立测量台架 |
| P2 | 深度 + 重投影打通；几何精度达标 |
| P3 | Late latching + 逐条带 warp；运动到光子达标 |
| P4 | 舒适度验证（人因）；EIS 截止频率确定 |
| P5 | 降级路径 + 故障注入 + fleet SLI |

**P1 的延迟测量台架必须最先建。** 因为这道题的每一个后续决策都要用延迟数字来判断，没有可信的测量手段，团队会在"感觉快了一点"的争论里浪费几个月。

**收口金句：** passthrough 的核心不是延迟，是**相机不在眼睛的位置**——0.3 m 处 9.5° 的视差误差必须用深度感知的重投影消除，而 late latching 只解决时间不解决空间。延迟预算里 19 ms（一半以上）由帧率和显示锁相决定，软件优化只值 10%。而这条路径的失败是**安全问题**，所以它的降级阶梯只有一条底线：**永远不黑屏，永远不静默失败。**
