# 场景 8：标定系统（产线 → 在线 → OTA）

**典型题：** 设计一套覆盖产线、运行时、和 OTA 的相机标定系统，支撑百万台设备。

**核心考点：** 标定参数的分类与 owner、产线节拍与成本、在线精化的边界、标定包与固件的版本绑定、单台设备的可追溯性。

**为什么这题会出现：** 标定在其他每一道题里都被提到（[`01`](./01-multi-camera-slam-sync.md) 的外参、[`02`](./02-e2e-isp-pipeline.md) 的 LSC/BLC、[`05`](./05-eye-face-tracking.md) 的 LED 位置、[`06`](./06-passthrough-reprojection.md) 的相机-眼盒外参），但**它本身是一个完整的系统**，横跨工程、制造、供应链、售后。**这是最能区分"做过量产"和"只做过原型"的一道题。**

---

## 1. 需求与约束

| 维度 | 默认假设 |
|------|----------|
| 规模 | 百万台/年，产线节拍 **每台标定 < 30–60 秒** |
| 参数类型 | 内参、畸变、立体外参、IMU-相机、LSC、BLC、坏点、色彩、LED 位置、显示-相机 |
| 精度 | tracking 外参 < 0.1°；内参重投影误差 < 0.2 px；色彩 ΔE < 3 |
| 变化 | 温度漂移、机械应力、跌落、老化 |
| 存储 | 每台设备几百 KB – 几 MB，存在设备的 NVM 或云端 |
| 可追溯 | 每台设备的标定数据、标定时间、设备/工站、复检记录 |
| 售后 | 维修换模组后必须能重新标定 |

**开场金句：** 标定的核心问题不是"怎么算"，是**"哪些参数在什么时候由谁产生、怎么绑定、怎么演进"**。我会先把参数按**变化时间尺度**分成四类，因为不同类别的产生方式、存储位置、更新机制完全不同——把它们混成一个"标定文件"是我见过最常见的架构错误，它会让你无法单独更新某一类参数。

---

## 2. 参数分类：这是整道题的骨架

| 类别 | 变化尺度 | 例子 | 谁产生 | 存哪 | 怎么更新 |
|------|---------|------|--------|------|---------|
| **① 设计常量** | 永不变 | 名义焦距、传感器尺寸、CFA pattern、LED 名义位置 | 设计 | **固件内** | 随固件 OTA |
| **② 单台永久量** | 制造时固定 | 内参、畸变、立体外参、LED 实测位置、坏点表、LSC mesh、BLC 基准 | **产线** | **设备 NVM**（一次写入） | 只在维修时重写 |
| **③ 缓变量** | 小时–月 | 温度导致的外参漂移、时钟 skew、机械应力 | **运行时在线估计** | 设备可写区（带回滚） | 持续更新 |
| **④ 会话量** | 每次使用 | 用户 kappa 角、IPD、佩戴姿态 | **用户标定 / 隐式估计** | 用户配置 | 每次戴上或首次使用 |

**为什么这个分类是骨架：**

> - **① 和 ② 的区别决定了产线要做什么**——每多一项 ②，产线就多几秒和一台设备。
> - **② 和 ③ 的区别决定了架构**——② 是只读的信任基准，③ 是可变的但必须**被 ② 钳位**（在线估计不能跑飞）。
> - **④ 和前三者的区别决定了隐私**——④ 是用户数据，涉及生物特征，存储和删除有法律要求。
>
> **把它们放进同一个 blob 是灾难**：你无法只更新 ③ 而不动 ②，无法在换用户时只清 ④，无法在 OTA 时只推 ①。

## 3. 核心子系统

### 3.1 产线标定：节拍就是成本

**每一秒的节拍 = 百万台的产能和产线数量。** 30 秒 vs 60 秒，直接是一倍的设备投资。

**典型工站与耗时：**

| 工站 | 测什么 | 耗时 | 能否合并 |
|------|--------|------|---------|
| 光学靶标 | 内参、畸变、立体外参 | 10–20 s | 可以和 LSC 共用一次拍摄 |
| 积分球 / 均匀光源 | LSC、暗角、坏点 | 5–10 s | — |
| 遮光 | BLC、暗电流、热像素 | 3–5 s | 可与上一站合并 |
| 色卡 | 色彩、AWB 基准 | 5 s | 可与光学靶合并（多光源切换） |
| IMU-相机 | 时间偏移、外参 | 10–20 s | **最贵的一站**（需要机械运动） |
| 显示-相机（头显） | 相机与显示/眼盒的几何 | 10 s | — |

**优化节拍的三个手段：**

1. **一次拍摄多项复用**：一张包含靶标 + 色块 + 灰阶的复合标定板，一次拍摄同时算内参、色彩、暗角。
2. **抽检而非全检**：某些参数（例如色彩）的批次一致性好，可以**按批次抽检 + 全检简化项**。这是一个**统计决策**：要用早期数据算出批次内方差，才能定抽检率。
3. **把慢的挪到离线**：IMU-相机标定需要机械运动，很慢。可以改成**在线自标定 + 产线只做粗标定**——但这要求算法能可靠收敛，是一个风险交换。

> **E6 的表述：** "节拍是产线投资的直接函数，所以标定项的增减是**财务决策不只是技术决策**。我会给出一张表：每一项标定的耗时、它能带来的精度提升、以及不做它的后果——让产品和运营在同一组数据上做取舍。**工程师单方面决定'这个也标一下更保险'是不负责任的。**"

### 3.2 在线标定：必须被产线值钳位

**为什么需要在线：** 温度、机械应力、跌落会让外参漂移。tracking 对外参极敏感（0.1° 的外参误差在 1 m 处就是几毫米的三角化误差）。

**为什么必须钳位：**

> 在线估计是一个开环的优化过程，它可能**收敛到错误的解**（尤其在退化场景：只看一面白墙、长时间静止、只做纯旋转运动）。**一旦在线值跑飞并被持久化，设备就永久坏了，而且用户无法自己修复。**

**设计：**

```
在线估计值 = clamp(在线估计, 产线值 ± k·σ_产线公差)

if |在线估计 - 产线值| > 阈值 持续 T:
    → 不采纳，回退到产线值
    → 上报遥测（可能是硬件损坏的信号）
    → 提示用户可能需要送修
```

**持久化策略：**

| 层 | 内容 |
|----|------|
| 产线值（只读分区） | **永不覆盖**，是最后的安全网 |
| 在线值（可写，双份 A/B） | 定期写入，写入前校验；损坏则用另一份 |
| 会话值（内存） | 每次启动从在线值初始化 |

**要主动说的一句：** "**产线值是不可变的信任锚点。** 在线标定只能在它周围的一个小邻域里活动。这个设计的代价是在线标定无法修正真正的大偏差（例如跌落导致模组移位），但这是对的——那种情况应该走维修流程，而不是让软件假装还能用。"

### 3.3 版本绑定：这是最容易出事的地方

**标定数据不是孤立的，它和消费它的代码是一对。**

| 绑定关系 | 出事的方式 |
|---------|-----------|
| LSC mesh ↔ ISP FW | ISP 换了 LSC 的插值算法 → 旧 mesh 产生错误的暗角补偿 → **不崩溃，只是四角偏色**，灰度几天后才被投诉发现 |
| 外参 ↔ tracking binary | 坐标系约定改了（例如 Z 轴方向）→ tracking 完全错乱 → 这个会立刻被发现（好事） |
| 畸变模型 ↔ 消费者 | 从 5 参数改成 8 参数模型 → 旧数据缺字段 |
| BLC 温度表 ↔ 传感器批次 | 换了传感器供应商 → 温度系数不同 |

**机制：**

```
标定包 = {
    schema_version,          // 数据结构版本
    compatible_fw_range,     // 兼容的固件版本区间
    device_serial,           // 绑定到具体设备
    sensor_module_id,        // 绑定到具体模组（维修后必须匹配）
    calibration_timestamp,
    station_id,              // 哪个工站标的（追溯用）
    signature,               // 防篡改
    payload...
}
```

**启动时的校验必须是硬失败：**

```
if 标定包.schema_version 不被当前 FW 支持:
    → 拒绝加载，用安全回退值，上报遥测，功能降级
    → **不要"尽力解析"** —— 部分正确的标定比没有标定更危险
```

> **"部分正确比没有更危险"这句话值得展开：** 没有标定时系统知道自己没标定，会用保守的默认值和更大的不确定度。**部分正确的标定会让系统自信地给出错误结果**——例如外参错了 5°，tracking 不会报错，只会持续输出偏移的 pose。**静默的错误比明显的失败难查一个数量级。**

### 3.4 维修与售后

**换模组后必须重新标定。** 这意味着：

| 需求 | 设计 |
|------|------|
| 维修站要有标定能力 | 简化版标定工装（比产线便宜，精度略低但达标） |
| 模组与标定的绑定要能验证 | 标定包里存 `sensor_module_id`，启动时比对；不匹配则拒绝 |
| 部分重标 | 换主摄只需重标主摄相关项，不必全套重来 → **这要求标定包是可分片的**（呼应 §2 的分类） |
| 云端备份 | 设备 NVM 损坏时能从云端恢复（需要考虑隐私：标定数据本身通常不敏感，但要绑定设备身份） |

> **"可分片"是 §2 分类的直接收益。** 如果标定是一个大 blob，换一个模组就要全套重标，维修成本翻几倍。**架构决策在这里变成了售后成本。**

### 3.5 与温度的关系（贯穿各篇）

几乎所有参数都有温度依赖：

| 参数 | 温度效应 | 处理 |
|------|---------|------|
| **黑电平 BLC** | 暗电流随温度指数增长 | **用遮光像素（OB）区实时测量**，而不是查表——这是最可靠的做法 |
| **外参** | 结构件热膨胀 | 产线在 2–3 个温度点标定，运行时按温度插值（一阶模型够用） |
| **时钟 skew** | 晶振 ppm 随温度变 | 在线估计（见 [`../code/timestamp_sync.md`](../code/timestamp_sync.md)） |
| **焦距**（塑料镜头） | 热致对焦漂移 | 定焦系统要在设计时留景深余量；有 AF 的可以补偿 |
| **LED 输出**（眼动） | 强度随温度变 | 检测阈值要自适应，不能用固定阈值 |

> **BLC 那一行是最重要的：** "黑电平必须用 OB 区实时测，不能纯查表。因为它同时依赖温度、增益、曝光时间和器件个体差异，查表覆盖不了组合空间。**这是一个'产线标定做不到、必须在线做'的典型例子**——识别出哪些参数属于这一类，是这道题的核心判断。"

## 4. 性能优化与边界

| 问题 | 策略 |
|------|------|
| **标定数据大小** | LSC mesh 是大头（例如 17×13 网格 × 4 通道 × 2 字节 = 1.7 KB，但高精度可能到几十 KB）。用低阶多项式拟合替代密集网格能压缩 10×，代价是拟合残差 |
| **加载时间** | 冷启动时读 NVM + 解析 + 校验签名，要 < 100 ms（在启动预算里） |
| **在线估计的算力** | 外参在线精化可以低频跑（例如 1 Hz），不必每帧 |
| **写 NVM 的磨损** | 在线值不要每帧写；用"显著变化 + 定期"策略，并且 A/B 双份轮流写 |
| **掉电保护** | 写标定时掉电 → A/B 双份 + 校验和 + 原子切换指针 |

## 6. 数字预算

### 6.1 产线节拍就是钱

假设年产 300 万台，产线每天有效工作 20 小时，一年 300 天：

$$
\text{所需产能} = \frac{3\times10^6}{300 \times 20 \times 3600} = 0.139\ \text{台/秒}
$$

$$
\text{所需工位数} = 0.139 \times \text{节拍(秒)}
$$

| 节拍 | 所需并行工位 | 相对设备投资 |
|------|-------------|-------------|
| 30 s | 4.2 → **5 个** | 1× |
| 45 s | 6.3 → **7 个** | 1.4× |
| 60 s | 8.3 → **9 个** | 1.8× |

> **每增加 15 秒节拍 ≈ 增加 2 个标定工位。** 一个光学标定工位（含精密靶标、运动机构、光源、夹具、控制）的量级是几万到几十万美元。**所以"多标一项"的对话应该是这样的：**
>
> "这一项要 12 秒，会让节拍从 33 秒到 45 秒，需要多 2 个工位，大约 X 万美元的资本支出，外加占地和维护。它带来的收益是 tracking 精度从 0.15° 到 0.10°。**这个收益值 X 万美元吗？** 这个问题我回答不了，需要产品和运营一起定——但我能保证的是，如果不做，在线自标定能否补上这个差距，我可以用现有数据给出一个概率。"
>
> **把技术选择翻译成资本支出，是 E6 和 E5 在这道题上最明显的差别。**

### 6.2 精度预算的分配（误差链）

外参误差最终表现为三角化误差：

$$
\Delta_{\text{position}} \approx Z \times \tan(\Delta\theta_{\text{extrinsic}})
$$

在 1 m 处，0.1° 的外参误差 → **1.7 mm** 的位置误差。

**误差要分配到各个来源（这是一张必须画的表）：**

| 来源 | 分配预算 | 怎么控制 |
|------|---------|---------|
| 产线标定的测量误差 | 0.04° | 靶标精度、拍摄张数、优化收敛判据 |
| 装配公差残差（标定后的剩余） | 0.03° | 标定本身就是为了吸收装配公差，残差来自模型不完美 |
| 温度漂移（工作范围内） | 0.05° | 多温度点标定 + 一阶补偿 |
| 机械应力 / 老化 | 0.05° | 在线精化 |
| **RSS 合成**（平方和开根） | $\sqrt{0.04^2+0.03^2+0.05^2+0.05^2} = \mathbf{0.086°}$ | ✓ 进 0.1° 预算 |

> **用 RSS 而不是直接相加**，因为这些误差源是独立的。直接相加（0.17°）会让你过度设计。**能正确地做误差合成，是这道题的硬技能信号。**
>
> 而且这张表**直接指导投资**：如果温度漂移项超了，加一个温度点比提高靶标精度便宜得多。

### 6.3 数据量与存储

| 参数 | 大小 |
|------|------|
| 内参 + 畸变（每相机） | ~100 B |
| 立体外参（每对） | ~50 B |
| IMU-相机（外参 + 时间偏移） | ~100 B |
| **LSC mesh**（17×13×4ch×2B） | **1.7 KB**（高精度可到 20 KB） |
| 坏点表（稀疏，1000 个坏点 × 4B） | 4 KB |
| 色彩 CCM + AWB 基准（多光源） | ~500 B |
| LED 位置（眼动，12 颗 × 6 自由度） | ~300 B |
| **单台合计** | **~10–50 KB** |

300 万台 × 30 KB = **90 GB** 的云端标定数据。**这不大**，可以全量存储并支持按序列号查询——这对追溯（"这批设备的外参分布有没有异常"）价值极高。

> **主动提出建立标定数据仓库：** "把每台设备的标定结果都存到云端，不只是为了恢复，更是为了**制造质量的统计过程控制**。如果某一天某条产线的外参分布均值偏移了，那是夹具松了或者靶标脏了——**在良率下降之前就能发现**。这个能力的边际成本几乎为零，因为数据已经产生了。"

## 7. 关键决策与被否方案

| 决策 | 我选 | 否掉的 | 为什么 | 什么会让我翻盘 |
|------|------|--------|--------|----------------|
| 参数组织 | **按变化尺度分四类，可分片** | 单一标定 blob | §2：决定了能否单独更新、能否部分重标、能否分离用户数据 | 系统极简（单相机、无在线标定），此时 blob 更省事 |
| 在线估计 | **必须被产线值钳位** | 自由在线估计 | 跑飞后设备永久损坏且用户无法自救 | 无 |
| 黑电平 | **OB 区实时测量** | 温度查表 | 组合空间（温度×增益×曝光×个体）表覆盖不了 | 传感器没有 OB 区（罕见） |
| 版本不匹配 | **硬失败 + 安全回退 + 遥测** | 尽力解析 | §3.3：部分正确比没有更危险 | 无 |
| IMU-相机标定 | **产线做粗标（快）+ 在线精化** | 产线做精标 | 精标需要机械运动，是最贵的一站；而 VIO 本来就能在线估计这些量 | 在线估计的收敛性在目标使用场景下不可靠（例如用户很少做激励充分的运动） |
| 色彩标定 | **按批次抽检 + 全检简化项** | 全检 | 需要早期数据支持——**这个决策必须用批次内方差的实测数据来定，不能拍脑袋** | 批次一致性差 |
| 标定数据存储 | **设备 NVM（权威）+ 云端备份（恢复与追溯）** | 只存设备 | NVM 损坏 = 设备报废；云端备份成本极低 | 隐私/合规不允许（标定通常不敏感，但要确认） |
| LSC 表示 | **看精度需求定：密集网格 vs 多项式拟合** | 一律密集网格 | 存储和加载时间 vs 拟合残差 | — |

## 8. 失效模式与降级

| 失效 | 检测 | 恢复 | 用户可见 |
|------|------|------|----------|
| **标定数据损坏 / 校验失败** | 启动时签名 + 校验和 | 用 A/B 的另一份；都坏则用出厂只读分区；再不行用云端恢复或通用默认值 + 功能降级 | 严重时"设备需要维修" |
| **版本不兼容** | schema/FW 版本校验 | 硬失败 + 安全回退 + 遥测 | 画质/精度降级 |
| **模组 ID 不匹配**（换了模组没重标） | 启动时比对 | 拒绝加载该模组的标定，用通用值 + 强提示 | "相机需要校准" |
| **在线估计跑飞** | 偏离产线值超阈值持续 T | 回退产线值 + 遥测 + 可能提示送修 | 精度降级 |
| **在线值写入时掉电** | A/B + 校验和 | 用另一份 | 无 |
| **NVM 磨损失效** | 写入错误率 | 减少写频率；只读回退 | 在线优化失效 |
| **产线工站漂移**（夹具松动、靶标脏污） | **标定结果的统计过程控制（SPC）** | 报警停线复检 | 无（在出厂前拦截） |
| **某批次传感器 OTP 数据异常** | 产线的 OTP 校验 + 批次统计 | 拦截该批次 | 无 |
| **温度补偿模型失效**（超出标定温度范围） | 温度超出标定区间 | 外推但扩大不确定度；极端则提示 | 精度降级 |

**倒数第三行是这道题独有的、其他题没有的失效模式：**

> "**产线本身会漂移。** 夹具用几万次会松、靶标会脏、光源会衰减。如果没有对标定结果做统计过程控制，你会在几万台设备出厂之后才通过用户投诉发现问题——而那时候召回成本已经是天文数字。
>
> 所以标定系统的一个**必需组件**是 SPC：实时监控每条产线、每个工站的标定结果分布（均值、方差、异常率），任何显著漂移立即报警停线。**这不是锦上添花，这是标定系统的核心功能之一。**"

## 9. 怎么证明它是对的

### 9.1 标定精度本身怎么验证

**元问题：怎么知道标定是对的？** 不能用同一套数据自证。

| 方法 | 说明 |
|------|------|
| **留出验证（hold-out）** | 标定用一部分靶标位姿，验证用另一部分，看重投影误差 |
| **独立真值** | 用更高精度的设备（三坐标测量机、光学动捕）测同一台设备的几何，与标定结果比对 |
| **交叉验证** | 同一台设备在不同工站/不同时间标两次，看重复性 |
| **端到端指标** | 最终的 tracking 精度、图像质量——**这才是真正关心的指标**，标定精度只是中间量 |

> **要说的判断：** "标定的重投影误差低**不等于**下游算法就准。我见过重投影误差 0.15 px 但 tracking 精度很差的情况——因为标定的位姿覆盖不足，模型在使用区域外推了。**所以验收标准必须是端到端的**（tracking ATE、图像 ΔE），标定的内部指标只用来诊断。"

### 9.2 产线验证

| 测试 | 方法 |
|------|------|
| **Gauge R&R**（量具重复性与再现性） | 同一台设备在同一工站重复标定 N 次（重复性）、在不同工站标定（再现性）；变异应远小于公差 |
| **金标设备（golden unit）** | 几台已知真值的设备，定期在每条产线上过一遍，验证工站没有漂移 |
| **节拍实测** | 不是设计值，是实测的 p95（含异常重试） |
| **良率与失败原因分布** | 标定失败的设备为什么失败？是设备问题还是工站问题？ |

**金标设备是最实用的一条：** 每条产线每班次跑一次金标设备，结果偏离即停线。这比纯统计的 SPC 反应更快、更明确。

### 9.3 在线标定验证

- **注入式测试**：人为给外参加一个已知偏差，验证在线估计能收敛回来，且收敛时间在预期内
- **退化场景测试**：白墙、纯旋转、长时间静止——验证在线估计**不会跑飞**（这比验证它能收敛更重要）
- **钳位验证**：给一个超出公差的偏差，验证系统拒绝采纳并上报
- **长跑**：几天的连续使用，看在线值的漂移轨迹是否合理

### 9.4 版本兼容验证

**矩阵测试：** 老标定 × 新 FW、新标定 × 老 FW、损坏的标定 × 各版本 FW——**每一格都要验证行为符合设计**（正确加载 / 正确拒绝 / 正确回退）。

**这个矩阵要进 CI**，因为 FW 每次改动都可能破坏兼容性，而这类问题在人工测试里极易漏掉。

### 9.5 Fleet SLI

| SLI | 阈值 |
|-----|------|
| 标定加载成功率 | > 99.99% |
| 标定校验失败率（按原因分） | ~0 |
| 模组 ID 不匹配率 | ~0（非零说明维修流程有问题） |
| 在线估计偏离产线值的分布 | p99 在公差内 |
| 在线估计被拒绝（钳位触发）的比例 | < 0.1% |
| **按产线/工站/批次分组的标定参数分布** | SPC 监控，任何漂移即调查 |
| 端到端精度指标（tracking ATE、色彩 ΔE）按批次分组 | 批次间无显著差异 |

**倒数第二行是这道题最有价值的 SLI**：它把 fleet 数据反馈回制造。

> "设备出厂后的真实表现，是产线质量的最终检验。如果某个批次的 tracking 精度分布明显差于其他批次，那是标定或制造的问题——**而这个信号只能从 fleet 拿到，产线自己看不到**。建立这条从 fleet 回到产线的反馈回路，是标定系统真正成熟的标志。"

## 10. 演进与组织

### 10.1 契约

| 契约物 | Owner | 消费者 | 出事的方式 |
|--------|-------|--------|-----------|
| **参数的数学定义与坐标系约定** | 你 | 所有算法团队 | "外参是 A 到 B 还是 B 到 A"、"畸变是正向还是反向"——**这类歧义会产生一个符号错误，症状是系统性偏差，能藏几个月** |
| 标定包 schema + 版本策略 | 你 | FW、算法 | 见 §3.3 |
| 公差范围（在线钳位的阈值来源） | 光学/结构 | 你 | 用猜的阈值 → 要么钳得太紧（正常漂移被拒）要么太松（跑飞没拦住） |
| 产线节拍预算与工站清单 | 你 + 制造 | 运营 | 定得晚 → 产线设备来不及采购 |
| OTP 格式 | 模组供应商 | 你 | 换供应商时格式变了 |
| 维修站工装规格 | 你 + 售后 | 制造 | 想不到 → 换模组的设备无法恢复 |
| SPC 的监控指标与报警阈值 | 你 + 质量 | 制造 | 没建 → 产线漂移无人发现 |

**第一行是最隐蔽也最贵的：**

> "坐标系约定的歧义是标定系统的头号杀手。'相机到 IMU 的外参'这句话有两种理解，符号相反。如果标定团队和算法团队理解不同，结果是一个恒定的偏差——**系统能跑，只是精度差一点，而且没人觉得是自己的问题**。
>
> **我的做法是：不写自然语言定义，写可执行的定义。** 提供一个参考实现（几十行代码），明确给出'给定这个外参，一个 IMU 坐标系的点怎么变换到相机坐标系'，并配一组测试向量。**任何消费者必须先通过测试向量。** 这比十页文档有效得多。"

### 10.2 分阶段

| 阶段 | 出口标准 | 备注 |
|------|---------|------|
| **P0（最早）** | 参数分类表 + 坐标系约定 + 参考实现与测试向量 | **必须最早做**，因为所有下游都依赖它 |
| P1 | 实验室手工标定跑通全链路；端到端精度可测 | 不等产线 |
| P2 | 标定包 schema + 版本机制 + 兼容性矩阵测试 | |
| P3 | 产线工装原型；节拍实测；Gauge R&R | **与产线设备采购并行**——采购周期长 |
| P4 | 在线标定 + 钳位 + 退化场景验证 | |
| P5 | SPC + 金标设备 + fleet 反馈回路 + 维修流程 | |

**两条关键的依赖线（E6 要守住的）：**

1. **P0 必须最早。** 参数定义是所有人的输入，晚一个月就是所有下游晚一个月，而且已经写的代码要返工。
2. **P3 的产线工装采购周期是几个月。** 如果等到软件都做完了才去定工装，产线会成为量产的瓶颈。**所以节拍预算和工站清单要在 P1 阶段就给出初版**，哪怕还不精确——采购需要一个数字才能开始。

> **这两条是"技术上不难但组织上最容易翻车"的典型。** 能在设计讨论里主动提出"这两件事的时间线比技术方案本身更关键"，是 E6 的判断力信号。

**收口金句：** 标定系统的骨架不是算法，是**按变化尺度把参数分成四类**——设计常量随固件走、单台永久量在产线一次写入、缓变量在线估计但被产线值钳位、会话量属于用户。这个分类决定了能否单独更新、能否部分重标、能否分离用户数据。而这道题真正的 E6 内容在三处：**把节拍翻译成资本支出**（每 15 秒 ≈ 2 个工位）、**用 RSS 做误差预算分配**（指导钱花在哪）、以及**建立从 fleet 回到产线的 SPC 反馈回路**（因为产线本身会漂移，而这个信号产线自己看不到）。
