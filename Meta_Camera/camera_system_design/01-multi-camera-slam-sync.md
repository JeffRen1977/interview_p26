# 场景 1：AR/VR 空间感知 — 多相机 6DoF SLAM / Controller Tracking

**典型题：** 设计一个针对 6DoF SLAM / Controller Tracking 的多相机同步感知系统。

**核心考点：** 多 Sensor FSYNC/VSYNC、Global vs Rolling Shutter、曝光锁相、IMU–Camera 时间戳、MIPI 低功耗高帧率路径。

---

## 1. 需求与约束

先钉死产品，再画图。VR 头显与眼镜 tracking 相机不是同一套预算。

| 维度 | 默认假设（头显 tracking） | 为什么 |
|------|---------------------------|--------|
| 相机 | 4 路 inward/world GS（两对立体）+ 可选 2 路控制器 IR | 6DoF 需要多视角；控制器常用闪烁 LED + 头显相机 |
| 规格 | 640×480 或 800×600，**RAW8/10**，60–90 fps（冲刺 120） | 特征点够用；分辨率上去带宽和 ISP 立刻爆 |
| IMU | 6 轴 1 kHz，与相机 **同一晶振域或可测偏移** | VIO 融合；1ms 误差在 100°/s 转动下是像素级错位 |
| 延迟 | 曝光中点 → pose 输出 **< 5–10 ms** | 合成层 / 重投影要赶上下一帧 display |
| 功耗 | tracking 子系统持续 **< 几百 mW** 量级（头显可略宽） | 不能走完整拍照 ISP |
| 失败 | 丢 FSYNC、MIPI CRC、SOF timeout、热降帧 | IMU 不能停；要有 degrade 而不是黑屏 |

**开场金句：** 这不是拍照 Pipeline。Tracking 相机要 **固定或缓变曝光、Global Shutter、硬件同步、FE-only、零拷贝进 CV/DSP**。美颜、TNR、3A 猎焦全部砍掉。

## 2. 高层架构

```
                    SoC 时钟 / 同步器
                           │ FSYNC (GPIO / dedicated PLL)
           ┌───────────────┼───────────────┐
           ▼               ▼               ▼
     [GS Cam L]       [GS Cam R]     [GS Cam …]     [IMU 1kHz]
           │               │               │              │
           │ MIPI CSI-2    │               │              │ SPI/I2C/SLIMbus
           ▼               ▼               ▼              ▼
        CSIPHY/CSID  (每口独立或 VC 复用)
           │
           ▼
        IFE FE-only：BLC + 可选 binning + 硬件时间戳
           │ 不解 Bayer 成预览 YUV
           ▼
        dma-buf 环（每路 SPSC，cache-line 对齐）
           │ fence
           ▼
        Tracking DSP / NPU：特征 → 光流/描述子
           │
           ▼
        VIO / SLAM 融合（IMU 预积分 + 视觉更新）
           │
           ▼
        Pose 给 compositor / controller 解算
```

**控制面：** CCI 配 mode、exposure、gain、FSYNC slave。  
**数据面：** MIPI → CSID → IFE DMA，CPU 不碰像素。

与拍照 ISP 解耦：同一颗 SoC 上 **CV usecase graph ≠ media usecase graph**。详见 [`02-e2e-isp-pipeline.md`](./02-e2e-isp-pipeline.md)。

## 3. 核心子系统

### 3.1 多 Sensor 硬件同步（FSYNC / VSYNC）

软件“尽量同一时刻 `streamon`”不够。90fps 下一帧 11ms，1ms 的软件抖动就是 **8% 的帧相位误差**，立体匹配和多目三角直接漂。

推荐拓扑：

1. **SoC 主时钟** 产生周期 FSYNC 脉冲（或专用 sync PLL）。
2. 所有 tracking sensor 配成 **external trigger / slave**：收到 FSYNC 边沿才开始积分。
3. Master 不再用“某颗 sensor 当主、其余跟”——主从级联会叠 settle 延迟。统一 SoC 触发，相位可配。

Bring-up 验证（面试加分）：示波器看各路 `FSYNC` 与 `FSIN` 边沿，目标 **< 50–100 µs** 对齐（具体看 sensor 手册）。再对比各路 SOF 硬件时间戳差。

VSYNC 是显示域概念。Tracking 同步说 **FSYNC / FSIN**；若还要和显示锁相（passthrough），另做 **display genlock**，不要和相机 FSYNC 混成一个词。

### 3.2 Global Shutter vs Rolling Shutter

| | Global Shutter | Rolling Shutter |
|---|---|---|
| 积分 | 全阵列同时 | 逐行开始 |
| 快转头 / 摆手 | 特征几何真 | 垂线变斜、控制器 LED 拖影 |
| 噪声 / 成本 / 功耗 | 通常更差、更贵 | 手机主摄主流 |
| Tracking | **必选** | 仅低端或极低速兜底 |

口述：**Rolling shutter 行时间 × 角速度 = 像素剪切**。IMU 可以补偿 RS，但要精确到行时间戳，标定和算力都更贵。头显 tracking 用 GS 把问题从算法挪回硬件，这是正确的钱。

主摄 / passthrough 仍可能是 RS：那条路径走 EIS + 行时间戳，**不要和 tracking 相机共用同一套曝光策略**。

### 3.3 曝光动态锁相

Tracking 要在“不糊”和“不欠曝”之间：

- **运动优先：** 曝光上限钳位（例如 ≤ 2–4 ms @ 90fps），宁可提 analog/digital gain。
- **多路同一曝光时间：** 立体对必须相同 integration time，否则亮度不一致，匹配打穿。Gain 可以每路略调（镜头、遮光不同）。
- **不要跑完整 AE 猎值：** 用慢环（几十帧）或分区增益；禁止 3A 每帧大幅改曝光导致光流失效。
- **室内闪烁：** 50/60Hz 灯。GS 整帧同时积分，选曝光为电网周期整数倍可减 banding；RS 更惨。检测电网频率后锁 exposure。

“锁相”在这里有两层：**(a) 多路曝光时间一致；(b) 与市电/PWM 光源相位稳定。** 面试时分开说。

### 3.4 IMU–Camera 时间同步

VIO 误差对时间比对内参更敏感。目标：每帧一个 **曝光中点时间戳**，落在 **IMU 时钟域**。

```
Sensor SOF ──► CSI/IFE 打硬件 timestamp（SoC 单调钟或专用 timer）
IMU sample ──► 同一 timer 或已知换算的 PHC

t_mid = t_SOF + t_exposure / 2     （GS）
t_mid_row = t_SOF + row * t_line   （若被迫用 RS）

pose 融合使用 t_mid，而不是“用户态 clock_gettime 收到 buffer 的时间”
```

校准：

1. **静态偏移：** 产线或开机用 LED / 机械激励同时打 IMU 和相机，估 $\Delta t_0$。
2. **漂移：** 两路时钟不同晶振，用缓慢 Kalman / PLL 跟 $\dot{\Delta t}$（典型 ppm 级）。
3. **禁止** 用“buffer 出队时间”当曝光时间——那是调度延迟。

Controller tracking：头显相机看到 LED 闪烁码，LED 与控制器 IMU 也要同步。常用 **光编码 + 同一无线时钟域**，或头显发 IR sync。讲清楚 **三方时间**（头显 IMU、头显相机、手柄 IMU）。

### 3.5 MIPI CSI-2 → SoC/DSP 传输

带宽粗算（RAW8，640×480@90fps，4 路）：


$$
640 \times 480 \times 1 \times 90 \times 4 \approx 110\ \mathrm{MB/s}
$$

加上 MIPI 包头、RAW10（×1.25）、blanking，仍远小于 4K 视频。瓶颈通常是 **口数 / lane 数 / 同时 IFE 客户端**，不是理论 Gbps。

要点：

- 每路独立 CSI 口最干净；口不够再用 **VC 复用**（CSID 按 VC 分给不同 IFE）。
- Tracking 走 **RAW8/10 packed**，在 CV 侧解包或 FE 解成 8-bit。不要升到 16-bit preview。
- 连续 dma-buf 环，深度 3–4：sensor 写 n、CV 读 n-1，多一帧抗 ISR 抖动。
- 低功耗：lane 在帧间隙进 LP 模式；不要为 tracking 开 C-PHY 全家桶除非口不够。

CSIPHY vs CSID 故障切分见 [`camera/sensor.md`](../../camera/sensor.md)。

## 4. 性能优化与边界

| 问题 | 策略 |
|------|------|
| 延迟 | FE-only；特征提取在 DSP；pose 用上一帧 IMU 传播（async）赶显示 |
| 带宽 | binning / ROI；室内降到 60fps；远处相机 30fps（若算法允许） |
| 掉帧 | IMU 继续预积分；视觉更新用“上一有效帧 + 更大协方差”；**不要**插一张黑帧进 SLAM |
| 热 | 先降 CV 复杂度（描述子维度）再降 fps；FSYNC 周期跟着改，避免“相机 45fps、算法仍按 90 等帧” |
| 失同步 | 检测 SOF 时间戳差超阈值 → 丢该立体对、单目+IMU 降级；告警校准 |

Tiling：tracking 分辨率小，一般不必 stripe；passthrough 才 stripe。

## 5. 跨团队落地

| 团队 | 你要对齐的契约 |
|------|----------------|
| Sensor HW | FSIN 极性/建立时间、GS 行读出、OTP 坏点、每路 extrinsics 安装公差 |
| 结构 / 光学 | 基线、遮光、IR 滤光；热膨胀 → 外参随温度的一阶模型 |
| 算法 / SLAM | 时间戳定义（SOF vs 曝光中点）、坐标系、丢帧语义、最大曝光 |
| IQ | tracking 几乎无 IQ；只保证 BLC 稳定、不饱和。不要把拍照 LSC 套过来导致特征漂移 |
| FW / 驱动 | FSYNC PLL、SOF 打戳寄存器、dma-buf 队列深度 |

产线：Zhang 标定内参 + 立体外参；IMU-cam 用视觉靶或 LED。结果进 **校准 blob**，与 tracking binary 版本绑定（同 OTA 故事，见总清单 OTA 节）。

**收口金句：** 多相机 tracking 的正确性首先是 **同一微秒开始曝光 + 同一时钟域的曝光中点时间戳**；算法再强也补不了未定义的时间。

## 6. 数字预算（当场算，必须收口）

### 6.1 带宽：tracking 根本不缺带宽，缺的是"口"

4 路 640×480 GS RAW8 @ 90fps：


$$
640 \times 480 \times 1 \times 90 = 27.6\ \mathrm{MB/s}\ \text{(per cam)}\quad\Rightarrow\quad 4 \times 27.6 = 110\ \mathrm{MB/s}
$$

CV 侧还要**读一遍**：总 DDR 流量 ≈ **220 MB/s**。头显 SoC 的 LPDDR5 可用带宽 10–25 GB/s，**这占不到 2%**。

MIPI 侧：每路 payload $= 640\times480\times8\times90 = 221$ Mbps，加 15% 开销 ≈ 255 Mbps。**一条 1.5 Gbps 的 D-PHY lane 能扛 5 路**。

> **所以要主动说出来：** "带宽不是这题的约束。真正的约束是 **CSI 口数、CSID 的 VC 通道数、以及 IFE 能同时服务几个客户端**。如果 SoC 只有 3 个 IFE 客户端而我有 4 路相机，我要么 VC 复用两路进同一个 IFE 上下文（要求它们分辨率格式一致），要么改用行交织。这是我第一个要向 SoC 团队确认的数字。"

主动报出带宽不是瓶颈，比算错瓶颈更能体现判断力。

### 6.2 功耗：tracking 子系统的账

| Block | 数量 | 单价 | 小计 |
|-------|------|------|------|
| GS VGA sensor @90fps | 4 | 50 mW | 200 mW |
| CSIPHY + CSID | 4 路 | 20 mW | 80 mW |
| IFE FE-only（BLC + 打戳） | 1 | 100 mW | 100 mW |
| DDR 流量 220 MB/s | — | ~100 mW/(GB/s) | 22 mW |
| DSP 特征提取（4 路 @90fps） | 1 | 250 mW | 250 mW |
| VIO 融合（CPU 一个大核部分占用） | 1 | 150 mW | 150 mW |
| **合计** | | | **≈ 800 mW** |

**这个数字的意义：** 头显有几 W 预算，800 mW 的 always-on tracking 可接受。**眼镜没有**——1.5–2.5W 的整机预算里 tracking 占 800mW 意味着录像根本开不起来。

> **所以：** 眼镜上的空间感知必然是 **更少的相机（2 路而非 4 路）+ 更低帧率（30fps 而非 90）+ 更多依赖 IMU 推算**，视觉更新退化成"漂移校正"而不是主要位姿来源。**这个结论要在设计里直接说出来**，而不是把头显方案原样搬到眼镜上。

### 6.3 延迟账本：这里有一个必须点破的矛盾

先老实把账列出来（640×480 @90fps）：

```
曝光时间 2 ms          → 中点参考
readout（SOF→EOF）     ≈ 7 ms      ← 最大的一项
DMA 写完 + fence signal   0.3 ms
DSP 特征提取             2.5 ms
VIO 视觉更新             2.5 ms
────────────────────────────────
曝光中点 → 位姿可用    ≈ 13 ms
```

**但需求写的是 pose 更新 < 5–10 ms。矛盾。**

> **E6 的答案不是"优化到 5ms"，而是指出需求被误读了：**
>
> "13 ms 是**视觉更新**的延迟，它是收敛不到 5 ms 的——readout 一项就 7 ms，除非提帧率或换 readout mode。但**给合成器的 pose 输出不需要等视觉**。架构是：
>
> - **VIO 视觉更新**：90 Hz，13 ms 延迟，负责**修正漂移**
> - **pose 输出**：IMU 前向传播（forward propagation）到 1 kHz，延迟 < 1 ms，负责**跟手**
> - 合成前再做一次 **late latching**：取当前时刻 IMU 传播的最新 pose
>
> 所以'< 5–10 ms'约束的是 **IMU 传播路径**，而不是视觉路径。视觉路径的真正指标是**漂移率**（m/min、deg/min）和**更新间隔的抖动**。"

**这一段是这道题最强的加分点**：它证明你理解 VIO 为什么是 IMU 主导 + 视觉修正，而不是"相机算位姿"。

派生结论：既然视觉是慢修正，**降 tracking 帧率对跟手性几乎无影响，只影响漂移**——这直接给了热降级的第一把刀。

### 6.4 交错曝光：用同样的硬件把有效视觉更新率翻倍

立体对内部**必须同时曝光**（三角化的前提）。但**两对之间不必**：

```
时刻:   0ms      5.5ms     11ms     16.5ms
Pair A: [曝光]            [曝光]
Pair B:          [曝光]            [曝光]
```

代价：DDR/MIPI 峰值被摊平（好事）；收益：VIO 的视觉更新间隔从 11 ms 变成 5.5 ms，**同样的功耗下漂移改善**。

代价的另一面：跨对的特征匹配不再是同一时刻，做 4 目联合三角化时要按各自时间戳做 IMU 补偿。**这是一个真实的 trade-off，值得在白板上画出来并说明我选哪个。**

> **我的选择：** 头显上做交错（算法团队能吃下时间补偿，收益明确）；眼镜上不做（只有一对相机，无所谓）。

## 7. 关键决策与被否方案

E6 要**收敛**，并说清楚**什么证据会让我改主意**。

| 决策 | 我选 | 否掉的方案 | 为什么 | 什么会让我翻盘 |
|------|------|-----------|--------|----------------|
| 同步源 | **SoC 生成 FSYNC，全部 sensor 做 slave** | Sensor 主从菊花链 | 菊花链每跳叠 settle 延迟且相位不可单独配；SoC 主控可以给每路配相位偏移（做交错曝光的前提） | SoC 没有可用的同步 timer 外设，或 FSYNC 走线太长信号完整性不过关 |
| 快门 | **Global Shutter** | RS + 逐行 IMU 补偿 | RS 补偿需要精确到行的时间戳 + 更重的标定 + 算法复杂度；把问题从算法挪回硬件是对的钱 | 极低成本 SKU，且角速度上限能压到 ~50°/s 以下（此时行时间 × 角速度的剪切 < 1 px） |
| 位深 | **RAW8** | RAW10 | 角点检测 8-bit 够用；省 20% 带宽和一步解包 | 场景动态范围极端（室内看窗外），特征在暗区全丢——此时上 RAW10 或 **PWL 压扩（companding）**，而不是简单提 gain |
| 曝光策略 | **曝光时间钳位 + 慢环 AE（几十帧时间常数）** | 每帧全速 AE | 快速改曝光会让光流/描述子跨帧不一致，直接打穿匹配 | 场景光照突变（进出隧道）成为主要失败模式，此时改成"快速但只改 gain 不改 integration time" |
| 立体对增益 | **integration time 严格一致，gain 允许每路微调** | 全部严格一致 | 镜头透过率、遮光、模组批次差异会导致同样曝光下亮度不同，匹配代价升高 | 算法侧已做光度标定（vignetting + response curve），那就全部锁死更简单 |
| 时钟对齐 | **硬件时间戳打在 CSID SOF 中断** | 用户态收到 buffer 时取 `clock_gettime` | 后者含调度抖动，几 ms 级，直接吃掉整个时间预算 | 没得选（SoC 不提供硬件打戳）——那就必须在设计里显式建模这个抖动并向算法团队申报 |

**否掉方案的表述方式很重要。** 说"RS 不行"是 E4；说"RS 在角速度 < 50°/s 时可用，我们的产品用例 P95 角速度是 200°/s，所以不行"是 E6。

## 8. 失效模式与降级阶梯

E6 的 FMEA 要有**四列**：失效 → 怎么检测 → 怎么恢复 → 用户看到什么。

| 失效 | 检测信号 | 恢复动作 | 用户可见性 |
|------|----------|----------|-----------|
| **FSYNC 丢失 / 相位漂移** | 各路 SOF 硬件时间戳两两差值超过阈值（例如 > 100 µs）连续 N 帧 | 在帧边界重新 arm 同步；期间该批帧标记 `unsynced`，算法降级为单目 + IMU | 无（除非持续，则轻微漂移） |
| **单路相机掉线**（CSI 错误 / 供电） | 该路 SOF 计数停止 / DQBUF 超时 | 从 VIO 观测集中摘除该路；协方差按剩余基线放大；尝试软复位该路 CSI 链路（**不重启整个 session**） | 追踪精度下降；若掉到只剩单目，提示"追踪质量降低" |
| **MIPI CRC / ECC 错误** | CSID 错误计数寄存器，按帧统计 | 单帧错误 → 丢该帧；持续错误 → 降 lane rate 或降帧率重试；记录到 fleet 遥测 | 偶发无感；持续则表现为帧率下降 |
| **CSID overflow** | overflow 状态位 | 说明下游来不及收：优先怀疑 DDR 拥塞或 IFE 客户端冲突，降帧率 | 帧率下降 |
| **热降频** | thermal zone 越过阈值 | **降 tracking 帧率**（90→60→45），同时**必须改 FSYNC 周期并通知算法**——否则算法按 90fps 等帧会一直超时 | 漂移略增，跟手性不变（因为 IMU 传播不受影响） |
| **外参随温度漂移** | VIO 残差的系统性偏置；或在线估计的 extrinsics 偏离产线值 | 把外参的一阶温度项放进 VIO 状态向量做在线精化，**但要钳位**在产线公差 ±k σ 内 | 无；超出钳位则告警要求重标定 |
| **时钟域漂移**（sensor 晶振 vs SoC） | `ClockOffsetEstimator` 的 offset 窗口出现单调斜率 | 在线估计 skew（ppm）并补偿；见 [`../code/timestamp_sync.md`](../code/timestamp_sync.md) | 无 |
| **长时间静止后重定位** | 视觉更新连续失败 N 秒 | 进入 relocalization；期间 pose 纯 IMU 推算并快速发散 | "正在重新定位" |
| **全黑 / 全白场景**（关灯、强光直射） | 特征数低于阈值 | 不要往 SLAM 里塞黑帧；扩大协方差，靠 IMU 撑过去；若超过 X 秒则提示 | 提示"环境光线不足" |

**防抖振：** 每一档降级都要有滞回（例如 90→60 在 42°C 触发，60→90 要等回到 38°C 且稳定 30 秒）。降级动作**必须单调**，禁止在两档之间来回跳。

**关键一句：** "IMU 永远不停。所有视觉侧的降级都表现为**漂移变大**，而不是**黑屏或卡顿**——这是设计原则，不是实现细节。"

## 9. 怎么证明它是对的（E6 最强信号）

### 9.1 台架：LED 频闪同步 rig

**这是这道题的标志性验证方法，能说出来就赢一半。**

```
信号发生器 ──┬─► 高速 IR LED（微秒级上升沿，放在所有相机视野内）
             └─► GPIO 直接进 SoC 的同一个 timer / 或直接打进 IMU 的 sync 脚

测量：LED 亮的那一帧，各路相机报的曝光中点时间戳
      与 GPIO 事件时间戳之差
```

这个 rig 一次同时验证三件事：
1. **多相机相位对齐**（各路报的时间戳应该一致，残差就是同步误差）
2. **时间戳绝对正确性**（相机域 vs IMU 域的真实偏移，不是推算的）
3. **曝光中点计算是否正确**（改变曝光时间，偏移不应该跟着变——如果跟着变，说明你报的是 SOF 而不是中点）

第 3 点尤其重要：**大量真实 bug 是"时间戳定义写错了"**，而只有变曝光时间的实验能抓到它。

补充台架：
- **示波器直接测 FSIN 引脚边沿**：目标 < 50–100 µs 对齐（看 sensor 手册的 setup time）。这是 bring-up 第一天做的事。
- **电动云台 / 转台**：已知角速度下扫棋盘格，用于估计 camera–IMU 时间偏移（Kalibr 的做法：把 $\Delta t$ 当标定参数一起优化）和验证 RS 剪切。
- **热箱**：从 -10°C 到 60°C 扫，测外参漂移量和时钟 skew 随温度的变化，产出温度补偿模型。

### 9.2 回放框架（regression 的基石）

```
录制：RAW 帧 + IMU 原始样本 + 所有硬件时间戳  →  磁盘
回放：bit-exact 灌进 VIO，输出轨迹
指标：ATE（绝对轨迹误差）/ RPE（相对位姿误差）vs 动捕真值
```

**关键设计要求：整条 pipeline 必须能脱离硬件回放。** 这意味着时间戳、丢帧、乱序都要能在回放里复现。做不到这一点，你永远只能"在真机上凭感觉调"，每次 SoC 或驱动改动都要重跑一遍全部手工测试。

配套：一个**故障注入**开关——回放时人为丢帧、注入 100 µs 同步误差、注入时钟漂移，验证 §8 的每一条降级路径真的被触发了。**降级路径不被测试就等于不存在**，这是 E6 会主动说的话。

### 9.3 真值来源

| 方法 | 精度 | 用在哪 |
|------|------|--------|
| 光学动捕（OptiTrack / Vicon） | 亚毫米 / 亚度 | 实验室黄金真值，标定和回归 |
| 机械转台 | 角度精确，位置受限 | 时间同步和 RS 验证 |
| 闭环轨迹（回到起点） | 只给漂移量 | 现场快速检查，不需要动捕 |
| 多传感器互检（视觉 vs 轮式/UWB） | 中等 | 外场长时间测试 |

### 9.4 上线后看什么（fleet SLI）

**不能上传图像**（隐私 + 带宽），所以指标必须是标量：

| SLI | 定义 | 告警阈值示例 |
|-----|------|-------------|
| 同步误差超限率 | 各路 SOF 时间戳两两差 > 100 µs 的帧占比 | > 0.1% |
| 视觉更新丢失率 | 连续 3 帧无有效视觉更新的发生频率 | > 1 次/分钟 |
| 重定位次数 | 每小时 relocalization 事件数 | > 2/小时 |
| 追踪丢失时长 | 纯 IMU 推算持续时间的 p95 | > 500 ms |
| 在线外参偏离 | 相对产线值的偏移分布 | p99 超出公差 |
| 丢帧率（按层） | sensor / CSI / IFE / 算法各一个计数器 | 任一层 > 0.5% |

**分层的丢帧计数器是设计要求，不是调试功能**——见 [`../additional_questions.md`](../additional_questions.md) §3 的分层定位法。要在架构阶段就把这些计数器设计进去，而不是出问题了再加。

**OTA 之后按 SKU 分组对比这些 SLI**，任何一组回归就 halt rollout。

## 10. 演进路线与组织落地

E6 的答案要能回答"这东西怎么真的做出来"。

### 10.1 分阶段交付

| 阶段 | 目标 | 出口标准 |
|------|------|----------|
| **P0 Bring-up** | 单相机出图、时间戳可信 | 示波器验证 FSIN；LED rig 验证时间戳定义；单目 + IMU 能跑出轨迹 |
| **P1 多路同步** | 4 路 FSYNC 对齐 | 同步误差 p99 < 100 µs；回放框架跑通 |
| **P2 精度达标** | ATE / 漂移进指标 | 动捕对比达标；故障注入全部降级路径验证通过 |
| **P3 功耗热** | 进 800 mW 预算 | 功耗逐 block 实测；热降级阶梯在热箱验证 |
| **P4 量产** | 标定 + 遥测 | 产线标定节拍达标；fleet SLI 上线；OTA 回滚演练 |

**依赖倒排：** 回放框架必须在 P1 就有，否则 P2 之后每次改动都要重跑真机。**这是最容易被砍、但砍了最痛的一项**——E6 要能守住它。

### 10.2 跨团队契约（谁 own 什么）

| 契约物 | Owner | 消费者 | 版本绑定 |
|--------|-------|--------|----------|
| Sensor mode 表（HTS/VTS、FSIN 极性与 setup time） | Sensor / FW | 驱动 | 与驱动版本绑定 |
| **时间戳语义定义文档**（SOF? 曝光中点? 哪个时钟域?） | 你（相机系统） | 算法、驱动、FW | **这份文档是 P0 的交付物**，写晚了后面全是返工 |
| 标定 blob 格式与内容 | 标定团队 | VIO、ISP | 与 tracking binary 的 major 版本绑定 |
| 帧元数据 schema（seq、时间戳、曝光、gain、sync 状态） | 你 | 算法 | 只增字段不改语义；改语义要 bump 版本 |
| 降级状态机的状态定义 | 你 | 算法、上层应用 | 算法必须能消费"这帧不同步"的标记 |
| FSYNC 周期变更 API | 你 | 算法、热管理 | 热管理改帧率时算法必须收到通知 |

**最容易出事的是第 2 行和最后一行。** "算法以为是曝光中点、驱动报的是 SOF" 这类 bug 能藏几个月，表现为一个恒定的小漂移，谁都不觉得是自己的问题。**主动说出"我会先把时间戳语义写成文档并让三方签字"，是很强的 E6 信号。**

### 10.3 Partner 晚交付时的 plan B

- **Sensor 样片晚到** → 先用 EVB + 已有 sensor 搭同步 rig，把 FSYNC 和打戳的软件路径验证完；回放框架用录制数据推进算法。
- **SoC 的硬件打戳有 bug** → 短期用 SOF 中断在内核打软戳（已知有几十 µs 抖动），把这个抖动量申报给算法团队让他们建模，同时推 SoC 团队修。**申报比隐瞒重要**。
- **标定产线没就绪** → 先用实验室手工标定跑通全链路，产线节拍问题单独并行推进。

**收口金句（E6 版）：** 多相机 tracking 的正确性首先是 **同一微秒开始曝光 + 同一时钟域的曝光中点时间戳**；但系统的可交付性取决于另外两件事——**回放框架**（否则你无法回归）和**分层的失效计数器**（否则你无法在 10 万台设备上定位）。算法再强也补不了未定义的时间，工程再强也补不了不可观测的系统。
